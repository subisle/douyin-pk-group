# 25 · 展示端抖音头像（2026-10-16）

> **需求来源：2026-10-16 用户口径**（原话要点，本文按此口径实现与验收）：
> ① 展示端主界面「主播列表」要显示主播的**抖音真实头像**；
> ② **已经注销的账号不用取头像**；
> ③ 头像要**本地留存**（防抖音以后改接口 / 取不到图）；
> ④ **每 7 天刷一遍**（服务内定时器，不依赖外部 cron；**2026-10-16 二期口径变更：更新改默认手动**，定时器默认不启动，`AVATAR_SYNC_ENABLED=1` 可重开自动，见 §12）；
> ⑤ **后续新加的主播也要自动纳入**，且**全部主播都同步**（不看是否展示）；
> ⑥ **展示不展示由后端决定**（`person.hide_in_daily_report` / 榜单口径），前端只渲染后端下发的 item。
>
> 适用页面：展示端数据榜「主播列表」（领奖台 + 名次行，`/st/m`、`/st/f`）。
> 涉及：迁移 `rust/crates/pk-server/src/migrations/025_person_avatar.sql`、
> 同步器 `rust/crates/pk-server/src/avatar_sync.rs`、
> 下发 `rust/crates/pk-server/src/public_teams/avatars.rs`（端点）与 `public_teams/site.rs`（榜单 DTO）。
> 契约：`contracts/pk-local/openapi.yaml`（`operationId: publicAvatar`）。
> 本文只做设计与验收；**验收流程里的数据库命令一律只读 SELECT**（沿用 docs/15 的纪律）。

## 1. 一句话结论

抖音头像用**服务内定时器**从抖音开放页面接口取一次，**JPEG 原图落 PG 的 `person_avatar` 表**（事实源是库，不落文件系统）；
榜单 item 只带一个**同源路径** `avatar`，浏览器再按路径回读本地副本。
抖音接口哪天改了/封了，页面照样有图 —— 这就是「本地留存」的全部意义
（请求失败与「号查不到」两种失效形态都保留本地图，2026-10-16 已收口；唯一会清图的是「账号已注销」，见 §9）。

> **2026-10-16 二期口径变更**：上文「服务内定时器」自二期起**默认不启动**（`AVATAR_SYNC_ENABLED` 默认 `1` → `0`），
> 更新改为**默认手动**（管理页同步按钮 / `sync-avatars` CLI，见 §12）；设 `AVATAR_SYNC_ENABLED=1` 可重开自动刷新。
> 取图、留存、下发链路（本节其余内容）不变。

## 2. 需求口径逐条落地（用户口径 → 实现）

| # | 用户口径 | 落地方式 | 验收锚点 |
|---|---|---|---|
| ① | 主播列表显示抖音真实头像 | 日/月/年榜 item 新增 `avatar` 字段；前端 `<img>` 渲染 | 榜单 JSON 有 `avatar`、页面见真头像 |
| ② | 已注销账号不用取头像 | 响应 `special_state_info.special_state=1` → 记 `note='deregistered'`、**不下载图片** | `note='deregistered'` 的行 `image IS NULL` |
| ③ | 头像本地留存 | 图片字节写 `person_avatar.image`（BYTEA）+ `source_url` 留原图 URL | `image IS NOT NULL` = **82 行**（§10 本机实测） |
| ④ | 每 7 天刷一遍（服务内） | 后台定时任务，`AVATAR_SYNC_DAYS=7` 按 `synced_at` 判定；`AVATAR_SYNC_CHECK_SECS` 默认 21600（6 小时醒一次）。**二期起定时器默认不启动**（`AVATAR_SYNC_ENABLED` 默认 0），改手动触发（§12），7 天新鲜度判定本身不变 | 定时器日志 + `synced_at` 分布 |

> **二期补注（2026-10-16）**：④ 的「定时器」已默认关闭（`AVATAR_SYNC_ENABLED` 默认 1 → 0），更新改**默认手动**（管理页按钮 / CLI，§12）；上表保留一期原口径供追溯。
| ⑤ | 新主播自动纳入、全部主播都同步 | 同步范围 = `person.deleted_at IS NULL` 的**全部人**（**不过滤** `hide_in_daily_report`）；没有 `person_avatar` 行的人（新登记）天然到期，下一次检查就捞到 | 新登记抖音号后一轮内出现该行 |
| ⑥ | 展示与否由后端决定 | 前端只渲染后端下发 item；`avatar` 由榜单口径（含 `hide_in_daily_report`）决定是否随行下发 | 被隐藏的人不在榜单 item 里 |

> **注意 ⑤ 与 ⑥ 的分工**：同步器「全部主播都同步」（连 `hide_in_daily_report=1` 的人也取图、留图），
> 因为他们可能随时被放回榜单；而**下不下发**是榜单口径的事 —— 后端不下发的 item，前端根本看不到。

```
                         ┌─────────────── 展示端浏览器（手机） ───────────────┐
                         │  数据榜「主播列表」（领奖台 + 名次行）             │
                         │  有 avatar → <img src="/api/public/avatars/…">     │
                         │  无 avatar（null）→ 姓名首字色块回落               │
                         └───────▲──────────────────────────┬────────────────┘
                                 │ ① 榜单 JSON：item.avatar  │ ② 取图
                                 │    = /api/public/avatars/ │
                                 │      <personId>?v=<hash>  │
                                 │      （无图 = null）      ▼
   GET /api/public/teams/{team}/daily|monthly|yearly   GET /api/public/avatars/{person_id}
                                 │                          │
                                 ▼                          ▼
                       public_teams/site.rs          public_teams/avatars.rs
                       （榜单 DTO，含 avatar）        （读 person_avatar.image）
                                 │                          │
                                 │                          ├─ 有行且 image 非空 → 200 image/jpeg（长缓存）
                                 │                          └─ 无行 / image 为空      → 404
                                 ▼
                              PostgreSQL · person_avatar
                                 ▲
                                 │ upsert（图变更才换行；失败不动旧行）
                                 │
   ┌────── 刷新链路（服务内定时器※二期默认关 / 手动触发）──────────────────┐
   │ 每 AVATAR_SYNC_CHECK_SECS（默认 21600s）醒一次                        │
   │ （※2026-10-16 二期起定时器默认不启动，AVATAR_SYNC_ENABLED=1 才醒）     │
   │   → 捞 person.deleted_at IS NULL 的全部人                             │
   │       · 没有 person_avatar 行（新登记主播）        → 立即纳入           │
   │       · synced_at 超过 AVATAR_SYNC_DAYS（默认 7 天）→ 到期重刷          │
   │       · person_avatar 仍在新鲜期内（synced_at 未过期）→ 跳过   │
   │       · person_avatar.note='deregistered'              → 照常到期复查，但不下载图片 │
   │   → 按 account.douyin_no（is_primary DESC, id）逐个探测                │
   │   → GET https://www.iesdouyin.com/web/api/v2/user/info/?unique_id=…   │
   │       · status_code=0 + avatar_thumb.uri → 取 CDN 200x200 JPEG        │
   │       · special_state=1（已注销）        → note=deregistered，不取图   │
   │       · status_code=5（号查不到）        → note=not_found，**保留原图**  │
   │       · 网络 / 非 JPEG / 超限           → 保留旧图 + WARN，不写库      │
   └───────────────────────────────────────────────────────────────────────┘
```

## 4. 数据来源（非官方契约，故障点就在这）

| 项 | 值 |
|---|---|
| 用户信息接口 | `GET https://www.iesdouyin.com/web/api/v2/user/info/?unique_id=<抖音号>` |
| 请求头 | iPhone UA（移动端 UA，免签名，实测可用）；`Referer: https://www.douyin.com/` |
| 成功判定 | `status_code=0` 且 `user_info.avatar_thumb.uri` 非空（`avatar_medium.uri` 为兜底） |
| 已注销判定 | `user_info.special_state_info.special_state=1`（接口可能同时没有 `sec_uid` / 头像字段） |
| 查不到 | `status_code=5`（`status_msg` 多为「参数不合法」）→ 号改名 / 号废：落 `note='not_found'` + 刷新 `synced_at`，**保留原图**，等新鲜度过期再试（2026-10-16 收口，见 §9） |
| 图片地址 | `https://p3.douyinpic.com/aweme/200x200/<uri>.jpeg` |
| 尺寸桶 | 抖音 CDN **只认 100 / 200 / 720 / 1080** 四档；其它尺寸返回 400 JSON。取 200x200（单张约 3KB） |

> ⚠️ 这是抖音**网页端接口，不是官方开放平台契约**，随时可能改字段、加签名或限流。
> 接口口径唯一权威处：`avatar_sync.rs` 顶部常量 + 本文 §4；改接口时两处一起改。

## 5. 表结构（迁移 `025_person_avatar`）

`person_avatar`（一人一行，主键 `person_id`；**不加 FK 约束** —— 与 `account` / `daily_metric` 一致，
是真外键语义、由服务层维护，见 docs/12 外键口径）：

| 列 | 类型 | 语义 |
|---|---|---|
| `person_id` | `BIGINT PRIMARY KEY` | 主播 id（真外键指向 `person.id`，不加约束） |
| `image` | `BYTEA`（NULL） | 抖音 CDN 200x200 档 JPEG 原图。`NULL` = **当前没有留存的图**：没取到过 / 已注销被清 / 收口前（T6 之前）查不到被清 |
| `mime` | `VARCHAR(32) NOT NULL DEFAULT 'image/jpeg'` | 恒为 `image/jpeg`（入口按文件魔数校验，非 JPEG 一律不收） |
| `source_url` | `VARCHAR(512) NOT NULL DEFAULT ''` | 抖音 CDN 原图 URL，接口失效后人工回溯 / 重抓用 |
| `hash` | `VARCHAR(16) NOT NULL DEFAULT ''` | `image` 内容的前 16 位 md5(hex)；下发拼成 `?v=<hash>` 破缓存，图一变 URL 就变，因此可放心长缓存 |
| `note` | `VARCHAR(32) NOT NULL DEFAULT ''` | 探测结论：`''` 正常 / `deregistered` 已注销 / `not_found` 号查不到（schema 另预留 `no_douyin_no`、`bad_response`）。**实现当前只写前三种** |
| `synced_at` | `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP` | 上次探测时间（「查不到 / 已注销」也算探测过）；7 天刷新靠它判定 |

索引：`idx_person_avatar_synced (synced_at)`（定时器按到期时间捞人）。

**为什么存库、不落文件、也不塞进 `person`**（与 023 对 `admin_messages` 图片同口径）：

- `person` 是榜单 / 台账每查必读的表，百来行 × 3KB 的图塞进去没必要，列表投影只该拿小字段；
- 文件系统的副本不随库走（换机 / 恢复 / 迁移就丢）—— **本项目的事实源是 PG**；
- 图片单独一表，读写路径分明：同步器只写它，头像端点只读它。

**没有抖音号的人不写行**：`person_avatar` 只在真正探测过之后才有行；没登记抖音号的人查无此表行。
补登记抖音号后，这个人下一轮就变成「无行 = 到期」被自动捞到（口径⑤）。

## 6. 刷新策略

- **范围**：`person.deleted_at IS NULL` 的**全部人**（不过滤 `hide_in_daily_report`）。
- **候选判定**：有抖音号 **且**（`person_avatar` 无行 **或** `synced_at` 早于 `now() - AVATAR_SYNC_DAYS`）→ 本轮探测；
  否则跳过（本轮 `fresh_skipped`）。到期判定用**库里的 `now()`**，不吃本机时钟。
- **已注销**：结论落 `note='deregistered'`，**不下载头像字节**；`synced_at` 一并刷新，
  所以 7 天新鲜度内不再探测，到期后才复查一次（确认仍注销）。
- **号查不到**（`status_code=5` / 有 `user_info` 但无头像字段）：落 `note='not_found'` + 刷新 `synced_at`，
  **保留已留存的图**（2026-10-16 收口：查不到 ≠ 要清图），等新鲜度过期再试；运营在台账改号后自然修好。
- **失败**（网络 / HTTP 非 2xx / 解析失败 / 不是 JPEG / 超过 64KB）：**一个字都不写**，
  保留上一次的图，下轮再试。
- **`--force`**：忽略新鲜度整批重抓；**`--days N`** 覆盖到期阈值（`0` = 全部视为到期）。
  日常由手动触发（二期）或定时器（`AVATAR_SYNC_ENABLED=1` 时）按到期增量化，不打扰抖音。

> `AVATAR_SYNC_DAYS` 走环境变量时最小 1（`config.rs` 的 `.max(1)`）；`--days 0` 只存在于命令行。
>
> **二期补注（2026-10-16）**：本节「刷新策略」描述的是**探测规则**（范围 / 候选 / 失败处置），这些没变；
> 变的是触发方式——定时器默认不启动，改管理页按钮 / CLI 手动触发（§12.1）。

**触发方式**：① 手动 —— 管理后台「主播管理」页同步按钮（`POST /api/admin/avatars/sync`，二期新增，见 §12）或 CLI `sync-avatars`；② 服务内后台定时器（**二期起默认关**，`AVATAR_SYNC_ENABLED=1` 才启动）。**不依赖外部 cron。**
定时器每轮先看「有没有缺图 / 超期的人」，**没有候选就不发任何抖音请求**（空转不打扰接口）。

环境变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `AVATAR_SYNC_ENABLED` | `0`（**二期改**，原 `1`） | 定时器总开关；**默认不启动**（2026-10-16 二期口径：更新改默认手动）。显式设 `1` 重开自动刷新；设 `0` 或不配只关定时器，手动命令仍可用 |
| `AVATAR_SYNC_DAYS` | `7` | 新鲜度天数：`synced_at` 超过它就重刷（用户口径④；手动同步的「无图或超 7 天」默认范围也用它） |
| `AVATAR_SYNC_CHECK_SECS` | `21600` | 检查间隔秒（6 小时）；仅定时器开启时生效，本地验证可设小值（如 `60`） |

## 8. 接口契约

### 8.1 榜单 item 新增字段

`GET /api/public/teams/{team}/daily|monthly|yearly` 的每个 item 新增：

```json
{
  "name": "南方楠",
  "avatar": "/api/public/avatars/123?v=9f2c1ab34d5e6789",
  "...": "其余字段不变"
}
```

- `avatar` = **同源头像路径**，值为 `/api/public/avatars/<personId>?v=<hash>`；**没有头像时为 `null`**。
- `?v=<hash>` 是内容版本号：图片内容变了 hash 就变，URL 随之变化，因此可放心长缓存。
- **DTO 白名单不变**：**不新增任何内部 id / 抖音号字段**（榜单 item 照旧不下发 `personId`、
  更不下发 `douyinNo`；`avatar` 里的数字 id 是图片定位键，与已有的内部 id 字段口径不冲突，见 §11 风险）。

### 8.2 头像端点

`GET /api/public/avatars/{person_id}`

| 情形 | 响应 |
|---|---|
| `person_avatar` 有行且 `image` 非空 | `200`，`Content-Type: <mime 或 image/jpeg>`，`Cache-Control: public, max-age=31536000, immutable`，body = 本地副本 JPEG |
| 无该行 / `image` 为空（已注销 / 号查不到 / 未登记） | `404` 空体 |
| `person_id <= 0`（含非正数脏路径） | `404`（不查库） |
| 表不存在（迁移未跑）/ 连接池抖动 / 查询异常 | `404` 空体（**装饰性资源，任何失败都不升级成 500**；错误只留服务端日志） |

> **为什么能 immutable 长缓存**：`?v=<hash>` 是内容版本号，同一个 URL 的响应内容保证不变；
> 换图时前端拿到的是新 URL，不会命中旧缓存。`hash` 为空的历史行退化成不带 `?v=` 的地址，
> 仍能出图，只是失去「换图即破缓存」的保证。

契约文件：`contracts/pk-local/openapi.yaml` → `operationId: publicAvatar`，description 以 `状态：已实现` 开头。

## 9. 失效应对（留存策略）

> **2026-10-16 已收口**：`not_found`（抖音号查不到 / 接口改版返回 `status_code≠0`）**不再清空本地图** ——
> 只记 `note='not_found' + synced_at=now()`，已留存的图原样保留，页面照样有图。
> 至此**唯一**会清空 `image` 的情形只有「账号已注销」（用户口径②）。落地见 `avatar_sync.rs::note_not_found`。

| 失效场景 | 表现 | 应对 |
|---|---|---|
| 抖音接口改字段 / 换域名 | 探测全部落 `not_found`（或请求失败） | **页面仍有本地旧图**（这就是留存的意义）：`not_found` 只记结论不动图，失败更是一个字都不写；确认接口变了再改 `avatar_sync.rs` 常量 + 本文 §4，改完 `--force` 重抓 |
| 抖音接口限流 / 风控 | 单次请求失败 | 走**失败**通道：**不写库**（保留上一次的图），下一轮到 `synced_at` 再试 |
| 某主播号改名 / 号废 | `status_code=5` | 记 `note='not_found'` + 刷新 `synced_at`，**保留原图**，7 天后再试；运营在台账改号后自然修好 |
| 主播抖音号被注销 | `special_state=1` | 记 `note='deregistered'`，**不取图**；这是**唯一**会清空本地图的情形（口径②） |
| 返回的不是图片（HTML/JSON 风控页，或超 64KB） | 魔数 / content-type / 大小校验不过 | 走**失败**通道：不写库、保留旧图 + WARN |
| 本地没有图（从未取到 / 注销清过） | 端点 `404` | `sync-avatars --force` 从抖音重抓（前提是接口还活着）；仍然 404 时前端回落姓名首字色块 |
| 端点依赖的库不可用 / 表未建 | 端点 `404` | 榜单 `avatar` 变 `null`，前端回落姓名首字色块；页面其余部分不受影响，不升级成 500 |

**兜底原则（三条）**：

1. **同步失败绝不写库**：网络 / HTTP 非 2xx / 解析失败 / 非 JPEG / 超限 → 只打 WARN，上一次的图原样留着；
2. **只有「已注销」清图**：`deregistered` 是唯一会清空 `image` 的结论（结论明确、用户口径②）；
   `not_found` 只更新结论与 `synced_at`，**图保留** —— 接口改版导致大面积查不到时，页面照样有图；
3. **端点侧任何异常都退化成 404**：`<img>` 拿不到图 → 前端首字色块，不会白屏、不会 500。

> 结论：**接口失效仍有本地图**（口径③）现在对「请求失败」与「查不到」两种形态都成立；
> 想确认一轮同步会不会动图，先跑 `sync-avatars --dry-run`（只探测打印、不写库）。

## 11. 风险与回滚

| 风险 | 等级 | 说明 / 缓解 |
|---|---|---|
| 抖音页面接口非官方，随时可能失效 | 高 | 已做本地留存（§9）：**请求失败与「号查不到」都不动本地图**（2026-10-16 收口），接口挂了页面仍有图；失效只需改常量后 `--force` 重抓。唯一清图情形是「账号已注销」（口径②） |
| 接口限流 / 封 IP | 中 | 默认 600ms 间隔 + 6 小时检查 + 7 天增量，请求量≈百级/天 |
| `avatar` 里的数字 id 暴露自增主键 | 低 | 展示端本就按 person 渲染、榜单口径已知百人规模；id 只作图片定位键，**不等于**下发内部 id / 抖音号字段。若后续要求彻底隐藏，改随机 token 映射即可（不改本表结构） |
| BYTEA 图随 push 同步到 64 体积与耗时 | 中 | 见 docs/17 §5.1：`person_avatar` 归 A 类本机权威，但**BYTEA 图片列走 COPY 同步尚未在本地沙盘验证**，上线 64 前必须跑一次 db-align 对账 |
| 图片内容变更导致 URL 失效缓存 | 低 | `?v=<hash>` 内容版本号，天然免脏缓存 |

**回滚（只做本地，不动远端）**：

1. **停刷新**：`AVATAR_SYNC_ENABLED=0` 重启（或摘掉定时器接线）—— 已有本地图不受影响；
2. **停下发**：移除 `avatar` 字段 / 头像路由，前端回落姓名色块，无需动库；
3. **退表**：`DROP TABLE person_avatar;`（纯新增表，无 FK 指向它，删除不影响任何既有表；回滚的唯一代价是丢掉已留存的图）；
4. 迁移 `025` 幂等（`CREATE TABLE IF NOT EXISTS`），重放安全。

### 12.1 更新方式改默认手动（口径变更）

| 项 | 一期（原口径） | 二期（2026-10-16 现口径） |
|---|---|---|
| 服务内定时器 | 默认启动（`AVATAR_SYNC_ENABLED` 默认 `1`） | **默认不启动**（默认值改 `0`）；显式设 `AVATAR_SYNC_ENABLED=1` 可重开自动刷新 |
| 手动途径 | 仅 CLI `pk-server sync-avatars` | ① 管理后台「主播管理」页新增的**同步按钮**；② CLI `sync-avatars`（不变，`--force` / `--dry-run` 等参数照旧，见 §7） |

- **管理页同步按钮**调 `POST /api/admin/avatars/sync`，**默认只抓「无图或超 7 天」的人**（即 `image IS NULL` 或 `synced_at` 超过 `AVATAR_SYNC_DAYS`；与定时器的到期判定同口径），不是全量重抓。
- 变更动因：本地测试阶段不需要后台无人值守地定期打抖音接口，改成运营**主动点一下才动**，出错可控、请求可数。
- 7 天新鲜度判定（`synced_at` + `AVATAR_SYNC_DAYS`）本身没变，变的只是「谁来触发探测」。

### 12.2 多抖音号头像来源号口径（用户口径已定，实现待对齐）

- **用户口径（2026-10-16，CSV 核对后运营确认）**：一人挂多个抖音号时，头像取名下**音浪最多**的那个号的头像。
- **当前实现**：仍是 `is_primary` 主号优先的顺序探测（多号按 `is_primary DESC, id` 依次试，**活号优先出图者胜**，见 §3 刷新链路与 §10 表格）——**与用户口径不一致，待对齐**，对齐前后本文如实记录，不写「已实现」。
- 对齐前的实际效果：若主号与「音浪最多号」不是同一个号、且两者头像不同，页面头像按主号出（运营如发现个别头像「用错了号」，先按此解释）。

### 12.3 管理后台「主播管理」页显示头像

- `GET /api/admin/streamers` 的 item 新增两个字段：
  - `hasAvatar`（boolean）：`person_avatar` 有图；
  - `avatarHash`（string，可空）：图片内容 md5 前 16 位（即 `person_avatar.hash`，与公开端点 `?v=` 同源）。
- 前端姓名列显示 **32px 圆形头像**；无图回落**姓名首字色块**，不裂图（与展示端回落规则一致）。
- 取图走**同一个同源端点** `GET /api/public/avatars/{personId}?v={hash}`，管理端不再另开图片接口。
  该端点**没有管理权限校验**（头像本是抖音公开资料，与展示端同权），管理页复用它只是省一份拷贝。

### 12.4 HTTP 客户端防挂死参数（二期新增）

抖音探测的 HTTP client 补了三个超时/池参数（背景：本机代理曾致**连接池挂死 40 分钟**，服务表面活着、同步卡死）：

| 参数 | 值 | 作用 |
|---|---|---|
| `connect_timeout` | 10s | 建连挂住 10 秒必返回，不再无限等 |
| `pool_idle_timeout` | 30s | 空闲连接 30 秒后回收，避免代理半死连接常驻池内 |
| `pool_max_idle_per_host` | 2 | 每主机最多留 2 条空闲连接，池子小了挂死面也小 |

> 同步器本体（探测流程、落库规则、失效应对 §9）不受影响；这两个超时只保证「卡了会自己断」，不保证「断了能成功」。
