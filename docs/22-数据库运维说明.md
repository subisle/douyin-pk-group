# 22 · 数据库运维说明：属主、迁移 runner 与暂存区清理

> 2026-10-14 审计新增。本文是数据库层的**操作手册**：谁必须拥有表、`pk-server migrate`
> 怎么跑、报「must be owner」怎么处置、import_pending 怎么按保留期清理。
> 背景设计见 docs/17-数据库对齐与64部署方案.md；权限模型见 docs/16-数据库资产总览.md。

## 1. 谁必须拥有表（owner）

| 角色 | 用途 | 对表的要求 |
|---|---|---|
| `zmy`（或部署时指定的属主角色） | 建库 / 灌库（pg_restore） | **表的属主**。本机 douyin_dev 实查：27/27 张表属主都是 zmy |
| `pk_writer` | 服务写库 + `pk-server migrate`（DDL） | 理想状态 = 属主；至少要对全部表有 SELECT/INSERT/UPDATE/DELETE |
| `pk_reader` / `pk_backup` | 只读 / 备份 | 只读即可，**绝不给 DDL 权** |

**规则：跑 `pk-server migrate` 的账号必须是全部表的属主（或先把属主移交给它）。**
PG 的 `CREATE INDEX / ALTER TABLE` 一类 DDL 要求执行者是表属主，授权（GRANT ALL）不替代属主。

### 查当前属主

```sql
-- 全部表按属主汇总
SELECT tableowner, count(*) FROM pg_tables WHERE schemaname = 'public' GROUP BY tableowner;

-- 列出不是 pk_writer 属主的表（migrate 前先跑这句）
SELECT tablename, tableowner FROM pg_tables
 WHERE schemaname = 'public' AND tableowner <> 'pk_writer';
```

期望结果：**0 行**。只要这里查出表来，migrate 迟早会在某条 DDL 上失败。

### 实踩案例（2026-10-14）

本机 douyin_dev 表属主全是 `zmy`，而 `rust/.env` 的 `DB_WRITER_USER=pk_writer` →
migration 019 的 `CREATE INDEX` 直接报 `must be owner of table monthly_metric`，
019/020/021 只有换成 zmy 才跑成。这种失败**不会自愈**：schema_migrations 里该版本
没登记，重跑还是同一个错。

migrate.rs 现在会识别这类报错（`must be owner of` / `permission denied for table|relation` /
`must have create privilege on schema` / `must be superuser` / `permission denied to change owner`），
失败时点名账号、表名并给出处置语句；识别不了对象名时**不猜**，提示看完整报错。

## 2. `pk-server migrate` runbook

```bash
# 本机（迁移账号来自 rust/.env 的 DB_WRITER_*）
cd rust && cargo run --release -- migrate

# 生产（64 容器内）
docker exec pk-server /usr/local/bin/pk-server migrate
```

1. **先查属主**（上面 §1 的 SQL），发现非 `pk_writer` 属主的表 → 先做 §3 的移交。
2. 跑 migrate；成功标志是日志里逐条 `迁移已应用`（版本号）。
3. **失败时看错误文案**：带【属主权限不足】段落的，按段落里的两条路处置其一，重跑；
   其它错误按文案里的语句定位（`语句: …` 会带上出错 SQL）。
4. 迁移是幂等的：`schema_migrations` 只登记应用过的版本，重复执行只补缺。

### 迁移脚本红线（不改 runner 前提下）

- 新 schema 变更 = 新增 `0XX_*.sql` 并在 migrate.rs 的 `MIGRATIONS` 登记（有测试防漏登记）；
- 禁止手改库 schema、禁止在 migrate 里夹带数据回填（`SELECT 1` 占位的历史版本照旧保留）；
- 索引名全局唯一（schema 内）——001 里两次 `uk_anchor_date` / `uk_person_period` 撞名
  的教训见 migrations/019/020/021，命名一律带表前缀。

## 3. 属主移交（处置办法，人工执行）

代码**不会**自动改属主（改属主是高危操作，必须人确认后手工跑）。二选一：

```sql
-- A) 全库一次到位（推荐）：scripts/deploy/bootstrap-roles-64.sql §5 会把
--    public 下全部表/序列/函数的属主移交给 pk_writer，并补默认 ACL（幂等，可重跑）。
--    本机：把 scripts/db-align/local.env 里的 DST_* 指向 douyin_dev 后跑
--    scripts/deploy/bootstrap-roles-64.sh；生产 64 同脚本。
--
-- B) 只补当前挡路的表（临时救急）：
ALTER TABLE monthly_metric OWNER TO pk_writer;   -- 由**当前属主**或 superuser 执行
-- 生产 64 容器内示例：
-- docker exec -it <pg容器> psql -U zmy -d douyin -c "ALTER TABLE monthly_metric OWNER TO pk_writer;"
```

移交后重跑 migrate，并再跑一次 §1 的检查 SQL 确认 0 行。

## 4. import_pending 暂存区按保留期清理

### 背景

导入时「有抖音号 / 采集 ID 但没匹配上台账」的行落 `import_pending`（暂存），
解绑抖音号时也会往这里留档一笔。前台暂存 UI 已移除，**但写入没有停**：没人清理就单边增长。
本机实查（2026-10-14）：181 行，全部未认领。

### 清理入口（手动，不挂任何自动任务）

```
DELETE /api/admin/import/pending?pruneDays=N
```

| 参数 | 行为 |
|---|---|
| `?pruneDays=N` | 删除 `absorbed_at IS NULL AND created_at < now() - N 天` 的行，返回 `{"ok":true,"deleted":N}` |
| `?id=<行id>` | 丢弃单行（原行为，未变） |
| `?douyinNo=x` | 丢弃该号全部未认领行（原行为，未变） |

约束与安全口径（实现在 `store/import_pending.rs`，端点在 admin.rs `import_pending_delete`）：

- **永不删已认领行**：`absorbed_at IS NULL` 是硬条件，补账/解绑留档不会被清；
- `pruneDays` 必须 > 0（`≤0` 一律 400，防手滑清全表）；与 `id` / `douyinNo` 互斥；
- 天数走**绑定参数**（`make_interval(days => $1)`，int4），SQL 无字符串拼接；
- 删除条数写日志（`已清理过期导入暂存行`），失败记 error 返回 0，不 panic。

### 建议保留期

- 常规运维：`pruneDays=30`（一个月内的行还可能等建档后补账）；
- 库存清理首次执行：先 `pruneDays=7` 试水，看 `deleted` 数与业务确认无异议再放大。

```bash
# 调用示例（管理端鉴权同其它 /api/admin 接口）
curl -X DELETE 'http://127.0.0.1:8080/api/admin/import/pending?pruneDays=30'
```

### 盘点 SQL（只读，随时可跑）

```sql
SELECT count(*) FILTER (WHERE absorbed_at IS NULL)                          AS 未认领,
       count(*) FILTER (WHERE absorbed_at IS NULL
                          AND created_at < now() - interval '30 days')       AS 超过30天未认领,
       min(created_at) FILTER (WHERE absorbed_at IS NULL)                    AS 最早未认领
  FROM import_pending;
```

## 5. schema 类型对照（审计结论，2026-10-14）

对 migrations/001..021 与 store/*.rs 全部 `try_get` 读点做了逐列核对（依据本机
douyin_dev 实查的 information_schema）：

- **结论：无代码侧类型漂移遗留。** 上一轮已修的两处（my_bind_requests 时间列改
  chrono 读、wx_sessions 多写的 updated_at 列）已确认修对；
- 两处疑似漂移实为 PG 语义（非 bug，已核实）：`SELECT COUNT(*)/LENGTH(...)` 返回
  int8，代码用 `i64` 读——正确；`CHAR(7)/CHAR(1)`（bpchar）去尾空格后按 `String` 读——正确；
- 剩余风险不在 Rust 读侧，而在**错误文案匹配**：`store/my_account.rs` 仍在匹配 MySQL
  文案（`Duplicate entry` / `Unknown column`），PG 下永不命中，中文提示退化成裸英文
  （docs/21 P2 已记录，本轮不改行为，只在此归档）；
- 约束名唯一性教训（001 内 `uk_anchor_date`/`uk_person_period`/`idx_person` 撞名 →
  019/020/021 补建）已由 migrate.rs 的登记完整性 + 编号连续性测试防回归。
