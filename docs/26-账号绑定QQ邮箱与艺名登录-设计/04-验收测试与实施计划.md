## 1. 验收标准

### 1.1 角色定义（5 类）

| 角色 | 判定条件（`my_accounts`） | 本机现状 | 造数方式 |
| --- | --- | --- | --- |
| **R1 未绑手机号主播（S1）** | `bound=1 AND is_admin=0 AND phone='' AND email=''`；账号名 = 主播艺名（`person.name`） | 当前 0 行（实测 `phone='' and is_admin=0` = 0） | 管理端 `POST /api/admin/my-accounts`，`phone` 留空即可——`my_accounts.bound` 默认 1（`001_core.sql:216`），建号后天然是 S1；响应里 `password` 为随机串（`initial_password("")` 回落 `random_password()`，见 `store/my_account.rs:549-558`） |
| **R2 已绑手机号未绑 QQ（S2）** | `is_admin=0 AND phone<>'' AND (email='' OR email NOT LIKE '%@qq.com')`；`qq_bound` 按文档② = email 非空且以 `@qq.com` 结尾 | email 全空，已有 64 个普通手机号账号可直接用 | 已有账号；或管理端新建带 phone 的账号 |
| **R3 已绑 QQ（S3）** | `is_admin=0 AND phone<>'' AND email LIKE '%@qq.com'` | 0 行 | R2 账号登录后调 `POST /api/public/my/email {"qq":...}` 写入 |
| **R4 管理员（B2）** | `is_admin=1`，或 `/api/public/my/login` 的「账号=密码=ADMIN_PASSWORD」快捷口令（`public_teams/my.rs:227-250`） | 4 个管理员 | 内置账号（`BUILTIN_MY_ACCOUNTS`，`rust/.env`）；或快捷口令 |
| **R5 无账号访客** | `my_accounts` 查不到该姓名/手机号 | — | 不造数；用随机姓名/手机号 |

> 旁支 **B1（`bound=0`，未绑主播）** 不在本文件的 5 个主角色内：文档②规定它继续走 `needBind`（联系管理员绑主播），不进入 `profile/bind` 引导。若测试中出现 `bound=0`，应看到 `needBind:true` 而不是 `needProfile:true`——这是 E2E-01 的前置校验项。
> 说明：「没绑定账号的支持艺名登录」在本文件按文档②解释为 S1「账号存在、`phone=''`、用艺名+密码登录」；「主播完全没有 `my_accounts` 行」没有密码可校验，不成立。若用户另有所指，见 §7-Q1。

### 1.3 契约基线（已对齐文档② §8；完整定义以②为准）

| 接口 | 入参 | 本文件断言的成功响应 | 主要失败 |
| --- | --- | --- | --- |
| `POST /api/public/my/login`（`my.rs:156`） | `{account, pass}`（兼容 `name`） | `{ok:true, personId, name, team, token, bound, needBind, needProfile, needQq, mustChangePass, phone(打码), emailMask, switchable}` | 200 `{ok:false, code:"BAD_PASSWORD"|"NO_ACCOUNT", error:"密码错误"|"账号还没开通"}`；400 `INVALID_INPUT`；403 地区 |

错误码与文案（验收按字面量断言；文档② §5.6/§4.2/§3.2）：

| code | HTTP | 文案 |
| --- | --- | --- |
| `INVALID_PHONE` | 400 | 手机号格式不对：应为 5~20 位数字 |
| `RESET_MISMATCH` | 400 | 手机号与 QQ 号不匹配，或该账号未绑定 QQ 邮箱 |
| `INVALID_QQ` | 400 | QQ 号格式不对：应为 5~12 位数字且不以 0 开头（`/my/email` 旧 email 入参非 QQ 域时：只支持 QQ 邮箱，请填写 QQ 号） |
| `QQ_TAKEN` | 400 | 该 QQ 邮箱已被其他账号绑定 |
| `PHONE_TAKEN` | 400 | 该手机号已被其他账号绑定，请联系管理员 |
| `PROFILE_ALREADY_DONE` | 400 | 该账号已完成绑定，如需修改手机号请联系管理员 |
| `INVALID_PASS` | 400 | 密码必须是 4~20 位字母、数字或点 |
| `SMTP_UNAVAILABLE` | 503 | 邮件服务暂时不可用，请稍后重试或联系管理员 |
| `NEED_PROFILE` | 403 | 请先完成手机号绑定 |
| `MUST_CHANGE_PASS` | 403 | 请先修改临时密码 |
| `TEMP_EXPIRED` | 200 | 临时密码已过期，请重新获取（登录响应 `{ok:false,code:"TEMP_EXPIRED"}`） |
| `RATE_LIMITED` | 429 | 尝试太频繁，请稍后再试 |

> 断言建议用「HTTP 状态 + code + 关键字段 + 行为」，不要断言整包 JSON；后续①②若有微调，只改这张映射表。
> **有效期默认按 15 分钟写断言**；若 §7.0-D1 裁决为 30 分钟，按 D1 的「需同步改」列表一次性替换，不要只改一处。

### 2.5 异常与限流

| 编号 | 场景 | 期望 | 备注 |
| --- | --- | --- | --- |
| LIM-01 | 单 IP 12 次/分 | 第 13 次 `429 {code:"RATE_LIMITED"}`；窗口滑过恢复 | 现有 `PASSWORD_RESET_LIMITER::new(12)`（`my.rs:392-395`） |

| LIM-03 | 同手机号 1 小时 3 次 | 第 4 次被抑制（同上） | 现有 `RESET_GUARD_MAX_PER_HOUR=3`（`my.rs:416`） |
| LIM-04 | 并发同 phone+qq | 只 1 封邮件、1 份有效临时密码；其余同形成功；无 500 | **现实现的 check→发信→record 有竞态**（`my.rs:583-591` 与 `:630-633` 之间隔着 SMTP await，5 并发可能都通过）；实现时改成「先原子占坑，失败回滚」，并把抑制回包与成功统一（现 `{ok,names}` vs `{ok,sent}` 不同形） |
| LIM-05 | 并发改密/临时密码消费 | 同一临时密码只成功一次；改密后旧 token 立即失效 | 用条件 UPDATE（`WHERE name=? AND temp_pass_hash=? AND temp_pass_exp>now()`）原子消费，禁止先查后改；改密成功清三列 |
| LIM-06 | 进程重启 | 限流窗口内存清零（可接受）；已发临时密码仍有效（落库） | 在验收记录里写明，不当作 bug |
| LIM-07 | 时钟/时区 | 过期判定用同一时钟源；跨时区差异不影响 | `temp_pass_exp` 用 DB `CURRENT_TIMESTAMP` 或统一 UTC |
| LIM-08 | S1/强制改密态写接口 | `needProfile` 或 `must_change_pass=1` 时，非白名单写接口一律 403（`NEED_PROFILE` / `MUST_CHANGE_PASS`）；`who`/`profile/bind`/`password`/登出放行 | 文档② §6.4；读接口不拦 |

### 5.2 回滚

**顺序：先停写/回代码 → 再回 DB；不要先删列。**

1. **前端降级（最快，1 分钟）**：隐藏「忘记密码」入口、关闭强制引导与弹窗（前端开关/注释回退），保留密码登录 + 管理员后台改密。

3. **代码回滚**：`git revert` 本特性的提交（T1/T2 后端、T3/T4 前端），重新 `cargo build` 并重启 `pk-server`。
4. **DB 回滚 039**（仅在代码已回滚后执行）：

```sql
-- 先确认没有用户正持有未消费的临时密码（只读留证）
SELECT COUNT(*) FROM my_accounts
 WHERE temp_pass_hash <> '' OR must_change_pass = 1;

-- 回滚 039 三列
ALTER TABLE my_accounts
  DROP COLUMN IF EXISTS temp_pass_hash,
  DROP COLUMN IF EXISTS temp_pass_exp,
  DROP COLUMN IF EXISTS must_change_pass;

-- 让迁移可重跑（否则 schema_migrations 会让 039 被跳过）
DELETE FROM schema_migrations WHERE version = '039_my_temp_pass';  -- 以文档①终稿文件名为准
```

> 038（email）**不要跟着回滚**：它已经被「我的」页邮箱入口使用；若确需连 038 一起撤：
> `ALTER TABLE my_accounts DROP COLUMN IF EXISTS email;`
> `DELETE FROM schema_migrations WHERE version='038_my_account_email';`
> 这会丢掉全部已绑邮箱（本机当前 email 全空，风险为零，但仍不推荐）。
> 本机无 pg 客户端时，用 §3.3 的 psycopg 连接（**写操作需换 `pk_writer` 账号**）执行；属主 `zmy` 才能 DDL，回滚同样用 `DB_MIGRATOR_USER=zmy`。
> 若后续 040 建了邮箱唯一索引：先 `DROP INDEX IF EXISTS uk_my_email_uniq;` 再删 040 的 `schema_migrations` 行；本轮 039 不涉及。
> 若 D2 最终裁决为「重置即覆盖 pass」，则回滚代码不会恢复被覆盖的旧密码：回滚前先列出 `temp_pass_hash <> '' OR must_change_pass=1` 的账号，回滚后逐个用管理员「我的页面账号」重设密码——这是 A2 方案的额外运维成本（也是本文件默认选 A1 的原因之一）。

5. **数据面**：本机 `my_accounts` 只有 68 行且 email 全空，最坏情况按 `name` 重建账号；不依赖备份文件（AGENTS §2）。
