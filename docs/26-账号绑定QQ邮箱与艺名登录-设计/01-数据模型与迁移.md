# 01 · 数据模型与迁移：绑定 QQ 邮箱 / 艺名登录 / 临时密码

> **文档编号**：docs/26 设计文档①（数据模型与迁移）
> **作者**：子代理 `doc-data-model`（设计文档组）
> **日期**：2026-10-17
> **状态**：设计稿，待用户确认 §7 的问题后冻结
> **范围**：只讨论数据模型、迁移 039、影响面与执行验证。接口/UI 细节见同目录其它子文档（本文件不代替它们）。
> **用户口径原文**（本次唯一需求来源）：
> 「本地进行开发，账号支持绑定邮箱，填写qq号码即可，发送到对应的qq邮箱。自动添加后缀。如果没绑定账号的，支持艺名登录，如果没绑定手机号，提示用户绑定QQ号码和手机号码然后设置密码。已经绑定的用户弹窗提示绑定QQ号码。忘记密码就是重设密码需要输入手机号进行和输入qq邮箱，然后发送临时密码到他的邮箱。」

**设计基线（不可擅改，本文档在基线上展开）**

1. 绑定邮箱 = 绑定 QQ 邮箱：用户只填 QQ 号（数字），服务端自动补 `@qq.com`，落库存完整地址。
2. 复用 `my_accounts.email`（038 迁移已有，`rust/crates/pk-server/src/migrations/038_my_account_email.sql:13`）存 `<qq>@qq.com`，**不新增 qq 列**；新增迁移 039 只加临时密码相关列。
3. 艺名登录：账号名 `name` 即台账 `person.name`（生产里就是艺名）；未绑手机号账号凭艺名 + 密码可登录。
4. 忘记密码 = 手机号 + QQ 号双知识因子 → 生成临时密码（CSPRNG、有时效、单次、登录后强制改密）。
5. 数据库是 PostgreSQL（本机 `127.0.0.1:3318/douyin_dev`，属主 `zmy`），迁移语法一律 PG；**不要沿用 docs/13 里过时的 MariaDB 写法**（例如 docs/13 §7.4 的回滚示例 `ALTER TABLE person DROP INDEX ...` 是 MariaDB 写法，PG 不成立）。
6. 只做本地开发：不推远端、不做数据库备份（遵守根 `AGENTS.md` 第 1/2 条）。

## 2. QQ 号存储决策

### 2.1 方案 A（复用 `email` 列）vs 方案 B（新增 `qq` 列）

| 维度 | A：`email = '<qq>@qq.com'`（推荐） | B：新增 `qq VARCHAR(12)` |
|---|---|---|
| 事实源 | 单一：邮箱地址就是可发信目标 | 双事实源：`qq` 与 `email` 可能不一致，必须定主从 |
| 唯一性 | 直接对 `email` 建 partial unique index 即可 | 要么对 `qq` 建、要么对拼出的邮箱建（PG 表达式索引），两套口径 |
| 脱敏/展示 | `mask_email`（`public_teams/wx.rs:239-253`）现成：`1***@qq.com` | 需要新写 `mask_qq`，且下发时还要拼后缀 |
| 解绑 | `email=''`，partial index 自动排除 | `qq=''`，email 要不要跟着清？易留脏 |
| 存量兼容 | 038 已进本地 `schema_migrations`（实测 038 已应用；代码仍是未提交 WIP）；存量非 QQ 地址原样可读 | 038 的 `email` 仍会被别处写入（WIP 已有写入口），必须处理双列冲突 |
| 查询 | `WHERE email = '<qq>@qq.com'` 或 `split_part`；加索引后等值查很快 | `WHERE qq = ?` 快，但对应邮箱仍要拼 |
| 迁移成本 | **0 列迁移**（039 只加临时密码列） | 加列 + 回填（从 email 反解）+ 清理歧义行 + 双写风险 |
| 邮件发送 | `mailer::send_mail(&email, ...)`（`src/mailer.rs:125`）直接可用 | 发送前仍要拼邮箱，多一处可错点 |
| 审计日志 | 直接对完整地址 `mask_email` | 日志里出现 QQ 号，也要单独脱敏 |
| 与用户口径贴合 | 用户说的「绑定邮箱」本身就是邮箱地址，QQ 号只是输入形态 | 语义上更「原生」，但没有额外收益 |

**结论：采用方案 A。** 不新增 `qq` 列、不新增生成列。唯一代价是「列名是 email，但本轮业务上只允许 QQ 邮箱」——用文档不变量（§2.2）和展示层 `emailKind` 弥补，而不是靠加列解决。

方案 B 唯一值得保留的场景是「将来还要支持 163/企业邮箱」：那时 `email` 列照样能存，`qq` 列反而多余。所以 B 连未来兼容性都不占优。

### 2.2 存储不变量（实现与后续迁移都必须守住）

1. `email = ''` ⇔ 未绑定。
2. 非空时**优先**满足 `^[1-9][0-9]{4,11}@qq\.com$`（本轮新写入只允许这一种形态；长度上限见 Q1）。
3. 历史值允许为非 QQ 邮箱（038 WIP 早期可能写入过任意邮箱）；**不因历史值非法而阻断登录/展示**，只在重置路径明确提示重绑（§2.5）。
4. 一账号一绑定：`email` 是账号行的一部分，随账号改名、改绑主播而保留（改名只动 `name`，`admin.rs:791-830`）。
5. 任何对外展示/日志都不得输出完整邮箱（展示端）；管理端是否明文见 Q7/§4。
6. 临时密码邮件**只发往库里存的 `email`**，绝不发往请求里原样传入的字符串（防头注入与「输入 A、发到 B」）。

### 2.3 QQ 号校验规则与归一化函数

输入规则（服务端为准，前端只做提示）：

- 去首尾空白；**去掉内部所有空白**（含全角空格）；不做「去横线」——横线不是 QQ 号的一部分，遇到直接判非法。
- 必须是 **ASCII 数字**：`[0-9]`。全角数字（`１２３`）建议**拒绝**而不是自动转换（避免用户看不出服务端改过什么；如产品希望宽容，可在 Q1 一并确认）。
- 长度 **5~12 位**（本次任务口径）。腾讯对 QQ 号长度的公开稳定规范**待核实**；现行常见 5~11 位，取 12 作冗余，落实为一个常量，将来只改一处。
- **首位不能是 `0`**（QQ 号没有前导 0；`012345` 视为输错，而不是「补零后的 12345」）。
- 其它字符（`+`、`-`、`.`、`@`、字母、中文）一律拒绝；错误文案走 `BIZ::` 前缀（`store/my_account.rs:61-79` 的约定），由路由层 400 原样下发。
- 允许「粘贴完整 QQ 邮箱」作为兼容输入：`123456@qq.com` → 剥掉大小写不敏感的 `@qq.com` 后缀再校验（建议实现，见 Q1；不做也不影响主流程）。

建议函数放在 `store/my_account.rs` 紧邻 `validate_email`（:158）处，签名如下（仅设计，不是已实现代码）：

```rust
/// QQ 邮箱域名（唯一允许值，小写）。
pub const QQ_MAIL_DOMAIN: &str = "@qq.com";

/// QQ 号归一化 + 校验：去空白 → 5~12 位 ASCII 数字、首位 1~9。
/// Ok 返回纯数字串；Err 带 BIZ:: 前缀（面向用户文案）。
/// 例：" 123456 " → Ok("123456")；"012345" / "12345a" / "" → Err。
pub fn normalize_qq(raw: &str) -> std::result::Result<String, String>;

/// QQ 号 → 完整邮箱（调用 normalize_qq 后补后缀，永不产生空串邮箱）。
/// 例："123456" → Ok("123456@qq.com")。
pub fn qq_to_email(qq: &str) -> std::result::Result<String, String>;

/// 完整邮箱 → QQ 号反解：只认 `<5~12位数字>@qq.com`（域名大小写不敏感）。
/// 非 QQ 邮箱（如 xx@163.com、123@vip.qq.com）→ None；不做「猜测式」解析。
pub fn qq_from_email(email: &str) -> Option<String>;
```

### 2.4 邮箱唯一性：要不要加 partial unique index？

**建议加，但单独放 040，不进 039**（039 基线限定「只加临时密码相关列」）。

| | 加 `UNIQUE (email) WHERE email <> ''` | 不加，仅应用层查重 |
|---|---|---|
| 防重复绑定 | 数据库硬保证，并发下也不会出现两个账号同邮箱 | 依赖「先查后写」，并发可被穿透 |
| 用户文案 | 捕获 SQLSTATE `23505` 映射成「该 QQ 号已绑定其他账号」（参考 `bind_update_err` 的既有范式，`store/my_account.rs:68-76`） | 需要自己组织查重 SQL |
| 查询性能 | 按邮箱等值查走索引（本地 68 行无所谓，量大后有用） | 全表扫 |
| 业务弹性 | **同一 QQ 不能绑两个账号**（如「一人两号/经纪代管多个主播」会被挡） | 允许复用，靠产品约束 |
| 存量数据 | 加之前必须查重，否则 `CREATE UNIQUE INDEX` 直接失败 | 无风险 |
| 回滚 | `DROP INDEX IF EXISTS uk_my_email_uniq;` + 删 040 登记行 | 无 |

本地实测 `email<>''` 为 0 行，**现在加索引零风险**；但「同一 QQ 是否允许绑多个账号」是产品问题（Q2）。因此文档给出的顺序是：

1. 若 Q2 = 不允许复用 → 040 执行：
   ```sql
   -- 040_my_email_unique.sql（建议编号/文件名，非本文件交付物）
   CREATE UNIQUE INDEX IF NOT EXISTS uk_my_email_uniq
     ON my_accounts (email) WHERE email <> '';
   ```
   执行前查重（结果必须 0 行）：
   ```sql
   SELECT email, count(*) FROM my_accounts
    WHERE email <> '' GROUP BY email HAVING count(*) > 1;
   ```
2. 若 Q2 = 允许复用 → 不建索引，仅在 `my_account_set_qq` 做「查重 + 明确文案」，并把「一个 QQ 可能对应多个账号」写进文档②的接口说明；忘记密码仍靠**手机号 × QQ** 双因子锁定单账号（复用本身不扩大攻击面）。

> 注意：即使加唯一索引，也**不改变**忘记密码的定位逻辑——仍然先用手机号定位到唯一账号，再比对 QQ。唯一索引只解决「绑定阶段防手误/防重复」，不是重置链路的安全前提。

### 2.5 存量非 QQ 邮箱的兼容与提示重绑

038 之后可能有 `xx@163.com` 这类历史值（本地 0 条；远端是否已产生**待核实**）。处置原则：**不清洗、不自动改、不猜 QQ**（把 `cszimy@163.com` 的本地部分当 QQ 号是错误映射，会发到错误的人手里）。

三种状态的判定（直接可执行）：

```sql
SELECT
  count(*) FILTER (WHERE email = '')                                AS unbound,
  count(*) FILTER (WHERE email ~ '^[1-9][0-9]{4,11}@qq\.com$')      AS qq_bound,
  count(*) FILTER (WHERE email <> ''
                     AND email !~ '^[1-9][0-9]{4,11}@qq\.com$')     AS non_qq_legacy
FROM my_accounts;
```

| 状态 | 展示端「我的」页 | 忘记密码（手机号 + QQ） | 建议动作 |
|---|---|---|---|
| `email=''` | 显示「未绑定」；登录后弹窗引导绑定 QQ | 400「该账号未绑定 QQ 邮箱，请先在『我的』页绑定」 | 用户自助绑定（已登录） |
| 合法 QQ 邮箱 | 显示脱敏后地址；可改绑/解绑 | 正常：手机号 + QQ 匹配 → 发临时密码 | — |
| 非 QQ 历史邮箱 | 显示「已绑定非 QQ 邮箱」（可给原地址脱敏预览） | **不发送**；400「当前绑定的是非 QQ 邮箱，请先重绑 QQ 号」 | 用户自助重绑；管理员不代发 |

实现细节：

- 「是否合法 QQ 邮箱」由 `qq_from_email` 判定，**不写回数据库**、不加派生列；`who` 可下发 `emailKind: "none"|"qq"|"other"` 或 `emailBound: bool`（见 §4）。
- 重绑即 `UPDATE my_accounts SET email='<qq>@qq.com'`，覆盖旧值；旧值不留历史（审计日志里记一次脱敏的前后值即可，见 §4 审计项）。
- 若决定「允许非 QQ 历史邮箱继续收临时密码」（产品可能想兼容老用户），则重置链路要放宽到 `email 匹配输入`：输入是 QQ 号就只能匹配 QQ；输入完整邮箱则匹配完整邮箱——但这与「只填 QQ 号」口径冲突，**不推荐**（Q6）。

### 3.1 迁移 runner 的硬约束（写 039 之前必须知道）

迁移登记与执行逻辑在 `rust/crates/pk-server/src/migrate.rs`：

- 编译期数组 `MIGRATIONS`（:13 起）按 `(version, sql)` 登记，执行时按数组顺序（:357），只跑 `schema_migrations` 里没有的版本（:357-380）。**新增文件必须登记**，否则永远不执行：`every_migration_file_is_registered` 测试会失败（`migrate.rs:506-538`）。

- `embedded_migrations_split_cleanly` 测试要求每条语句的首关键字是 `CREATE` / `ALTER` / `INSERT` / `UPDATE` / `DROP TRIGGER` / `SELECT`（`migrate.rs:400-418`）。因此 039 **不能用 `COMMENT ON COLUMN ...`**（首关键字是 `COMMENT`，测试会红），列语义只能写在 `--` 注释里。

```sql
ALTER TABLE my_accounts ADD COLUMN IF NOT EXISTS temp_pass_exp TIMESTAMPTZ;
ALTER TABLE my_accounts ADD COLUMN IF NOT EXISTS must_change_pass SMALLINT NOT NULL DEFAULT 0;
```

### 3.3 字段语义与读写归属

| 字段 | 何时写 | 谁读 | 何时清/改 |
|---|---|---|---|
| `temp_pass_hash` | 重置申请（邮件发送成功后）写入 `argon2id(临时密码)`；再次申请覆盖旧值 | 登录校验（`my_account_check_login`）、运维排查（只看是否为空） | 临时密码被成功使用（CAS 消费）→ 清空；解绑 QQ → 清空；管理员重设密码/批量开号重置 → 清空；账号删除随行删除 |
| `temp_pass_exp` | 与 `temp_pass_hash` 同一条 UPDATE 写入 `now() + interval '30 minutes'` | 登录校验（`temp_pass_exp > now()`）；过期清理 | 同上；过期后惰性清理 |
| `must_change_pass` | 下发临时密码时置 1；消费临时密码时保持 1；管理员强制重置也可置 1（本轮不新增入口） | 登录响应、`who`、受限 token 判定 | 用户改密成功后置 0；管理员 `my_account_set` / 批量 `force_reset` 覆盖密码后置 0 |

`pass` 列语义不变：仍是「登录密码哈希」。但**重置时会被覆盖为不可知 CSPRNG 的哈希**（§3.7），所以「`pass` 为空 = 未登记密码」的既有判断（`store/my_account.rs:1430`）不受影响。

### 3.4 账号密码状态机

```
                    （管理员设密码 / 用户自助改密）
        ┌────────────────────────────────────────────┐
        ▼                                            │
  S0 正常 ──忘记密码申请(手机号+QQ匹配)──▶ S1 待使用临时密码
        ▲                                     │  temp_pass_hash!=''  且 exp>now()
        │                                     │  must_change_pass=1，pass=不可知哈希
        │                                     │
        │                               登录命中临时密码（CAS 消费）
        │                                     ▼
        └──────────── 用户改密成功 ──── S2 已消费待改密
                                              temp_pass_hash='' / exp=NULL
                                              must_change_pass=1（受限 token）

  S1 超过 temp_pass_exp ──▶ S3 已过期：temp_pass_hash 置空（pass 仍是不可知哈希，
                                       用户只能重新走忘记密码）
```

关键点：

- S1/S2 期间**旧密码都不可用**（`pass` 已被覆盖为不可知哈希），这是「重置」的应有语义。
- S2 若用户丢失登录态（清缓存/换设备），因为临时密码已被消费，只能重新申请（本轮设计的代价，见 Q4）。
- 管理员随时可以打断：`my_account_set` 直接改密码 → 回到 S0（实现上必须顺手清 `temp_pass_*` 与 `must_change_pass`，否则会出现「密码已换但仍被要求改密」的假锁）。

### 3.5 生命周期 SQL（业务侧用 `?` 占位，经 `crate::pq::rewrite` 转 PG，见 `src/pq.rs:22`）

**(1) 下发临时密码**（邮件发送成功之后才执行；失败不改库）：

```sql
-- 入参：?1 = argon2id(不可知随机串)  ?2 = argon2id(临时密码)  ?3 = 账号名
UPDATE my_accounts
   SET pass            = ?,
       temp_pass_hash  = ?,
       temp_pass_exp   = now() + interval '30 minutes',
       must_change_pass = 1
 WHERE name = ? AND is_admin = 0;
```

> 为什么同时覆盖 `pass`：不覆盖的话，知道旧密码的人仍能登录，重置等于没做。覆盖值由 `crate::random::random_password()`（`src/random.rs:42`，getrandom CSPRNG）生成后立刻哈希，明文**生成即丢**，谁也不知道。

**(2) 登录命中临时密码 → 单次消费（CAS）**：

```sql
-- ?1 = 账号名，?2 = 读到的 temp_pass_hash 原值（用于 CAS）
UPDATE my_accounts
   SET temp_pass_hash = '',
       temp_pass_exp  = NULL,
       must_change_pass = 1
 WHERE name = ?
   AND temp_pass_hash = ?
   AND temp_pass_exp IS NOT NULL
   AND temp_pass_exp > now();
-- rows_affected == 1 才算消费成功；==0 说明并发被抢/已过期 → 按「临时密码不可用」处理
```

`temp_pass_hash = ?` 这一条是必要的：两个并发登录请求都可能通过 argon2 校验，但只有第一个 UPDATE 能命中旧哈希值，从而保证**单次**语义（不会发出两个有效会话）。

**(3) 过期惰性清理**（登录时发现 `exp <= now()` 或运维巡检时执行）：

```sql
UPDATE my_accounts
   SET temp_pass_hash = '', temp_pass_exp = NULL
 WHERE name = ?
   AND temp_pass_hash <> ''
   AND temp_pass_exp IS NOT NULL
   AND temp_pass_exp <= now();
```

**(4) 改密成功（强制改密走同一实现）→ 解除锁定**：

```sql
UPDATE my_accounts
   SET pass = ?,                          -- argon2id(新密码)
       temp_pass_hash = '',
       temp_pass_exp = NULL,
       must_change_pass = 0
 WHERE name = ?;
```

对应 `self_set_password_inner`（`store/my_account.rs:1406-1465`）末尾的 UPDATE（现状 :1458-1466），由它统一收口，避免两条改密路径各写一套。

**(5) 解绑 QQ / 管理员重设密码时的清理**：

```sql
-- 解绑（email=''）时顺带作废未使用的临时密码；must_change_pass 保留
UPDATE my_accounts
   SET email = '', temp_pass_hash = '', temp_pass_exp = NULL
 WHERE name = ?;

-- 管理员设密码 / 批量开号 force_reset 时
UPDATE my_accounts
   SET pass = ?, temp_pass_hash = '', temp_pass_exp = NULL, must_change_pass = 0
 WHERE name = ?;
```

### 3.6 索引评估

**不建索引**，理由：

1. 登录校验先按 `name`（主键）或 `phone`（`uk_my_phone_uniq`）定位，临时字段只作为该行内的附加列读取，没有「按临时字段过滤」的常规查询。
2. 清理/巡检是低频全表扫描，68 行量级（未来到几百行也毫秒级）；PG 对小表本来就会走 seq scan，索引反而多一份写放大（每次重置/消费都更新该列）。
3. 若将来接入定时清理任务且表显著变大，再单开迁移：
   ```sql
   -- 仅备选，不在 039 中执行
   CREATE INDEX IF NOT EXISTS idx_my_temp_exp
     ON my_accounts (temp_pass_exp) WHERE temp_pass_hash <> '';
   ```
   注意：该语句首关键字是 `CREATE`，runner 允许；但仍建议独立迁移，保持 039 单一职责。

### 3.7 是否「报废旧密码」：本轮采用，代价如实记录

**决定：重置申请成功即覆盖 `pass` 为不可知哈希。** 理由：

- 忘记密码的产品语义是「旧密码作废」；若旧密码仍可登录，任何知道旧密码的人（离职运营、泄露的密码本）都能继续进入。
- 强制改密若只靠 `must_change_pass` 拦截，旧密码持有者可以抢先登录并把密码改成自己的，等于一次静默接管；覆盖后这个路径不存在。

代价（必须在文档里讲清、并由 Q5 复核）：

1. 临时密码过期/丢失 → 账号进不去，只能重新申请（重置限流仍在：`public_teams/my.rs:390-392`、:415-461）。
2. **回滚 039 后，已重置过的账号会停留在「`pass` 是不可知哈希」状态**——回滚 SQL 必须配套人工重置（§5.4），不能只 DROP 列。
3. 若邮件发送失败，绝不允许先覆盖 `pass`：现有 WIP 已经做到「先发信、成功才落库」（`public_teams/my.rs:611-628`），本设计沿用该顺序。

### 3.9 边界与并发

| 场景 | 行为 |
|---|---|
| 连续点两次「忘记密码」 | 第二次覆盖 `temp_pass_hash/exp`，第一封邮件里的临时密码立即作废（只有最新一封有效）；重置限流仍拦高频 |
| 并发两次登录用同一临时密码 | CAS 只有一方成功；另一方收到「临时密码已失效/密码错误」 |
| 邮件发送成功但落库失败 | 用户拿到一封无效密码；现有 WIP 在丢库错误时返回 500，用户可重试申请；不会出现「库里已改但邮件没发」 |
| 临时密码过期后才使用 | 惰性清理 + 登录失败提示重新获取（文案见 Q4） |
| 账号被删除 | 行删除，临时密码随之消失（`my_account_delete`，`store/my_account.rs:499-507`） |
| 管理观看账号（`is_admin=1`） | 重置入口 SQL 带 `is_admin=0` 过滤（`store/my_account.rs:1343`、:1376），不参与临时密码流程 |
| 时钟 | 过期判定统一用 DB `now()`；应用侧不自己拼过期字符串，避免机器时钟漂移 |

### 4.5 「登录后强制改密」的服务端拦截（设计选择，非数据模型）

`must_change_pass` 只是数据，是否真拦在服务端要定方案：

- **方案 1（推荐，本轮）**：在 `/api/public/teams/{team}/my/*` 路由前缀挂一个轻量中间件：解析 `X-My-Token`（复用 `my_token_take` / `my_token_required_with_restore` 的逻辑），若该账号 `must_change_pass=1`，除白名单（`/my/password`、`/my/who`、`/my/email`）外一律 403「请先修改密码」。代价：每次请求多一次小表查询（68 行，可加短 TTL 内存缓存）。
- **方案 2（更彻底，改动大）**：`my_token_put` 的 token 记录加第 5 个字段（`admin.rs:494-517`，内存元组 + Redis JSON `mytok_redis_set` :458-478），`my_token_take` 返回结构体（现返回 `(u64,String,String)`，:519 起）；全仓 `my_token_take` / `my_token_required*` 调用共 27 处、分布在 5 个文件（my.rs / minutes.rs / wx.rs / admin.rs / site.rs），破坏面大，建议下一轮再做。
- **方案 3（最弱）**：仅前端拦截（登录响应 `mustChangePass=true` 强制弹窗）。不满足「强制」的安全语义，若本轮工期紧可作为过渡，但需在审计报告登记。

无论选哪个，`must_change_pass` 的清零点都在 §4.1 `self_set_password_inner`，与拦截方案解耦。

### 5.3 数据核对 SQL

```sql
-- (1) 表结构：三列必须存在，类型/默认值符合设计
SELECT column_name, data_type, is_nullable, column_default
  FROM information_schema.columns
 WHERE table_name = 'my_accounts'
   AND column_name IN ('email','temp_pass_hash','temp_pass_exp','must_change_pass')
 ORDER BY ordinal_position;

-- (2) 迁移登记
SELECT version, applied_at FROM schema_migrations
 WHERE version IN ('038_my_account_email','039_my_temp_pass')
 ORDER BY version;

-- (3) 邮箱形态盘点（QQ / 非 QQ / 未绑）
SELECT
  count(*) FILTER (WHERE email = '')                             AS unbound,
  count(*) FILTER (WHERE email ~ '^[1-9][0-9]{4,11}@qq\.com$')   AS qq_bound,
  count(*) FILTER (WHERE email <> ''
                     AND email !~ '^[1-9][0-9]{4,11}@qq\.com$')  AS non_qq_legacy
FROM my_accounts;

-- (4) 重复邮箱（加唯一索引/查重前必须为 0 行）
SELECT email, count(*) FROM my_accounts
 WHERE email <> '' GROUP BY email HAVING count(*) > 1;

-- (5) 状态一致性：应全部返回 0 行
SELECT name, 'temp_expired_but_not_cleared' AS issue
  FROM my_accounts WHERE temp_pass_hash <> '' AND temp_pass_exp <= now()
UNION ALL
SELECT name, 'temp_without_must_change'
  FROM my_accounts WHERE temp_pass_hash <> '' AND must_change_pass = 0
UNION ALL
SELECT name, 'must_change_without_any_reason'
  FROM my_accounts
 WHERE must_change_pass = 1 AND temp_pass_hash = ''
   AND pass = '';   -- 若 pass 非空，可能是「已消费临时密码待改密」，属正常

-- (6) 临时密码待处理量（运营观测）
SELECT
  count(*) FILTER (WHERE temp_pass_hash <> '')      AS pending_temp,
  count(*) FILTER (WHERE must_change_pass = 1)      AS must_change,
  count(*) FILTER (WHERE email = '')                AS no_qq_email
FROM my_accounts;

-- (7) 管理员观看账号不应出现在重置目标里（抽查）
SELECT name FROM my_accounts WHERE is_admin = 1 AND must_change_pass = 1;  -- 期望 0 行
```

> 说明：`now()` 相关条件在人工核对时可能因时间流逝出现「刚过期」的假阳性；以 `temp_pass_exp > now()` 为准做判定，不要用 `applied_at` 之类近似。

```sql
BEGIN;

-- 1) 把「因重置而 lock 住」的账号先人工复位（可选但强烈建议）：
--    这些账号的 pass 已被覆盖为不可知哈希，不回滚库删列前无法自助登录。
--    正常做法是由管理员在后台重新设密码（my_account_set），并按运营名单通知。
--    （没有数据库备份纪律，无法从备份恢复旧密码哈希。）
SELECT name, email, must_change_pass,
       temp_pass_hash <> '' AS has_temp
  FROM my_accounts
 WHERE must_change_pass = 1 OR temp_pass_hash <> ''
 ORDER BY name;

-- 2) 结构回滚（DROP COLUMN 会锁表；本机 68 行毫秒级）
ALTER TABLE my_accounts DROP COLUMN IF EXISTS must_change_pass;
ALTER TABLE my_accounts DROP COLUMN IF EXISTS temp_pass_exp;
ALTER TABLE my_accounts DROP COLUMN IF EXISTS temp_pass_hash;

-- 3) 版本登记回滚（否则下次 migrate 认为 039 已应用）
DELETE FROM schema_migrations WHERE version = '039_my_temp_pass';

COMMIT;
```

回滚注意：

1. **`pass` 被覆盖是不可逆的**（旧哈希没有第二份副本；本项目纪律明确不做数据库备份）。回滚后必须逐个给 `must_change_pass=1` / `temp_pass_hash<>''` 的账号重新设密码。
2. 如果 040（邮箱唯一索引）已经加了，回滚 039 时**不要**顺手删它；040 有自己的登记行。
3. 回滚后代码若仍调用 `temp_pass_*`，PG 会报 42703；因此代码回滚必须同步（或让新代码保留「列缺失回落」分支，如 §4.1 所述）。

## 7. 待用户确认问题（Q1–Q10）

> 每条都可直接回答；带「默认」的表示不答则按默认执行。

- **Q1 QQ 号校验细节**：长度取 **5~12 位**可以吗？是否接受「粘贴完整邮箱（`123456@qq.com`）自动剥后缀」？（默认：5~12、纯 ASCII 数字、首位非 0、去空白；兼容剥后缀。腾讯对 QQ 号长度的公开规范**待核实**，12 只是冗余上限。）
- **Q2 同一 QQ 能否绑定多个账号**？若「不能」→ 040 建 partial unique index，第二个账号绑定时 400「该 QQ 号已绑定其他账号」；若「能」→ 不建索引，仅应用层查重提示。（默认：不能，040 加唯一索引。）
- **Q3 临时密码有效期**：30 分钟合适吗？还是 15/60？（默认：30 分钟。注：文档②/④ 已按 15 分钟写契约，本问题也是**跨文档统一**的裁决点。）
- **Q4「单次有效」的精确含义**：①**登录成功一次即作废**（用户若在改密前清缓存/换设备，需要重新申请）；②保留到改密成功才作废（体验稳，但同一临时密码在有效期内可反复登录）。默认：①。
- **Q5 重置成功后旧密码是否必须立即失效**？默认：是（`pass` 覆盖为不可知哈希）。⚠️ 文档②/④ 当前按「旧密码仍有效」写（`must_change_pass` 只拦截），与本默认相反——请裁决；若选「否」，需要接受「知道旧密码的人仍可登录并被强制改密」的风险，且 Q5 与 Q3（有效期）一起决定 S2 状态的锁定风险。
- **Q6 非 QQ 历史邮箱（如 `xx@163.com`）怎么处理**？默认：忘记密码时**不发信**，提示「当前绑定的是非 QQ 邮箱，请先重绑 QQ 号」。是否要在「我的」页保留「解绑/重绑」入口（推荐保留）？
- **Q7 展示端/管理端能看到多少 QQ 信息**？建议：展示端只显示 `1***@qq.com` 或打码 QQ（`1****5678`）+ `emailBound`；管理端可明文（鉴权已由 `ADMIN_PASSWORD` 保护）。是否同意？（默认：按此执行。）
- **Q8 未绑手机号的账号如何「补手机号」**？当前没有短信通道，也没有用户自助绑手机号接口（`person_set_phone` 仅在管理端 `/api/admin/streamers/{id}/phone`，`main.rs:706-710`，且只改台账 `person.phone`，不改 `my_accounts.phone`）。默认：登录后提示「请联系管理员绑定手机号并设置密码」，不做自助入口。
- **Q9 未绑主播（`bound=0`）账号的艺名登录展示口径**：`who` 的 `name` 目前下发 `info.phone`（无手机号即空串，`minutes.rs:855`）。默认改为账号 `name`（即艺名），`phone` 另给脱敏值；是否同意？另外，若台账改名同步失败（`admin.rs:800-825` 只记 WARN），是否需要一次「账号名 ↔ 台账名」巡检 SQL？
- **Q10 「登录后强制改密」本轮做到哪一层**：①服务端中间件拦截（推荐，非白名单接口 403）；②token 结构改造（彻底但动 27 处）；③仅前端弹窗（过渡）。默认：①。
