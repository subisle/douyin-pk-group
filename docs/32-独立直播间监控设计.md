# 独立直播间监控设计（本地测试阶段）

> 2026-11-09 用户口径：当前先验证直播间能否稳定监控，不要求对应赛事分组；
> 分组、晋级和推送仍沿用原有 `live_*` 赛事链路。

## 1. 原链路的问题

原采集链路：

```text
collector --event E --room R
  → POST /api/internal/live/events/E/observations
  → ingest_observation(event_id)
  → resolve_group(event_id, battle)
  → live_round / live_score_sample
```

`resolve_group` 会按赛前 UID 集合找小组，找不到时回落到该赛事第一组。
因此，一个没有登记到赛事分组里的测试直播间，分数会被错误挂到某个小组。

## 2. 独立监控链路

新增一条不经过赛事/小组的窄链路：

```text
collector --room R
  → POST /api/internal/live/rooms/R/observations
  → ingest_room_observation(web_rid, observation)
  → live_room_score_sample(web_rid, battle_id, ...)
```

不写入 `live_round`、`live_round_seat`、`live_group` 或 `live_qualifier`。
管理端读取：

```text
GET /api/live/rooms/R
```

返回房间健康度、最近 `battle_id` 和该局每个 UID 的最新采样。

## 3. 分数口径

直播接口原始字段：

- `battle_scores[].score`：直播画面显示的分数，已计入加成。
- `battle_settings.lynx_data.battle_easter_egg_info`：
  - `config.addition_multiple`：`150` 表示 1.5 倍，`200` 表示 2 倍。
  - `update_info.reward_info.addition_score_map[uid]`：该 UID 已计入显示分的累计加成增量。
  - `period_list` 中 `stage=4`：实际加成窗口，`start_time_sec + duration_sec`。

计算：

```text
显示分（加成后） = battle_scores[].score
去加成原分       = max(0, score - addition_score_map[uid])
加成倍数         = addition_multiple / 100
```

注意：不能直接用 `score / addition_multiple` 计算整场原分，因为加成窗口之外的
礼物不会乘倍；只有在一个完整加成区间内比较增量时，才可用
`Δ显示分 / 倍数` 估算该区间原分增量。

## 4. 实测参考

- 10 分钟 PK：曾观测到 `06:30–09:00` 的加成窗口。
- 5 分钟 PK：曾观测到 `03:00–04:00`，也观测到不同主播因任务进度不同而分别为
  `01:35–03:59`、`02:00–03:59` 的窗口。

因此不能按固定分钟数写死；应以每场返回的 `period_list` 为准。

## 5. 本地运行

```bash
# 独立房间监控（不关联 event/group）
scripts/live/run-room.sh 90968758361

# 原有赛事监控
scripts/live/run-local.sh 5 505899768449
```

管理端页面：

```text
http://127.0.0.1:8787/admin/live-room?room=90968758361
```

原有页面仍为：

```text
http://127.0.0.1:8787/admin/live
```

## 6. 当前限制

- 独立链路与赛事链路目前是两套采样表；后续需要接分组时，按 `battle_id` 做一次显式关联，
  不在采集阶段自动猜测小组。
- `addition_score_map` 之外的 `rank_bonus_score` / `winning_streak_bonus_score` /
  `battle_count_bonus_score` 仍保留原始字段，当前页面只把彩蛋加成计入“去加成原分”；
  后续遇到非零值需要单独校准口径。
