# 15 · 主播台账字段与验收（2026-10-12）

> 适用页面：管理后台 `/admin/streamers`，前端 `apps/douyin-web/src/StreamerPage.tsx`
> 适用接口：`GET /api/admin/streamers?q=&team=`
> 本文只做验收和排查。**所有数据库命令均为只读 SELECT / SHOW；禁止在本验收流程里执行迁移、导入、UPDATE、DELETE、INSERT 或任何写接口。**
> 本次基线：本机 `douyin_dev`，只读账号 `pk_reader`，2026-10-12 实测。

## 1. 台账口径速查

台账**一行 = 一个人**，不是一行一个抖音号，也不是一行一个登录账号。

| 页面列 | 接口字段 | 真实来源 | 口径 |
|---|---|---|---|
| 姓名 | `name` | `person.name` | 姓名是人的唯一标识；当前列表里同名会显示“重名”红标，需合并或改名 |
| 抖音号 | `douyinNos` / `douyinCount` | `account.douyin_no` / `COUNT(account.id)` | 多号时主号在前；`douyinCount` 包含 `douyin_no=''` 的未登记账号，`douyinNos` 只拼接非空抖音号 |
| 手机号 | `phone` | `person.phone` | 016 迁移后的主播档案手机号；不是 `my_accounts.phone` |
| 微信机器人 | `wxbot` | `wx_push_accounts` | 一人一个 bot；优先按 `person_id` 匹配，老数据 `person_id=0` 才按 `name` 兜底，多行取 `bound_at` 最新 |
| 推送开关 | `wechatPush` | `push_bindings.notify_target / daily_report` | 与 `wxbot` 是两回事，只表达推送是否开着 |

`wxbot` 为 `null` 表示没有 `wx_push_accounts` 行；有行时结构为：

```json
{
  "bound": true,
  "activated": true,
  "nickname": "微信昵称",
  "boundAt": "2026-10-12 10:30:00"
}
```

`activated = conversation_id <> ''`。iLink 只能被动回复，主动推送要等用户先给机器人发消息留下 `context_token`；因此“已扫码但 `conversation_id` 还是空”显示为**待激活**，不是“未绑定”。

## 2. 接口验收

### 2.1 用管理端登录接口拿 token

路由和入参已按 `rust/crates/pk-server/src/auth.rs`、`rust/crates/pk-server/src/main.rs`、`apps/douyin-web/src/api.ts` 核实：

- 方法/路径：`POST /api/auth/login`
- JSON 入参：`{"password":"管理员口令"}`
- 成功响应：`{"token":"...","enabled":true}`
- 后续请求头：`Authorization: Bearer <token>`
- 未配置 `ADMIN_PASSWORD` 时接口返回 503；口令错误返回 401。

本机开发服务默认监听 `127.0.0.1:8787`。以下命令会提示输入口令，不把口令写进命令历史：

```bash
BASE="${BASE:-http://127.0.0.1:8787}"

printf '管理员口令: ' >&2
read -rs ADMIN_PASSWORD
printf '\n' >&2

TOKEN=$(curl -sS -X POST "$BASE/api/auth/login" \
  -H 'Content-Type: application/json' \
  --data "$(ADMIN_PASSWORD="$ADMIN_PASSWORD" python3 -c 'import json,os; print(json.dumps({"password": os.environ["ADMIN_PASSWORD"]}))')" \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["token"])')

test -n "$TOKEN" && echo 'token ok'
```

### 2.2 取台账并检查字段

```bash
curl -sS "$BASE/api/admin/streamers?q=&team=" \
  -H "Authorization: Bearer $TOKEN" \
  | python3 -m json.tool
```

如果输出很长，只看第一行并断言五个字段都在：

```bash
curl -sS "$BASE/api/admin/streamers?q=&team=" \
  -H "Authorization: Bearer $TOKEN" \
  | python3 -c '

```

**期望看到什么**：断言不报错；`name` 是姓名，`douyinNos` 是字符串或 `null`，`douyinCount` 是非负整数，`phone` 是字符串（未登记时为空串），`wxbot` 是 `null` 或上面的对象。当前本机服务未启动，本次只核实了代码路由与入参；在有服务的环境执行本节即可。

### 3.3 ① 每个主播的抖音号个数分布

全表口径（含软删 person；用于解释为什么旧文档说 94 人 1 个号）：

```sql
SELECT c.douyin_count, COUNT(*) AS person_count
  FROM (
    SELECT p.id, COUNT(a.id) AS douyin_count
      FROM person p
      LEFT JOIN account a ON a.person_id = p.id
     GROUP BY p.id
  ) c
 GROUP BY c.douyin_count
 ORDER BY c.douyin_count;
```

**期望看到什么**：当前真实输出为 `0 个号 = 4 人`、`1 个号 = 94 人`、`2 个号 = 13 人`、`3 个号 = 2 人`。这里统计的是 `account` 行数，不是非空抖音号的去重数。

台账页面口径（只看 `deleted_at IS NULL`，与 `/api/admin/streamers` 行范围一致）：

```sql
SELECT c.douyin_count, COUNT(*) AS person_count
  FROM (
    SELECT p.id, COUNT(a.id) AS douyin_count
      FROM person p
      LEFT JOIN account a ON a.person_id = p.id
     WHERE p.deleted_at IS NULL
     GROUP BY p.id
  ) c
 GROUP BY c.douyin_count
 ORDER BY c.douyin_count;
```

**期望看到什么**：当前真实输出为 `0 个号 = 1 人`、`1 个号 = 88 人`、`2 个号 = 13 人`、`3 个号 = 2 人`，共 104 个在职主播。台账页应当因此显示 104 行；`douyinCount=3` 的是有 3 行 `account` 的人，不代表 3 个非空抖音号。

### 3.4 ② wx_push_accounts 的 person_id 对账

```sql
SELECT COUNT(*) AS total_rows,
       COALESCE(SUM(w.person_id > 0), 0) AS matched_by_person_id,
       COALESCE(SUM(w.person_id = 0 AND EXISTS (
         SELECT 1
           FROM person p
          WHERE p.name = w.name
            AND p.deleted_at IS NULL
       )), 0) AS fallback_by_name,
       COALESCE(SUM(w.person_id = 0 AND NOT EXISTS (
         SELECT 1
           FROM person p
          WHERE p.name = w.name
            AND p.deleted_at IS NULL
       )), 0) AS unmatched
  FROM wx_push_accounts w;
```

**期望看到什么**：`matched_by_person_id` 是能直接按人关联的行数；`fallback_by_name` 是 015 之前 `person_id=0`、只能靠展示端账号姓名对应的行；`unmatched` 应尽量为 0。**2026-10-12 本次基线**：`wx_push_accounts` 总行数为 0，因此四项都是 0；台账接口对 104 人全部返回 `wxbot: null`。

### 3.5 ③ 一人多号清单

```sql
SELECT p.id AS person_id,
       p.name,
       COUNT(a.id) AS account_rows,
       GROUP_CONCAT(a.douyin_no ORDER BY a.is_primary DESC, a.id SEPARATOR ' / ') AS douyin_nos,
       GROUP_CONCAT(a.anchor_id ORDER BY a.is_primary DESC, a.id SEPARATOR ' / ') AS anchor_ids
  FROM person p
  JOIN account a ON a.person_id = p.id
 WHERE p.deleted_at IS NULL
 GROUP BY p.id, p.name
HAVING COUNT(*) > 1
 ORDER BY account_rows DESC, p.id;
```

**期望看到什么**：当前真实输出为 **15 行**；其中 2 人的 `account_rows = 3`（`狼佑`、`浩沐`），其余为 2 个账号。列表里的空抖音号或重复抖音号也要保留展示，因为 `douyinCount` 是 `account` 行数、`douyinNos` 是非空号拼接，不能擅自去重。

### 3.6 ④ 手机号重复清单

先检查 016 的 `person.phone` 是否已经落地：

```bash
PHONE_READY=$(mysql -h127.0.0.1 -P3306 -upk_reader -p douyin_dev -N -e \
  "SELECT COUNT(*) FROM information_schema.columns
    WHERE table_schema = DATABASE()
      AND table_name = 'person'
      AND column_name = 'phone'")

if [ "$PHONE_READY" = "1" ]; then
  mysql -h127.0.0.1 -P3306 -upk_reader -p douyin_dev -e "
    SELECT phone, COUNT(*) AS n, GROUP_CONCAT(name ORDER BY name SEPARATOR '、') AS names
      FROM person
     WHERE phone <> ''
     GROUP BY phone
    HAVING COUNT(*) > 1
     ORDER BY n DESC, phone;"
else
  echo 'SKIP: person.phone 不存在（016 未落地），本项不能验收；不要把空结果当成“无重复”。'
fi
```

**期望看到什么**：`PHONE_READY=1` 时，SQL 返回重复手机号分组；016 建了 `phone_uniq` + `uk_person_phone_uniq` 后，这里应始终为 **0 行**。若 `PHONE_READY=0`，文档不能把“未返回重复”解释为数据干净，必须先完成 016 迁移与排查。**2026-10-12 本次基线**：`PHONE_READY=0`，本机 `douyin_dev` 未落地 016，故本项无真实重复清单可出。

作为当前库的登录账号侧旁证，可以额外跑下面这条；它检查的是 `my_accounts.phone`，不是 `person.phone`：

### 3.7 ⑤ 一个人多个 wxbot 的清单

## 4. 人工点验 `/admin/streamers`

打开：

```text
http://127.0.0.1:8787/admin/streamers
```

逐条核对：

1. **姓名列**：当前列表有重名时，该行姓名旁应出现红色“重名”徽标。此时姓名已经不能作为人的唯一标识，运营必须用右键“合并”或改名处理，不能继续按抖音号猜。基线：104 行、0 组重名。
2. **抖音号列**：主号在前并带“主号”徽标；同一人多行显示为竖排。行内 `douyinCount > 1` 时显示“N 个号”；有账号但抖音号为空时显示“未登记抖音号（采集号 ...）”，不能显示成 `0` 或“未绑定抖音号”。基线：1 人没有 account，13 人有 2 个 account，2 人有 3 个 account。
3. **手机号列**：显示 `person.phone` 的值；为空显示“未登记”。若已有 `my_accounts` 登录账号则同时显示“已开号”。当前本机未跑 016，接口走兼容查询，基线应全部为空串/“未登记”，即使该人有登录账号也不能把 `my_accounts.phone` 回填进来。
4. **微信机器人列**：
   - `wxbot = null`：显示“未绑定”；
   - 有 `wx_push_accounts` 行但 `conversation_id=''`：显示“待激活”，表示已扫码但还没给机器人发过消息；
   - 有行且 `conversation_id<>''`：显示“已绑定”，有昵称则同时显示微信昵称；
   - `wechatPush=false`：额外显示“未开推送”。
   当前基线 `wx_push_accounts` 为 0 行，所以 104 行都应是“未绑定”；本次没有真实“待激活/已绑定”数据可供人工点验，需等真实扫码后复验。
5. **推送开关与 bot 不要混看**：看到“已绑定”只说明 `wx_push_accounts` 有扫码凭证；是否主动推送还要看 `wechatPush`。看到“待激活”不要让人重扫，先让对方给机器人发一条消息。

## 6. 本次发现的坑（验收到这里先停一下）

1. **本机库不是文档所述的完整身份模型**：`schema_migrations` 只到 014，但 `wx_push_accounts` 已有 018 的两个生成列；`person.phone`、`my_accounts.person_id` 仍不存在。结果是 `/api/admin/streamers` 会走 `STREAMERS_SQL_LEGACY`，四个字段里 `name / douyinNos / douyinCount / wxbot` 仍可验收，`phone` 只能是空串、`hasAccount` 只能是 false。不要把本机结果拿去当生产手机号基线。
2. **`douyinCount` 不等于“有抖音号的个数”**：它数 `account` 行，空 `douyin_no` 也算。当前狼佑有 3 个 `account` 行但其中 1 行号为空的重复项；页面显示 3 个号是符合代码口径的，不是重复计算 bug。
3. **`wxbot` 和 `wechatBound/wechatPush` 必须分开看**：前者回答“有没有扫码、激活没激活、微信昵称是什么”，后者回答“旧推送绑定/开关开没开”。扫码后到首条私聊前，只看 `push_bindings` 会误报“未绑定”。
4. **“待激活”是正常中间态**：不是没绑定，也不是服务端故障。主动推送需要用户先给机器人发消息产生 `context_token`；运营应提示对方发一条消息，而不是让他重扫。
5. **手机号验收不能跳过 schema 前置检查**：当前库没有 `person.phone`，直接照搬 SQL 会报 `Unknown column`。先执行 §3.2 / §3.6 的检查，看到 `PHONE_READY=1` 再验收重复清单。
