# 03 · 融合架构评审与修正版设计

> ⚠️ **本文件是 v1（Go + Rust 双服务）阶段的历史评审记录，仅作决策过程存档。**
> 2026-10-02 已决定后端统一为 Rust 单技术栈，现行方案以
> `docs/04-统一技术栈决策.md`、`docs/02-融合架构设计.md`、`docs/07-后端需求文档.md` 为准。
> 下文所有「`server-go` / Go 写库 / douyin-server / TypeSafe 决策层」均为过时表述。

> 评审对象：`docs/02-融合架构设计.md`
> 目标：把 `douyin-data-manager@3328` 融合进本仓库，跑在 RK3318 上
> 结论：**方向正确，可以做；但有 6 处需要修正后再进入 S0**

---

## 1. 总体结论

你现在的设计主线是对的：

- 3328 作为**数据上游**，不是简单外挂
- Go 负责写库，Rust 负责只读展示
- MySQL 作为唯一事实源
- 两套前端先分离，后续再决定是否合并

但文档里有几处事实偏差和设计风险，直接按原文执行会在 S0/S1 卡住：

1. **“typsafe” 是拼写错误**，正确名称是 **TypeSafe**
2. **TypeSafe 不是类型系统**，不能拿它替代 `enum` / `trait`
3. 3328 的实际技术栈与你描述不完全一致
4. RK3318 上跑 Chromium sidecar 的内存风险被低估
5. `packages/contract` 的生成方式需要更明确
6. TypeSafe 不能进入机器人请求路径，否则会违反 3328 的“无 AI”硬规则

---

## 2. 需要修正的事实

| # | 文档原文 | 实际情况 | 修正建议 |
|---|---|---|---|
| 1 | “Go 1.26” | 3328 实际是 **Go 1.27** | 构建镜像和 CI 按 `go 1.27` |
| 2 | “chi/gin 风格 HTTP” | 3328 用的是 **标准库 `net/http` + 自研 `httpapi`** | 不要引入 chi/gin，保持现状 |
| 3 | “arm64 scratch 镜像 ~25MB” | 实际 Dockerfile 基于 **alpine**，约 **50MB** | 文档和体积预期改成 50MB 级 |
| 4 | “schema 完全同源” | 核心表同源，但不是全表 1:1 | 只承诺**pk-server 依赖的子集**兼容 |
| 5 | “交给类型系统兜底” | 这是**编译期类型系统**，不是 TypeSafe | 分成两件事：类型系统 + TypeSafe 决策层 |
| 6 | “typsafe 落地” | 正确拼写是 **TypeSafe** | 全文统一改为 TypeSafe |

## 3. 修正后的目标架构

```text
RK3318 (arm64, Docker)
├─ Caddy :80
│  ├─ /dy/*   → douyin-server :8080
│  ├─ /st/*   → pk-server :8787
│  └─ /api/pk/* → pk-server :8787
│
├─ douyin-server (Go)
│  ├─ 采集 / CSV 导入 / 管理后台 API
│  ├─ 微信 iLink + QQ 机器人
│  └─ 拥有 MySQL 写权限
│
├─ pk-server (Rust)
│  ├─ 分组算法 / 展示页 / 方案管理
│  ├─ 只读账号连 MySQL
│  └─ 本地 SQLite 保存方案与别名
│
├─ MySQL 8
│  └─ person / account / daily_metric / monthly_metric / yearly_metric
│
└─ tools/decision (可选)
   ├─ TypeSafe 决策目录
   ├─ 只给管理员/开发期使用
   └─ 不进入机器人请求路径
```

### 3.1 职责边界

| 组件 | 职责 | 权限 |
|---|---|---|
| `server-go` | 采集、导入、机器人、管理 API | MySQL 写账号 |
| `pk-server` | 分组、展示、导出方案 | MySQL 只读账号 |
| `apps/douyin-web` | 3328 管理后台 | 只调 Go API |
| `apps/web` | PK 分组前端 | 只调 Rust API |
| `packages/contract` | API 契约与生成类型 | 无运行时权限 |
| `tools/decision` | TypeSafe 决策工具 | 只在开发期或管理员后台调用 |

## 4. 数据层设计

### 4.1 主库归属

- 主库：RK3318 本地 MySQL 8
- 库名：`douyin`
- Migration：只由 `server-go` 管理

### 4.2 账号权限

| 账号 | 权限 | 用途 |
|---|---|---|
| `douyin_writer` | `SELECT / INSERT / UPDATE / DELETE` | 业务写入 |
| `douyin_migrator` | `DDL + 上述权限` | 仅 migration 使用 |
| `pk_reader` | `SELECT` | pk-server 专用 |

不要让 `pk-server` 拿到写权限。

### 4.3 方言收窄

在 `pk-server` 里加显式方言：

```rust
pub enum Dialect {
    Local,
    SqlPub,
}
```

`Local` 指向 RK3318 上的 MySQL；`SqlPub` 保留为历史参考源。不要继续用字符串 ID 猜方言。

## 5. 服务间契约

### 5.1 契约包

新增 `packages/contract`，做三件事：

1. 用 OpenAPI 描述 API
2. 从 OpenAPI 生成 TS 类型
3. CI 校验 Rust/Go 实现与 OpenAPI 一致

不建议一开始就做“Go/Rust 双向生成”，会拖慢 S0。

### 5.2 路由挂载

```caddyfile
/dy/*      → douyin-server:8080
/st, /s/*  → pk-server:8787
/api/pk/*  → pk-server:8787
```

两个前端先不合并，避免一次性改动过大。

## 6. TypeSafe 决策层

### 6.1 定位

TypeSafe 用来处理**语义判断**，不是编译期类型系统。

适合用 TypeSafe 的场景：

- 名单匹配出现多个相似主播时，选择最可能的一个
- 判断某条数据是否需要人工复核
- 给异常数据做严重程度评分

不适合用 TypeSafe 的场景：

- 数据库方言选择
- API 权限判断
- 分组算法本身
- 机器人指令路由

### 6.2 与 3328 硬规则的冲突

3328 项目规则明确写了：

> 无 AI 能力，没有模型调用，没有 Agent。

所以 **TypeSafe 不能进入机器人请求路径**。

推荐做法：

- 只放在 `tools/decision` 或管理员后台
- 结果落库为 `DecisionRecord`
- 机器人仍然走确定性规则
- TypeSafe 的建议只作为人工确认参考

### 6.3 问题类型选型

| 场景 | TypeSafe 原语 | 说明 |
|---|---|---|
| 名单匹配候选 | `choice` | 从固定候选里选一个 |
| 异常严重程度 | `score` | 有序打分 |
| 是否需要人工复核 | `noul` | 是/否判断 |

### 6.4 示例：名单匹配

```json
{
  "state": {
    "input": "阿楠",
    "candidates": [
      { "id": "101", "name": "浩楠" },
      { "id": "102", "name": "晓楠" },
      { "id": "103", "name": "南方楠" }
    ]
  },
  "questions": {
    "best_match": {
      "type": "choice",
      "instructions": "选择最可能是用户想输入的主播",
      "criteria": {
        "101": "名字与输入高度相似",
        "102": "名字与输入部分相似",
        "103": "名字与输入部分相似"
      }
    },
    "needs_review": {
      "type": "noul",
      "instructions": "这个匹配是否足够模糊，需要人工确认？"
    }
  }
}
```

代码侧只消费 `choice` 和 `noul`，并设置置信度阈值。

## 7. RK3318 部署

### 7.1 常驻内存预算

| 容器 | 建议上限 | 说明 |
|---|---:|---|
| MySQL | 512MB | 主库 |
| douyin-server | 256MB | Go 服务 |
| pk-server | 128MB | Rust 服务 |
| Caddy | 64MB | 入口 |
| **合计** | **约 960MB** | 2GB 机器可跑 |

### 7.2 渲染策略

不建议在 RK3318 上常驻 Chromium。

推荐顺序：

1. 优先用 `resvg` 或原生 canvas
2. 需要像素级还原时，再临时启动 Chromium sidecar
3. 1GB 机型直接禁用 Chromium

把渲染后端抽成 trait：

```go
type Renderer interface {
    RenderPNG(ctx context.Context, tpl Template) ([]byte, error)
}
```

---

## 9. 结论

设计可以继续推进，但要做这四个调整：

1. 把 “typsafe” 全部改成 **TypeSafe**
2. 把 **类型系统** 和 **TypeSafe** 拆成两层
3. 把 3328 的实际技术栈和镜像体积修正
4. 渲染侧默认不用 Chromium，改为可插拔后端

做到这些，S0 就可以开始。
