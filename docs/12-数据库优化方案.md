### 1.4 「一人多号」是既定事实，不是脏数据

`account` 118 行 / `person` 105 行，实测多号分布：

| person_id | account 行数 |
|---|---:|
| 86 | 3 |
| 1021 | 3 |
| 49 / 26 / 27 / 77 / 1027 / 5 | 各 2 |

已确认 8 人占 18 个号；剩余 100 个号落在 97 人身上 → **至少还有 3 人是多号**。
所以「一人多号」在 `account` 层是**业务常态**（`account.is_primary` 已经表达了主/副号语义），
而 `my_accounts`（登录账号）应当保持**一人一号** —— 这两件事必须在模型上分清楚，不能混为一谈。

## 2. 问题清单

> 证据格式：`文件:行号`（均为仓库真实位置，可直接跳转核对）

### P1 · 主播改名 → 三张表的 `name` 不同步 → 账号彻底失联

| 项 | 内容 |
|---|---|
| 问题 | `my_accounts` / `push_bindings` / `wx_push_accounts` 三张表都以 **`name`（主播姓名）当主键**，改名只改 `person.name`，三表完全不知情 |
| 影响 | 主播改艺名后：登录时 `person.name` 查不到同名的账号 → **登不进去**；微信 bot 凭证、推送开关、追分目标全部留在旧名字下 → **推送静默失效**（用户以为开着，其实一条都收不到），且没有任何报错 |
| 证据 | 改名入口 `admin.rs:432` `sets.push("name = ?")` → `admin.rs:461` `UPDATE person SET {} WHERE id = ?`（只动 `person`，动不了其它三表）<br/>三表主键：`003_runtime.sql:60`、`004_push.sql:24`、`013_wx_push_accounts.sql:25` 全是 `PRIMARY KEY (name)`<br/>登录反查按姓名：`public_teams.rs:1247` 与 `public_teams.rs:1410` `WHERE p.deleted_at IS NULL AND p.name = ?`<br/>台账页绑定状态按姓名 JOIN：`dialect.rs:146-149` `WHERE pb.name = p.name`（→ `admin.rs:219` `wechatBound`） |
| 现状风险等级 | 表是空的（0/0/1 行）→ **暂未爆雷，但一放量就是批量事故**。现在改成本最低 |

### P2 · `my_accounts` 与 `person` 之间零外键，`person_id` 连列都没有

## 3. 优化方案

### 3.1 核心原则

1. **`person_id` 是唯一身份锚点**，`name` 降级为"显示名 + 兜底键"。
2. **只加不改**：015 全部是 `ADD COLUMN` / `CREATE INDEX` / `CREATE TABLE IF NOT EXISTS`。
   不删列、不改主键、不改列类型、不动任何既有行的数据 → **105 个主播一行都不会丢**。
3. **向后兼容**：现有 Rust 代码全部按 `name` 查询，015 之后**一行代码不改也能正常跑**。
   `person_id` 默认 0，所有 `INSERT` 不带新列照样成功；所有 `WHERE name = ?` 照样命中。
   代码迁移按模块**逐个灰度**（§3.5），不要求一次性改完。
4. **结构与数据分离**：沿用 009 迁移的先例（`009_anchor_convergence.sql` 注释：「迁移只建索引，
   不改任何数据……数据口径由代码负责」）—— **015 只做结构**，回填与孤儿扫描放附录 B 的运维 SQL。

### 3.2 结构改动清单

| # | 表 | 改动 | 为什么 |
|---|---|---|---|
| 1 | `my_accounts` | `ADD COLUMN person_id BIGINT UNSIGNED NOT NULL DEFAULT 0` | 补齐零外键（P2）。`0` = 未绑定 / 管理员观看账号，与 `push_bindings` / `wx_push_accounts` 的既有约定**完全一致**，不需要新的哨兵语义 |
| 2 | `my_accounts` | `ADD INDEX idx_my_person (person_id)` | 「某主播有没有账号」「按人查账号」的高频路径；也是 P7 批量开号后的去重扫描路径 |
| 3 | `my_accounts` | `ADD INDEX idx_my_person_bound (person_id, bound)` | 「已绑定主播的账号」列表，覆盖 P2 的回填验收 |

### 3.3 `name` → `person_id` 的查询契约（person_id 优先、name 兜底）

不改主键、不改数据的前提下，读路径统一改成这条模板（**两全其美：新数据走 `person_id`，老数据 / `person_id=0` 的行自动回落 `name`**）：

```sql
-- ① 已知 person_id（登录成功后 token 里带的）→ 优先按 person_id 定位，彻底免疫改名
SELECT ... FROM push_bindings
WHERE (? > 0 AND person_id = ?) OR (? = 0 AND name = ?)
ORDER BY person_id DESC
LIMIT 1;

-- ② 只有 name（管理员后台 / 机器人入站）→ 兜底，行为与今天完全一致
SELECT ... FROM push_bindings WHERE name = ? LIMIT 1;

-- ③ 孤儿过滤：任何读路径都要排除已离职主播（P3）
SELECT ... FROM push_bindings
WHERE ((? > 0 AND person_id = ?) OR (? = 0 AND name = ?))
  AND person_deleted_at IS NULL
ORDER BY person_id DESC
LIMIT 1;
```

**等价性论证（为什么不会破坏现有代码）**：
- 迁移刚跑完时，`my_accounts.person_id` 全部为 0（未回填）或回填成正确值，
  `push_bindings` / `wx_push_accounts` 的 `person_id` 现状也是 0 → 模板 ① 的第一个分支永不命中，
  恒等退化成 `WHERE name = ?`，**与今天逐字节等价**。
- 三张表行数 1 / 0 / 0 → 索引与列的代价可忽略，DDL 在 RK3318 上是毫秒级。
- 所有 `INSERT` 不带新列 → 走 `DEFAULT`，`person_id = 0` / `person_deleted_at = NULL`，语义正确。
- 已核查：仓库中不存在 `SELECT * FROM my_accounts / push_bindings / wx_push_accounts`，
  所有查询都是显式列清单 → **加列不会改变任何 `try_get` 的列序假设**。

### 3.4 孤儿清理 / 级联标记逻辑

**定义三类孤儿**（写入 `identity_orphan_log.kind`）：

| kind | 判定 | 处理建议 |
|---|---|---|
| `person_deleted` | `person_id > 0` 且对应 `person.deleted_at IS NOT NULL` | 后台列表展示，运营确认后：清 `wx_push_accounts.bot_token`（安全），`my_accounts` 置失效 |
| `person_missing` | `person_id > 0` 但 `person` 表里根本没有这行（硬删 / 数据搬迁遗留） | 人工核对后把 `person_id` 归零，回落 `name` 关联 |
| `dup_person` | 同一 `person_id` 在 `my_accounts` 里出现多行（唯一索引未生效时的兜底扫描） | 保留最早一行，其余改绑或删除 |

**级联标记时机**（应用层，不在 DDL 里）：

1. `delete_streamer`（`admin.rs:515`）/ `batch_delete`（`admin.rs:3518`）/ `merge_person`（`admin.rs:3638`）
   三处软删 `person` 成功后，**同一事务内**回填三张表的 `person_deleted_at`；
2. 每日一次定时扫描（或后台手动触发）跑附录 B-3 的 SQL，把漏网的写进 `identity_orphan_log`；
3. 后台新增"离职主播残留"列表（读 `identity_orphan_log WHERE handled = 0`），运营点"已处理"置 `handled = 1`。

> 为什么不用外键 `ON DELETE CASCADE`：本库全库刻意不建外键（`001_core.sql:4-5` 明确写了
> "不建外键（全量迁移时不用管插入顺序）"），且这里删的是**软删**（`UPDATE deleted_at`），
> 外键级联根本触发不了。用标记列 + 审计表，既保持既有风格，也避免物理删除凭证后无法追溯。

### 4.6 迁移内含的数据动作：**不放进 015**，原因说明

`migrate.rs:144-170` 的单测 `embedded_migrations_split_cleanly` 对迁移脚本有**语句白名单**：
每条语句必须以 `CREATE` / `ALTER` / `SET` / `PREPARE` / `EXECUTE` / `DEALLOCATE` 开头，
**裸 `UPDATE` / `INSERT` 会直接让单测失败**。加上 009 迁移已经确立"迁移只管结构、数据口径由代码负责"
的先例（且部署脚本 `scripts/deploy/147.sh:145` 把迁移与重启分成两步），
因此 **回填 / 孤儿扫描 / 批量开号一律放附录 B 的运维 SQL**，由运维显式执行。

> 若确实希望回填随迁移自动完成，把附录 B-1/B-2 的 `UPDATE` 用 `SET @s = 'UPDATE ...'; PREPARE ... EXECUTE`
> 包一层即可通过白名单（语句以 `SET` 开头）。**本方案不推荐**：迁移只应跑一次且要可预测，
> 回填数据量依赖当时台账状态，拆开更可控、也更好回滚。

### B-1 回填 `my_accounts.person_id`

```sql
-- 只回填 bound=1 的行：bound=0 的 name 是手机号占位串（008 迁移语义，store.rs:1074 附近），
-- 不能拿去和 person.name 比对。幂等，可重复跑（WHERE person_id = 0 保证不覆盖已回填的）。
--
-- ⚠️ 这里**故意不加** `p.deleted_at IS NULL`：已离职主播的登录账号正是 P3 要找的孤儿，
--    回填了 person_id，B-3.2 才能按 `person_id > 0 AND p.deleted_at IS NOT NULL` 把它们标出来。
--    （与 B-2 同一原则：回填阶段只管「能不能对上人」，在职与否交给 B-3 的级联标记判断。）

UPDATE my_accounts a
  JOIN person p ON p.name = a.name
   SET a.person_id = p.id
 WHERE a.person_id = 0
   AND a.bound = 1;

-- 同名主播（person.name 无唯一键）会导致 JOIN 出多行 → 先查出来人工裁决，别让 UPDATE 随机挑一个
SELECT a.name, COUNT(*) AS dup
  FROM my_accounts a
  JOIN person p ON p.name = a.name
 WHERE a.person_id = 0 AND a.bound = 1
 GROUP BY a.name HAVING COUNT(*) > 1;
```

### B-2 回填 `push_bindings` / `wx_push_accounts` 的 `person_id`（修 P5）

```sql
-- 现状两张表都是 0 行，回填是幂等空操作；以后 push_bind_account（store.rs:2171）
-- 补写 person_id 后，这两条用来兜历史行。
--
-- ⚠️ 与 B-1 不同：这两条**不能加 `p.deleted_at IS NULL`**。
--    理由（本地实测复现）：若某主播已经离职（person.deleted_at 非空），带该条件就回填不上
--    person_id，B-3 的孤儿扫描也就永远探测不到它 —— 离职主播的 bot 凭证会一直静默残留，
--    正是 P3 要防的事。这里**故意**也回填已离职的人，让 B-3 能把它们标出来。
--    同名主播同时有在职/离职两行时仍会 JOIN 出多行，需人工裁决（同 B-1）。

UPDATE push_bindings b
  JOIN person p ON p.name = b.name
   SET b.person_id = p.id
 WHERE b.person_id = 0;

UPDATE wx_push_accounts w
  JOIN person p ON p.name = w.name
   SET w.person_id = p.id
 WHERE w.person_id = 0;

-- 同名裁决（同上）：有行 = 人工改绑后再跑
SELECT w.name, COUNT(*) AS dup FROM wx_push_accounts w JOIN person p ON p.name = w.name
 WHERE w.person_id = 0 GROUP BY w.name HAVING COUNT(*) > 1;
```

## 6. 风险与回滚

### 6.1 如何保证 105 个主播数据不丢

| 保障 | 说明 |
|---|---|
| **DDL 性质** | 015 全部是 `ADD COLUMN` / `CREATE INDEX` / `CREATE TABLE IF NOT EXISTS`。**不 `DROP` 任何列、不 `MODIFY` 任何列类型、不 `DELETE` 任何行、不重建表** → 结构上不可能丢数据 |
| **新列必带 DEFAULT** | `person_id ... DEFAULT 0`、`person_deleted_at ... DEFAULT NULL` → 存量行自动填充，不会因 `NOT NULL` 无默认值而失败（MySQL 8 在 `sql_mode` 严格模式下会拒绝无默认值的 `NOT NULL` 加列，这里不存在该风险） |
| **不生成新主键** | 三张表的 `PRIMARY KEY (name)` 原样保留 → 现有 `WHERE name = ?` 全部照常命中，`ON DUPLICATE KEY UPDATE` 的冲突键也不变 |
| **INSERT 兼容** | 已逐处核查所有写入点（`store.rs:616` / `1074` / `1603` / `2038` / `2172` / `810`）都不带 `person_id` → 走 `DEFAULT`，不报错 |
| **SELECT 兼容** | 已核查仓库中**不存在** `SELECT * FROM my_accounts / push_bindings / wx_push_accounts`，全部是显式列清单 → 加列不影响任何 `try_get::<T,_>("col")` 或按序号取值 |
| **数据量极小** | 105 / 118 / 869 / 1 / 0 / 0 行 → `ADD COLUMN` 与建索引在 RK3318 上是毫秒级，无长事务、无锁表风险窗口 |
| **备份前置** | 执行前跑 `scripts/backup-to-remote.sh`（已有，落到远程备份库）；`scripts/deploy/147.sh` 也有 `--no-migrate` 开关可跳过 DDL |
| **迁移幂等** | `schema_migrations` 保证只跑一次（`migrate.rs:100-133`）；脚本内再用 `information_schema` 探测兜底，人工提前加过列也不会报错 |

### 6.2 灰度步骤

| 阶段 | 环境 | 动作 | 通过标准 |
|---|---|---|---|
| G0 | 本地 docker MariaDB | `cargo run -p pk-server -- migrate` + 附录 B 全量 | 结构查询（B-5-1/2）齐全；`cargo test -p pk-server` 全绿（含 `migrate.rs:144` 语句白名单、`versions_are_ordered`） |
| G1 | 147 / 备份库 | 同一套 SQL | 同上；顺带验证 `store.rs:2796-2826` 的 SQLite 搬家逻辑不受新列影响（它用的是显式列清单） |
| G2 | **RK3318 生产** | ① `backup-to-remote.sh` ② `pk-server migrate` ③ 结构验收 B-5-1/2 | 结构齐全且 `person_count = 105` 不变 |
| G3 | 生产 | 回填 B-1 / B-2 + 一致性验收 B-5-4 | B-5-4 返回 0 行（无接错人） |
| G4 | 生产 | 代码 S2 → S3 → S4 逐模块发版 | 每次发版后核对：登录成功率、推送条数、台账页 `wechatBound` 数量不下降 |
| G5 | 生产 | 孤儿扫描 B-3 接入定时任务 + 后台列表 | `identity_orphan_log` 有预期内的行 |
| G6 | 生产 | 启用 ⑤ 一人一号唯一索引（若 G0~G3 时跳过了） | `SHOW INDEX ... uk_my_person_uniq` 存在；重复开号报 `Duplicate entry` 并被代码翻成中文文案 |

> **关键灰度闸门**：G3 的 B-5-4（去掉 `p.deleted_at IS NOT NULL` 后只看 `name_mismatch` /
> `person_missing`）必须返回 0 行才允许进 G4。若返回 `name_mismatch`，说明台账存在重名且回填接错了人，
> 此时读路径会在"改名免疫"和"接错人"之间选了后者 —— 必须先人工改绑（把 `person_id` 改对）再继续。
> `person_deleted` 不算回填失败，交给 B-3 标记即可（这就是为什么 B-1/B-2 故意不排除离职主播）。

### 6.3 已知风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| **会话变量跨连接丢失** | 015 依赖 `SET @s` → `PREPARE` 在同一会话（与 012 同款）。`migrate.rs` 走连接池，理论上不同语句可能落在不同连接 | 迁移串行执行，sqlx 会复用刚归还的空闲连接，实践中与 012 一致可用；若要求绝对保险，把 `DB_MIGRATOR_*` 的 `pool_limit` 设为 1，或在 `migrate.rs` 里改用单连接执行（属于代码改动，本方案不做） |
| **重名主播回填接错人** | 姓名 JOIN 是启发式的，台账重名时会挑到错误的人 | B-1 先跑重名检测；B-5-4 一致性校验作为 G3 闸门；`person_id` 只在回填阶段由姓名推导，**之后一律以 `person_id` 为准** |
| **`person_id` 与 `name` 双写不一致** | 代码部分路径写 `name`、部分写 `person_id`，可能出现 `person_id` 指向 A 而 `name` 是 B | ① S4 统一写入口径；② B-5-4 持续巡检；③ 应用层约定：**改名时同步 `UPDATE ... SET name = ? WHERE person_id = ?`**（这是 P1 的最终修复形态，属于 S5 之后的代码改动） |
| **唯一索引导致开号失败** | ⑤ 启用后，"同一主播两个登录账号"会直接报 `Duplicate entry` | 与 012 一样：**存量有冲突就跳过建索引**，不阻断部署；代码侧把 `Duplicate entry` 翻成中文文案（注册路径 `store.rs:1090-1097` 已做，后台建号路径 `store.rs:627` 待补） |
| **`person_deleted_at` 无人回填** | 只加列不加代码 = 标记永远是 NULL，孤儿照旧 | 列本身无害；S6 补 `admin.rs` 三处软删的级联回填，B-3 定时扫描兜底 |
| **孤儿清理误删** | 直接 `DELETE` 凭证/账号不可逆 | 设计上**不做自动删除**，只写 `identity_orphan_log` 供人工确认；`bot_token` 的处理建议是"清空 token 字段"而非删行 |
| **回滚后重跑不生效** | `schema_migrations` 里 015 还在，重跑会跳过 | 回滚时**必须同时** `DELETE FROM schema_migrations WHERE version = '015_identity_unify'`（见 6.4） |
| **迁移白名单单测** | 若往 015 里塞裸 `UPDATE`，`migrate.rs:144` 单测失败、CI 红 | 已按此约束设计：015 纯 DDL，数据动作全在附录 B |

### 实测中发现并已修正的两个设计问题

1. **B-1/B-2 不能加 `p.deleted_at IS NULL`**。最初版本为"只回填在职主播"，实测结果是：
   已经离职的主播回填不上 `person_id`，B-3 的孤儿扫描（判据是 `person_id > 0 AND p.deleted_at IS NOT NULL`）
   就永远探测不到它们 —— **离职主播的 bot 凭证会一直静默残留**，恰恰是 P3 要防的事。
   已改为"回填阶段只管能不能对上人，在职与否交给 B-3 的级联标记判断"。
2. **B-5-4 的一致性校验要区分三种 issue**。回填接错人（`name_mismatch`）是**必须拦下的 G3 闸门**，
   而 `person_deleted` 是预期内的孤儿，不该混为一谈导致误判为"回填失败"。
   已改成带 `issue` 分类的查询，并注明"只想要 G3 闸门时去掉 `p.deleted_at IS NOT NULL` 条件再跑"。
