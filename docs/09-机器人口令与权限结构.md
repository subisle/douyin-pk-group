# 09 · 机器人口令与权限结构

> 定位：定义 QQ / 微信群机器人（`pk-server` 的 `bot/` 模块）的**角色分层、命令口径与推送开关语义**。
> 2026-10-10 起机器人从「仅管理员」改为三层：未绑定会话静默 → 已绑定主播 5 条用户命令 → 管理员全部命令。
> **2026-10-18 用户口径**：普通用户主命令改成**数字 1–4**（1 每日榜单 / 2 个人榜单 / 3 徒弟榜单 / 4 追分榜单）
> + 帮助 + 两个推送开关；旧中文名（每日报告 / 个人报告）保留为**别名**。微信对接改为**扫码即对接**
> （4 位对接码降为可选兜底），对接欢迎语改版（见 §5.5）。
>
> **实现状态**：命令的单一事实来源是代码注册表 `rust/crates/pk-server/src/bot/commands.rs`
> （2026-10-10 引入，分层随该改动落地；合入前线上仍是「仅管理员」）。本文与代码冲突时以代码为准，
> 并回头修订本文。**提权口令不落明文**（见代码常量 `WECHAT_ADMIN_CODE`；沿用 docs/08 的敏感信息要求）。

## 1. 角色模型与判定优先级

### 1.1 三个角色

| 角色 | 判定条件 | 可用范围 |
| --- | --- | --- |
| **未绑定访客** | 微信私聊，且 `push_bindings.conversation_id` 未命中 | 除绑定 / 解绑流程必须的回复外**完全静默**：帮助、未知命令、管理员命令、附件一律不回复，只在日志与 `bot_sessions` 留痕 |
| **普通用户** | 微信私聊，且 `push_bindings.conversation_id` 命中（已完成推送对接的主播，见 §5） | 数字 `1`–`4` + `帮助` + 暂停 / 开启接收每日推送（§3；2026-10-18 前为 5 条中文命令）；发管理员命令 → 拒绝并提示发「帮助」；发附件 → 提示导入是管理员功能 |
| **管理员** | ① QQ 全部会话（群聊 / 私聊，**免白名单**）② 微信白名单 `BOT_WECHAT_ADMINS` ③ `bot_sessions.is_admin`（内置提权口令 / 管理端会话列表勾选） | 用户命令（`1`–`4` / 帮助 / 两个推送开关）之外的全部管理员命令（§4） |

### 1.2 渠道差异

| 渠道 / 会话 | 行为 |
| --- | --- |
| QQ（全部会话） | 一律按管理员处理，没有绑定概念 |
| 微信私聊 | 对接 / 解绑 + 用户命令（`1`–`4` / `帮助` / 两个推送开关）+ 提权口令 + 白名单；未绑定静默 |
| 微信群 | 不做绑定（绑定只对私聊生效）；非白名单群消息静默；白名单命中的群 = 管理员 |
| 展示端网页 | 不属于本文；对接码（可选兜底）与推送开关在「我的」页生成 / 保存（见 docs/08 §4.5） |

> 1.0.1：微信 iLink 传输层全链路对齐 Tencent/openclaw-weixin 协议（扫码状态机、
> 验证码、baseurl 切换、-14 暂停重试）。**命令、角色、判定顺序不变**——协议细节见 docs/07 §3.5.1。

### 1.3 单条消息判定顺序（每次入站固定执行）

1. **会话登记**：所有渠道（含非管理员）写入 `bot_sessions`，管理端会话列表据此展示、勾选管理员；
2. **限流**：10 条/分钟/会话（`BOT_RATE_LIMIT`，对所有渠道、绑定尝试与管理员都生效），超限直接回
   「消息太频繁了，稍后再试（限流 10 条/分钟）」；
3. **微信私聊对接 / 解绑**（§5：**主路径是扫码即对接**，4 位对接码为可选兜底，见 §5.1）：命中即返回，不再往下走；
4. **微信内置提权口令**：私聊整条消息精确命中口令 → `bot_sessions.is_admin=1`，回「已成为管理员」；
5. **管理员判定**：QQ 全部会话 ∥ `BOT_WECHAT_ADMINS` ∥ `bot_sessions.is_admin`；
6. **非管理员分流**：命中 `push_bindings` → 普通用户命令集；未命中 → 静默（不回复）。

## 3. 普通用户命令（数字 `1`–`4` + 帮助 + 两个推送开关）

### 3.2 返回内容、数据口径与边界

| 命令 | 返回内容 | 数据口径 | 失败 / 边界提示 |
| --- | --- | --- | --- |
| 1 · 每日榜单 | 当天音浪榜 TOP10 + 我的名次 | 复用每日推送同一套文案与排序（`push.rs`）；手工查询不受「同一业务日只推一次」的去重限制（去重只管主动推送） | 当天无数据 → 明确提示；本人未开播 → 名次行按未开播展示；数据库不可用 → 「稍后再试」类文案 |
| 2 · 个人榜单 | 我的今日名次 / 音浪、本月累计与名次、追分目标进度 | 月榜按**本月累计**；追分进度与推送同源（`my_targets`，最多 5 个目标，本月累计口径），追名次比的是名次不是音浪 | 本月还没播 → 按未开播文案（追名次场景：「你还没进本月榜 · 本月还没开播」）；没设目标 → 引导去展示端「我的」页「追分设置」添加 |
| 3 · 徒弟榜单 | 名下徒弟的本月榜单（各自本月累计与名次） | 只列**直系徒弟**（`master_id` 指向本人），月榜按本月累计；与「师门日报」「族谱」同一套月口径 | 还没收徒 → 提示「暂未收徒」；徒弟本月未开播 → 按未开播展示；数据库不可用 → 「稍后再试」类文案 |
| 4 · 追分榜单 | 我在追的人排第几、还差多少 | 与追分提醒同源（`my_targets`，追人 ≤5 个，本月累计口径）；比名次与音浪差，不是绝对值 | 没设追分目标 → 引导去展示端「我的」页「追分设置」添加；目标人本月未开播 → 按未开播展示 |
| 暂停接收每日推送 | 关闭后的确认回执 | **只关** `push_bindings.daily_report`；`notify_target`（追分提醒）不受影响 | 重复暂停 → 幂等回执（当前已是关闭）；未绑定会话不可达（静默） |
| 开启接收每日推送 | 打开后的确认回执 | **只开** `push_bindings.daily_report`；与展示端「我的」页开关写同一字段 | 重复开启 → 幂等回执；未绑定会话不可达（静默） |
| 帮助 | 按角色显示可用命令 | 普通用户：`1`–`4` + 帮助 + 两个推送开关（共 7 条）；管理员：全部命令（§4） | 未绑定会话静默（连帮助也不回） |

## 4. 管理员命令表（沿用现状）

| 命令 | 功能简述 |
| --- | --- |
| `状态` | 数据新鲜度、最新业务日、有效日期数、在册主播数、写库连接状态 |
| `分组` | 当前已上架分组方案（分组、时段、名单口径） |
| `总榜` | 累计音浪榜 |
| `排行 [N]` | 近 N 日音浪榜，默认 10（取值收在 1~100） |
| `查询 <主播名>` | 查某人数据（走姓名归一 / 别名匹配） |
| `导出 今日\|YYYY-MM-DD\|总榜` | 导出指定口径，回 CSV 文本 |
| `日报 [男团\|女团] [日期]` | 指定团别 / 日期的日报文案。时长与展示端同一条 `x时x分` 格式（`push::fmt_minutes`，2026-10-16 用户口径「机器人推送的也改」）；时长 0（按日不导时长）时该行只显示音浪，不拼「0分」 |
| `缺数据` | 当日无数据 / 未开播清单 |
| `导入 [男团\|女团] [日期]` + 数据行 | 文本导入；只有需要按团校验时才带团别；与 HTTP 端同一套 `commit_import`（幂等 merge） |
| 纯日期黏住（如发「10.1」） | 先记下业务日期，之后发的 CSV 都按它入库；再发一个日期可改 |
| 直接发 CSV 附件 | 不分男女团，团别按主播档案逐行归属；含**只有时长列**的月度文件（文件名带月份 → 按 `MonthMetrics::MINUTES_ONLY` 导 `monthly_duration`）。时长 + 音浪同表的概览列表（`10.14….csv` 这类，既可能是按日快照也可能是月报）机器判不出来，一律走按日导入；要按月导整月音浪请到管理端「数据导入 → 按月导入」勾选（2026-10-16） |
| 附件的业务日期（2026-10-12 明确） | 四档优先级：**本条消息里带的日期 > 之前贴住的日期（12h 内）> 文件名里的日期 > 收到日 − 1**。最后一档是兜底：抖音后台半夜才出前一天的数据，所以「11 号收到的文件就是 10 号的数据」（`pick_biz_date` / `prev_biz_date`，纯函数有单测） |
| 同日期重复导入 | **覆盖**（不是求和、也不是新增一行）：同一主播同一天只有一条 `daily_metric` 行，第二次导入的值直接替换第一次（PG 上是 `ON CONFLICT DO UPDATE`）；值完全相同时算「未变更」（`WriteOutcome::Unchanged`），不写库。（2026-10-14：原 `bot_e2e::same_date_reimport_overwrites_value` 属 MySQL 方言、从未真正跑过 PG，已随 e2e 清理删除；覆盖语义由 `commit_import` 实现保证，暂无自动测试） |

## 5. 绑定 / 解绑流程

### 5.1 主路径：扫码即对接（2026-10-18 起；4 位对接码为可选兜底）

> 口径沿革：2026-10-10 发手机号绑定 → 同日审计 P1-1 改二要素（手机号 + 6 位码）→
> 2026-10-11 改用户自助扫码登录（多账号）→ 2026-10-16 回归「扫码加好友 + 4 位数字绑定码」单要素 →
> **2026-10-18 再改「扫码即对接」**：扫码确认后服务端已按账号名存好凭证，用**同一个微信给机器人发
> 任意一条消息**即自动完成绑定（`ilink_user_id` 校验本人）；**4 位对接码不再是必需品**（旧文档 / 旧文案
> 叫「4 位绑定码」，同一物；展示端现称「对接码」），降级为可选兜底（扫码异常 / 换号时可发码）。
> 历史扫码用户不受影响（见 §5.3 口令凭据表与下文「扫码入口的存续」）。

**2026-10-19 起主路径 = 打开页面自动出码、截屏即对接**（展示端「我的」页 →「消息设置」→「微信对接」）：

1. 进入「微信对接」子页即自动调用 `POST /my/push/wechat/start` 取二维码，不再要求先点按钮；
   用户截屏保存本页，用要收推送的微信「扫一扫 → 相册」识别 → 手机上点确认；
2. 页面每 2 秒轮询 `POST /my/push/wechat/poll`；扫码确认后**服务端已按账号名把凭证存好**
   （`wx_push_accounts`：`ilink_user_id` / `bot_token` / `baseurl`），`confirmed` 即对接完成
   （页面进「✓ 已对接（昵称）」）；
3. 之后用**同一个微信给机器人发任意一条消息**即自动完成绑定：服务端拿入站会话的 `ilink_user_id`
   与扫码凭证比对，**确认是本人**就把私聊会话接到 `push_bindings`（推送自此生效）；
4. 机器人回**对接欢迎语**（文案构成见 §5.5），**不再要求发 4 位对接码**。

**4 位对接码 = 可选兜底**（扫码异常 / 换微信号 / 老用户习惯）：

1. 同一次 `start` 响应会顺带生成 **4 位数字**（30 分钟一次性）；展示端只在
   「扫码遇到问题？」折叠区显示，不再单独请求 `POST /my/push/code`；
2. 在微信里把这 4 位数字发给机器人（裸数字即可，带关键词 `绑定` / `bind` / `bd` 也行；
   旧写法「绑定 手机号 码」仍被解析，但起作用的只有码）；
3. 机器人按码找到账号，把私聊会话接到 `push_bindings`（码用掉即清）→ 回对接欢迎语。

安全口径：

- 4 位只有 10^4 种取值，**必须一个活码只挂一个账号**，否则 `WHERE bind_code = ?` 会把微信
  绑到别人的账号上。双保险：写入侧 `store::push_rotate_code` 先查后写、撞号重摇；
  库侧迁移 `028_push_bind_code_unique` 给 `push_bindings(bind_code) WHERE bind_code <> ''`
  建部分唯一索引兜并发竞态。
- 裸 4 位数字**没对上码时静默**（正常聊天里出现 4 位数不该被回「绑定失败」）；
  带「绑定」关键词却没对上才回失败文案，文案统一、不区分码错还是过期。
- 绑定成功回复 = **对接欢迎语**（§5.5）：2026-10-16 前按 P1-1 审计要求**不带姓名**（防截图外传），
  2026-10-16 用户口径改为**带账号姓名**（主播一眼确认绑对了号）；限流（10 条/分钟/会话）前置在绑定分支之前。
- **扫码即对接不经过码空间**：只认「扫码凭证里的 `ilink_user_id` = 入站会话的本人」，不存在试码问题；
  上面两条（活码唯一、失败计数 / 会话锁、限流）随 4 位码兜底路径继续生效。

**推送通道**：扫码即对接的账号有自己的账号级凭证（`wx_push_accounts` 有行，走该账号 token 推送）；
**纯 4 位码兜底**没有账号级扫码凭证（`wx_push_accounts` 无行），推送统一走
`push.rs::send_binding` 的管理员全局机器人通道（`WxTransport::send_proactive`，
需要最后一次私聊入站留下的 `context_token`）。

**扫码入口的存续（2026-10-19 复核）**：官方 openclaw-weixin 扫码入口 2026-10-16 曾在展示端**收起**
（页面不再渲染，后端 `/my/push/wechat/start` + `/poll` 保留给历史用户）；**2026-10-18 起恢复为主路径**。
2026-10-19 起进入「微信对接」子页**自动取码**并展示二维码 + 折叠的 4 位对接码，2 秒轮询状态；
二维码页临时隐藏全屏手机号水印，避免水印压在二维码上影响相册识别。历史扫码用户（`scanBound`）
走「只差发一条消息激活」分支，不用重新扫码。

解绑：微信里发「解绑」，或展示端「我的」页「解除绑定」。

**协议对齐（2026-10-16 复核）**：客户端按**当前 npm 发布版 `@tencent-weixin/openclaw-weixin@2.4.10`**
实现（`bot/weixin.rs` 文件头），不是网上流传的 1.0.2 分析文（那份文档里 `get_bot_qrcode` 还是裸 GET；
2.4.10 已改成 `POST get_bot_qrcode?bot_type=3` + `{local_token_list:[…]}`，我们与之一致）。同一份源码里
核到的三条口径也逐条对齐：`iLink-App-Id: bot` + `iLink-App-ClientVersion`（`0x00MMNNPP` 打包 2.4.10）、
POST 必带 `AuthorizationType: ilink_bot_token` + `X-WECHAT-UIN`、`base_info.channel_version = 2.4.10`；
扫码状态机含 `wait/scaned/confirmed/expired/need_verifycode/verify_code_blocked/scaned_but_redirect/
binded_redirect`，其中 `binded_redirect`（该微信已连过本机器人）按官方语义**视作已连接**、
不再卡在「等待确认」。

**2026-10-16 修复：「二维码绑定有问题」的根因**（迁移 `027_weixin_conversation_len`）：

- iLink 会话 key 形如 `wxacct:{bot_id}:{user_id}`，实测 **65 字符**
  （`wxacct:9558d8586108@im.bot:o9cq808v597xaUoY0c-VHGRBHoDk@im.wechat`）；
  而 `wx_sessions` / `push_bindings` / `bot_sessions` 的 `conversation_id` 是 `VARCHAR(64)`：
  `wx_sessions` 报 `value too long for type character varying(64)`（推送永远取不到 `context_token`），
  `push_bindings` 的写入是 `let _ =`（静默）→ 展示端**永远显示未绑定**、一遍遍让用户重新扫码。
  三列统一放宽到 191（与 `wx_push_accounts.conversation_id` 对齐）。
- 连带修掉一个「不再自愈」的逻辑洞：激活判定原先用 `wx_push_accounts.conversation_id` 是否为空，
  而那列更宽、先写成功 → 一旦 `push_bindings` 那次写失败，`first_message` 永远是 false，
  激活分支再也不跑。现在判定改成 **`push_bindings.conversation_id == 本会话`**
  （`store::push_binding_conversation`），本人消息只要还没接上就重跑一次幂等激活。
- 「待激活」也改成问真正要用的那张表：`wx_sessions` 里有没有 `context_token`
  （原来问 `wx_push_accounts.conversation_id`，同样是列宽差异造成的假信号）。
- `push_bind_account` 写失败不再静默（记 warn + 会话 key 长度），团别非法显式拒绝（原先 `.bind(None)`
  会落 NULL 撞 NOT NULL，同样被静默吞掉）。
- 回归：`rust/crates/pk-server/tests/wx_binding_e2e.rs`（真库、`--ignored` 显式跑）用 65 字符 key
  验证两条写入口 + `push_state.bound` 变 true + 幂等 + 清理。

### 5.4 展示端账号的「可看团别」（view_team，2026-10-15）

> 迁移 `024_my_view_team`：`my_accounts.view_team VARCHAR(8) NOT NULL DEFAULT ''`。
> 代码单一事实来源：`store/my_account.rs` 的 `ViewTeam`（`token_team()` / `switchable()` 有单测钉死）。

管理员观看账号原先只有 `is_admin` 一个开关，登录后固定「任意团」，没法按团收敛。
`view_team` 把**数据可见范围**拆出来（与 `is_admin` 的「不绑主播也能登录」互补）：

| 存库值 | 语义 | 登录后 token 团别 | 页内可切团 |
|---|---|---|---|
| `''`（默认） | 沿用旧口径：绑了主播按主播所在团；没绑 / is_admin 按任意团 | base（旧行为，一字不改） | 否 |
| `any` | **全团账号**：男女团都能看 | 空串（两团放行） | **是**（全团/男团/女团三胶囊） |
| `male` | 钉死男团（不受改绑影响） | `male` | 否 |
| `female` | 钉死女团（不受改绑影响） | `female` | 否 |

**要点：**

- 钉死团别的优先级**高于绑定关系**：`view_team=female` 的账号即使后来被改绑到男团主播，
  登录拿到的仍是女团 token（`ViewTeam::token_team` 无视 base 里的绑定团）；
- 前端只在 `switchable=true`（即 `any`）时渲染换团条 —— 钉死某团的账号**压根没有入口**，
  不是「显示但点了报错」；后端 `gate_team` 仍按 token 团别在每个数据接口复核，前端藏只是体验；
- **改范围走专用端点 `PUT /api/admin/my-accounts/{name}/view-team {viewTeam}`**（只改团别、不动密码）。
  为什么不复用 `POST /api/admin/my-accounts`：那个端点不传 `pass` 时会**自动生成新密码**
  （手机号后四位）——「只想把饭团改成女团」会顺手把她的密码重置掉，运营当场转达不出去；
  该端点仍支持传 `viewTeam`，但**不带字段 = 保持原值**（常规改密/改手机号不会清掉可见范围）；
- 后台入口：机器人页「我的页面账号」列表**管理员账号行**带「可看团别」下拉（普通主播账号
  显示「按绑定主播」，不给下拉——改了会和台账不一致）；主播台账右键「我的页面账号」弹窗
  在管理员账号上也有同一下拉；
- 非法值由 `normalize_view_team` 收敛成 `''`；改动后回读复核，写不进去直接报错（不假成功）；
- 改 `view_team` / 改密 / 改绑都会吊销该账号全部 my token（旧 token 里挂着旧团别，不吊销等于没改）；
- 列不存在（没跑迁移）或值非法时一律回落 `Inherit`：退回旧行为，**绝不让账号因为一列脏值登不进去**；
- **`/my*` 系列的团别门（2026-10-16 修「我的页登录死循环」）**：`my_team_allows()` 一行口径 ——
  路径团别 `all` 恒放行；**token 团别为空 = 「团别待定 / 可看全团」，放行任何路径团别**；
  其余必须与 token 团别一致。`view_team=any` 的账号登录下发 `team=""`，而前端会套用
  「上次选的视角」（`localStorage.myViewTeam`，如男团）去请求 `/api/public/teams/male/my/*`；
  旧写法 `my_team != team && team != "all"` 把空团别判成「该账号不属于本团」→ 401 →
  前端按「登录态失效」清 token 弹登录门 → 登录成功又 reload → **无限死循环**。
  7 处（`minutes.rs` ×4 / `binds.rs` ×2 / `wx.rs` ×1）已统一走 `my_team_allows`，
  族谱那条（`site.rs`）原本就带 `!my_team.is_empty()`，一并复用同一函数。
  安全性不变：`/my*` 的数据一律只按 token 里的 `person_id` 取，路径里的团别只是授权校验；
  钉死某团的账号（如饭团=female）依旧不能访问别的团。

## 6. 推送开关语义（daily_report vs notify_target）

| 开关 | 落库字段 | 默认 | 打开后 | 关闭后 |
| --- | --- | --- | --- | --- |
| 每日报告 | `push_bindings.daily_report` | 关 | 每个业务日收 1 条「当天 TOP10 + 我的名次」 | 机器人「暂停接收每日推送」只关这个 |

## 7. 推送触发与去重口径

- **触发**：数据入库后延迟 `PUSH_DELAY_MINUTES`（默认 30；0 = 入库即推）统一推送，等一轮导入的几个文件都到齐，避免推半成品榜单；
- **每日报告去重**：同一业务日只推一次（`push_bindings.last_report_date`），补数据重排队列时不会重复推；
- **追分提醒**：与每日报告同轮合成一条消息（「🚀 已追上 / ⚠️ 又差回来 / · 距 X 还差 N」）；
- **后台可见**：机器人页「推送队列」（团别 / 业务日 / 计划推送时间 / 状态 + 「立即推送」按钮）；
- **失败兜底**：微信 iLink 只有被动回复形态，主动推送依赖最后一次私聊留下的 `context_token`；
  推送失败会把原因写回绑定记录，并在「我的」页提示「让对方给机器人发一条消息后再试」。

| 边界 | 口径 |
