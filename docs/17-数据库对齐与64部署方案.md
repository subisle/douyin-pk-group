# 17 · 数据库对齐与 64 Docker 持久化部署方案

> 版本 v1 · 2026-10-12 · 设计稿（只写方案，未实施）
> **决策变更**：生产部署目标从 147（systemd + MariaDB）改为 **64（64.188.8.149，Docker 持久化）**，
> 数据库统一 PostgreSQL 17，**新增 Redis 7**（缓存/锁层）。147 的生产数据已于 2026-10-12 全量合并进
> 本机 PG `douyin_dev`（逐表逐值对账一致，见 docs/16 §2.5），147 转为「数据已收割的历史生产」，

## 0. 一句话结论

**本机 PG `douyin_dev` 是唯一事实源；64 用 Docker 跑 `pk-postgres + pk-redis + pk-server` 成为新生产；
业务数据（Class A）本机→64 推送，运行时数据（Class B）64→本机回拉，config 按键拆分（Class C）；
Redis 只放可丢的派生数据，宕机自动回落内存缓存 + 直查 PG，服务零降级。**

```
              ┌────────────────── 本机 Mac mini（开发 / 运营） ──────────────────┐

              └──────┬────────────────────────────────────────▲─────────────────┘
                     │ push: Class A（分类 upsert 灌入 64）    │ pull: Class B（回拉刷新开发库）
                     ▼                                        │
┌────────────────────┴────────── 64 服务器 /opt/pk-group（Docker）─┴──────────────────────┐
│  Caddy 2.6.2（宿主 systemd，公网 80/443，已有 8 站点并站）                                │
│      └─ pk.subisle.cc  /s/* 展示端(短缓存)  /admin 管理端(no-store)                       │
│                                                                                          │
│  docker compose（pk-net 内网）                                                            │
│   ├─ pk-server  ghcr.io/subisle/douyin-pk-group  ← 只绑 127.0.0.1:6666→8787              │
│   ├─ pk-postgres  postgres:17-alpine  ← ./data/pg 持久化（唯一事实数据）                  │
│   └─ pk-redis     redis:7-alpine      ← ./data/redis 持久化（AOF，可丢的派生数据）        │
│                                                                                          │
│  备份：pg_dump cron → /opt/pk-group/backups/pg → rsync 离机回本机 Mac                     │
└──────────────────────────────────────────────────────────────────────────────────────────┘
                     ▲
                     │ P5：同套镜像 + compose（arm64 变体）
              rk3318（192.168.5.12 内网）
```

**四条分层原则**

1. **事实在 PG，派生在 Redis**——任何业务表数据只存 PG；Redis 只放缓存/锁/去重
2. **公网只见 Caddy**——PG / Redis / pk-server 端口不跨出宿主回环或 docker 内网
3. **一个方向一条命令**——push / pull 各一个脚本，不做双向同步器
4. **迁移只走 runner**——schema 变更 = 新增 `0XX_*.sql` + `pk-server migrate`，禁止手改 schema

| # | 决策 | 理由 | 否决的替代方案 |
|---|---|---|---|
| D1 | 生产 = 64 Docker 持久化 | 用户拍板；容器化便于备份/迁移/回滚 | 147 systemd 续用（用户明确不走） |
| D2 | Redis 开 AOF 持久化（`appendonly yes` + `everysec`）+ `requirepass` | 重启后缓存/锁不冷启动、避免抖动；AOF 成本极低 | 纯内存（重启全丢，冷启动抖动）；**注：子代理曾建议 appendonly no，本稿按 D2 定稿** |
| D3 | Redis 不发布宿主端口 | 宿主 6379 已被 systemd redis 占用；且无外部访问需求 | 映射 6380（无收益，扩大暴露面） |
| D4 | 表分类对齐（A/B/C）替代整库替换 | 旧「整库替换」会冲掉 64 上的线上账号/绑定/日志 | 继续整库替换（丢数据，否决） |
| D5 | Redis 停机自动降级 | 缓存是加速器不是依赖；最小化故障面 | 强依赖 Redis（无收益，否决） |
| D6 | 备份离机回本机 Mac（rsync） | 本机已有 PG 可随时演练恢复，无需再引入云凭据 | 只存 64 本机（单点，否决） |
| D7 | 64 备份保留 7 份（非 14） | 磁盘仅余 8.9G，先保安全余量 | 保留 14 份（磁盘风险） |

### 5.3 首次迁移链路（本机 PG → 64 PG）

```bash
# 1) 本机导出（-Fc；不含角色，角色在 64 侧重建成与本机一致的模型）
/opt/homebrew/opt/postgresql@17/bin/pg_dump -h 127.0.0.1 -p 3318 -U zmy -d douyin_dev \
  -Fc -Z 6 -f .dbmerge/douyin_dev-$(date +%Y%m%d).dump

# 2) scp 到 64（直连；如走代理加 -o ProxyCommand=...）
scp .dbmerge/douyin_dev-*.dump root@64.188.8.149:/opt/pk-group/

# 3) 64 侧起 PG 并恢复
cd /opt/pk-group/deploy && docker compose up -d pk-postgres
docker exec -i pk-postgres pg_restore -U douyin_dev -d douyin_dev \
  --no-owner --role=douyin_dev < /opt/pk-group/douyin_dev-*.dump

# 4) 角色引导（固化为 scripts/deploy/bootstrap-roles-64.sh，对齐本机 §2.1 权限模型）
#    pk_writer(owner) / pk_reader(只读) / pk_backup；owner 移交 + 默认 ACL + 回收 reader 的 CREATE
docker exec -i pk-postgres psql -U douyin_dev -d douyin_dev < bootstrap-roles-64.sql

# 5) 迁移登记（18 版本应为 no-op，验证 schema_migrations 一致）
docker exec pk-server /usr/local/bin/pk-server migrate

# 6) 对账（§5.5）+ 序列检查
docker exec -i pk-postgres psql -U douyin_dev -d douyin_dev -Atc \
  "SELECT sequencename, last_value FROM pg_sequences WHERE schemaname='public' ORDER BY 1"
```

`bootstrap-roles-64.sql` 要点（与本机实查权限一一对应）：建 `pk_writer`/`pk_reader`/`pk_backup` 角色 →
`REVOKE ALL ON SCHEMA public FROM PUBLIC` → 授 SELECT（reader）/ CRUD（writer）→ 表/序列/函数
`OWNER TO pk_writer` → `ALTER DEFAULT PRIVILEGES` 4 条 → `REVOKE CREATE ON SCHEMA public FROM pk_reader`。

### 5.4 日常对齐机制

**push（Class A 本机→64）：分类合并，不整库替换**

| 维度 | 整库替换（旧模式） | 分类合并（采用） |
|---|---|---|
| Class B 表 | 被本机旧行覆盖 → **丢线上账号/绑定/日志** | 不在 push 集内，零风险 |
| `schema_migrations` | 需停机重放 | 不动 |
| 窗口 | 需独占维护窗口 | 无需窗口，逐表 upsert |
| 代价 | 回滚=再灌一次 | 需处理删除语义（人工确认，不自动删） |

- **主键稳定性**：`person`/`account` 主键是显式 BIGINT（种子导入带显式 id），本机→64 搬运不漂移；
  `daily_metric` 主键 `(person_id, biz_date)`；外键均指向 `person_id`，
  故 push 顺序 = `person → account → daily_metric / import_* → plans / aliases / roster_state`。
- **形态**：`pg_dump --data-only --table=...` → 64 侧落 `tmp_*` 影子表 → 事务内逐表 upsert
  （`ON CONFLICT (id) DO UPDATE SET ...`，列清单由 `information_schema` 生成，避免手抄列名）。
  `account` 有 phone 唯一索引（012/016），灌 tmp 表前先内部去重。
- **删除语义**：本机删了、64 还在的行用反连接列出 → **人工确认后处理**，不自动删（FK 风险）。
- **序列复位（必做）**：upsert 保留显式 id，**不会推进 64 端 identity 序列**；push 收尾必须
  `setval(pg_get_serial_sequence('<表>','id'), max(id), true)` 遍历所有带 identity 的表。
- **不参与 push**：`sqlite_carried`、`__e2e_cfg__`。

**pull（Class B 64→本机，刷新开发库）**

```bash
docker exec pk-postgres pg_dump -U douyin_dev -d douyin_dev --data-only --column-inserts \
  -t access_logs -t my_accounts -t my_bind_requests -t my_targets -t bot_sessions \
  -t wx_push_accounts -t wx_sessions -t push_bindings -t push_jobs \
  -t ip_geo_cache -t ip_allowlist -t anchor_claims > b-$(date +%F).sql
scripts/backup/backup-pg.sh && psql ... -f b-*.sql   # 先备份再灌，本机被覆盖的仅是运行时数据
```

**时区**：两端会话 `Asia/Shanghai`；`timestamptz` 存 UTC 绝对值，搬运不漂移。唯一要盯的是 varchar 型
时间列（如 `created_at VARCHAR(40)` 存北京时间字面量）——字节级搬运、两端显示一致即可。脚本内要改时区
只用 `SET SESSION`，不要 `ALTER DATABASE` 污染 64 端默认值。

### 5.5 对账校验设计（`scripts/dbcheck`）

形态：**行数 + 关键列 md5 校验和**，两端各跑一次 diff，输出 `table|rows|md5`。关键列选值稳定、
非自增、非时间戳的列（避开 3 个 `touch_updated_at` 触发器造成的假差异）。

```sql
-- person（pk=id）
SELECT count(*)::text || '|' || coalesce(md5(string_agg(h, '' ORDER BY id)), 'EMPTY') FROM (
  SELECT id, md5(concat_ws('|', name, gender, master_id::text, generation,
         coalesce(group_name,''), coalesce(phone,''), status)) AS h FROM person) s;

-- daily_metric（pk=person_id,biz_date；注意列名是 minutes，不是 live_minutes）
SELECT count(*)::text || '|' || coalesce(md5(string_agg(h, '' ORDER BY person_id, biz_date)), 'EMPTY') FROM (
  SELECT person_id, biz_date, md5(concat_ws('|', person_id::text, biz_date::text,
         wave::text, minutes::text)) AS h FROM daily_metric) s;

-- account（pk=id）：person_id, anchor_id, douyin_no, anchor_name, is_primary
-- config（pk=cfg_key）：cfg_value；按 §5.2 拆分，运行时键（wechat_*）跳过
```

`scripts/dbcheck/dbcheck.sh <local|remote> <classA|classB|all>`：每表列清单放同目录 `dbcheck.sql`，
避免内联转义出错；diff 为空即通过。

### 6.2 docker-compose.yml（草案）

```yaml

services:
  pk-postgres:
    image: postgres:17-alpine
    container_name: pk-postgres
    restart: unless-stopped
    environment:
      POSTGRES_DB: douyin_dev
      POSTGRES_USER: douyin_dev
      POSTGRES_PASSWORD: ${PG_PASSWORD:?PG_PASSWORD 必填}
      TZ: Asia/Shanghai
      PGTZ: Asia/Shanghai
    command:
      - postgres
      - -c
      - max_connections=40
      - -c
      - shared_buffers=128MB
      - -c
      - log_min_duration_statement=500
    volumes:
      - ./data/pg:/var/lib/postgresql/data
      - ./backups/pg:/backup
    networks: [pk-net]
    mem_limit: 768m
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U douyin_dev -d douyin_dev"]
      interval: 15s
      timeout: 5s
      retries: 5

  pk-redis:
    image: redis:7-alpine
    container_name: pk-redis
    restart: unless-stopped
    command:
      - redis-server
      - --requirepass
      - ${REDIS_PASSWORD:?REDIS_PASSWORD 必填}
      - --appendonly
      - "yes"                 # D2：AOF 持久化
      - --appendfsync
      - everysec
      - --maxmemory
      - 256mb
      - --maxmemory-policy
      - allkeys-lru
    environment:
      TZ: Asia/Shanghai
      REDIS_PASSWORD: ${REDIS_PASSWORD:?REDIS_PASSWORD 必填}   # healthcheck 需要
    volumes:
      - ./data/redis:/data
    networks: [pk-net]
```

## 7. Redis 集成设计

### 7.1 现状盘点（现在数据存哪）

| 数据 | 现存位置 | 热点 |
|---|---|---|
| 音浪缓存（dates/waves/anchors/series） | 进程内存 `WaveCache`（state.rs:31-40/79），TTL=`WAVE_CACHE_TTL`（config.rs:135-137），读写 repos.rs；失效靠 `st.clear_cache()`（state.rs:110，触发点 repos.rs:336、admin.rs:1552/2097/2701/2834、routes.rs:300） | ✅ 最热 |
| IP 地理 | PG 表 `ip_geo_cache`（001_core.sql:169），读写 ipinfo.rs:497/531，TTL 7 天 | ✅ 热点（每次门禁查询打一次 PG） |
| 推送任务 | PG `push_jobs`，抢占 `push_job_take`（store/push_jobs.rs:42），循环 push.rs:194 | 非热点，但**多实例抢占无显式锁** |
| 机器人会话 | 持久在 PG `bot_sessions` + store/wx_sessions.rs；临时态在进程内（bot/mod.rs:154/779、限流器 :116、wxpush.rs:213） | 临时态可丢 |
| 管理员 token/ticket | 进程内存（auth.rs:82-85） | 重启即失效，可接受 |

### 7.2 接入原则

- Redis **只放可丢的派生数据**：缓存、锁、去重标记。
- **一律不放**：`push_jobs`、`push_bindings`、`bot_sessions`、`my_accounts`/`my_targets`、`anchor_claims`、
  `import_batch`/`import_pending`、`access_logs`、`ip_allowlist`、`monthly_duration` 等全部业务事实表。
- **宕机语义**：`REDIS_URL` 未配置或连接失败 → 缓存层返回 `None`，调用方静默回落现有内存 `WaveCache` + 直查 PG，
  打一条带指数退避的 `warn`；**不允许任何路径把 Redis 错误冒泡成 5xx**。停 Redis 时服务行为与引入前完全一致。

### 7.3 分阶段接入

| 阶段 | 内容 |
|---|---|
| **P0**（随首次部署） | compose 起 `pk-redis`；连接池选型 **deadpool-redis**（与 sqlx 池化心智一致、故障即降级入口；本项目低 QPS 无需 ConnectionManager 的单连接/pipeline 优势）；`/api/health` 加 `redis: "up"\|"down"\|"disabled"`（PING，500ms 超时，down 不影响整体 health） |
| **P1** | 音浪缓存迁移：读序 内存→Redis→PG，写序 PG→Redis(带 TTL)→内存；`clear_cache()` 内部追加 `DEL pk:cache:wave:*`（跨进程失效，为将来多实例铺路） |
| **P2** | `ip_geo` 热点缓存（Redis TTL 24h < PG 7 天，PG 仍是事实层；每 100 次输出命中率日志）+ 推送去重锁 `pk:lock:push:{job_id}`（`SET NX EX 300`，拿不到跳过本轮；Redis down 时沿用现有 DB 抢占语义） |
| **P3** | 观察项：机器人 pending 状态（bot/mod.rs:154/779）是否迁移；多实例部署时再评估 |

### 7.4 键空间设计

| 键 | TTL | 值 |
|---|---|---|
| `pk:cache:wave:dates:{source}` | `WAVE_CACHE_TTL`（600s） | JSON（DateInfo） |
| `pk:cache:wave:map:{source}:{metric}:{days}` | 同上 | JSON（HashMap<String,f64>） |
| `pk:cache:wave:anchors:{source}` | 同上 | JSON（Vec<AnchorBrief>） |
| `pk:cache:wave:series:{source}:{days}` | 同上 | JSON（WaveSeries） |
| `pk:cache:ipgeo:{ip}` | 86400s | JSON（IpGeo） |
| `pk:lock:push:{job_id}` | 300s | 空串（存在性） |

统一前缀 `pk:`；序列化统一 `serde_json`（复用现有派生），不引 msgpack/protobuf。

## 8. 安全 · 备份 · 回滚 · 上线阶段

### 8.1 安全基线

| 端口 | 绑定 | 说明 |
|---|---|---|
| 443/80 | Caddy（宿主） | 唯一公网入口（64 上已有 8 站点并站） |
| 6666→8787 | 127.0.0.1 | pk-server，仅 Caddy 反代 |
| 5432 | docker 内网 | pk-postgres，**不发布宿主端口** |
| 6379 | docker 内网 | pk-redis，**不发布宿主端口**（宿主 6379 已被 systemd redis 占用） |

- 验收：`ss -tlnp | grep -v 127.0.0.1` 除 Caddy 外不得有非回环监听。
- 机密：`deploy/.env` `chmod 600`；仓库零机密（口令一律环境变量注入）；定期 `git ls-files | grep -i env` 确认未入库。
- 防火墙：ufw `default deny incoming` + 放行 22/80/443；**Docker 会绕过 ufw 直写 iptables**，故端口只绑回环是第二层兜底，两层都要做。
- `ADMIN_PASSWORD` fail-closed；轮换 = 改 `.env` → `docker compose up -d --force-recreate pk-server`（PG 卷不动，零数据风险）；轮换后立即只读冒烟验证新口令生效、旧口令 401。
- `IP_GATE_DISABLED` 仅临时排障用，事后必须关回。

### 8.2 备份体系

| 对象 | 方式 | 保留 |
|---|---|---|
| PG | 64 上 cron 每日 03:17 调 `scripts/backup/backup-pg-64.sh`（改造：走 `docker exec pk-postgres pg_dump -Fc -Z 6`，输出 `/opt/pk-group/backups/pg`，**保留 7 份**；dump 后 `pg_restore -l` 验证可读，失败即 cron 非零退出） | 7 份 |
| Redis | 每日 `BGREWRITEAOF` 后把 AOF 拷到 `backups/redis/`（体积小，直接拷文件；恢复=停容器→替换 AOF→起容器）。缓存层，优先级低于 PG | 7 份 |
| 离机 | 本机 Mac 每日 04:30 `rsync -az` 拉回 `~/backups/64/{pg,redis}`，本机侧同策略清理 | 7 份 |
| 灌库前 | **强制目标机备份**（沿用 P1-19 模式）：任何 DROP/灌库脚本开头先 `pg_dump` 到 `backups/pg/pre-restore-<ts>.dump`，失败立即中止 | — |

### 8.3 回滚预案

**镜像回滚**（两条路，均离线可用）
- ghcr：`docker pull ghcr.io/subisle/douyin-pk-group:<上一版 sha>` → 改 `PK_IMAGE_TAG` → `docker compose up -d --force-recreate pk-server`
- 离线包：`gh workflow run amd64-bundle.yml --ref <上一版 commit>` → 下载 → `scp` → `docker load` → compose 回退；
  64 上 `/opt/pk-group/images/` 常驻最近 3 版 tar，回滚零 CI 依赖

**数据回滚**

```bash
docker compose stop pk-server                                   # 1 停写（PG 不动）
docker exec pk-postgres pg_dump -U douyin_dev -Fc douyin_dev \
  > backups/pg/rollback-evidence-$(date +%Y%m%d-%H%M%S).dump    # 2 坏状态留证
docker exec pk-postgres dropdb -U douyin_dev --if-exists douyin_dev
docker exec pk-postgres createdb -U douyin_dev douyin_dev
cat backups/pg/<目标>.dump | docker exec -i pk-postgres pg_restore \
  -U douyin_dev -d douyin_dev --no-owner --role=douyin_dev       # 3 恢复
docker compose start pk-server && curl -fsS http://127.0.0.1:6666/api/health   # 4 起服对账
```

⚠️ **镜像与数据回滚必须成对**：回滚旧 dump 后要用**旧版本镜像**启动，否则新镜像的 `migrate` 会在旧 schema 上补登记版本。

**compose 回退**：变更前 `cp docker-compose.yml{,.bak-$(date +%F)}`；回退 = 恢复文件 + `up -d --force-recreate`。Caddyfile 同理（`caddy validate` 后再 `reload`）。

### 8.4 上线阶段计划

| 阶段 | 动作 | 验收门禁 | 失败处置 |
|---|---|---|---|
