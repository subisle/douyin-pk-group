# 统一产品与系统架构基线

> 本文是项目当前唯一的产品与系统架构基线。模块 PRD、旧融合方案或部署说明与本文冲突时，以本文为准；有新决策时先更新本文，再同步接口、代码和部署文档。
> 本文刻意区分「目标架构」与「当前实现」，避免把路线图写成现状。

## 1. 产品目标

把主播数据管理、PK 分组、对外榜单和管理员机器人收敛为一个本地可部署系统：

- 管理员在一个后台维护主播、导入/核对数据、生成 PK 分组并发布内容。
- 主播和观众通过公开链接查看数据榜、个人数据和 PK 赛程；不开放粉丝机器人命令（2026-10-10 起机器人分层：已绑定主播可用 5 条个人命令，见 docs/09）。
- 主业务数据以 RK3318 本地 MariaDB（库 `douyin`）为最终事实源；旧 sqlpub 数据源已停用（2026-10-09 单库决策，见下文 §4）。
- 分组算法只有 Rust `pk-core` 一份权威实现。
- 最终生产形态为一个 Rust `pk-server`、一个管理/展示 Web SPA、MariaDB（唯一事实源，运行时表已并入）和宿主机 Caddy；Go API 常驻服务（douyin-server）**已于 2026-10 删除**。
- **运行环境（2026-10-11 更新）**：生产两处 —— 147（`147.90.235.187`，Debian 12 x86_64 / systemd，`https://pk.subisle.com`）与 RK3318 盒子（aarch64 / Debian trixie / Docker，arm64 生产）；115 开发机（x86_64 / CentOS 7 / Docker）只作开发与验收。不部署到其他任何服务器；CI 产物覆盖 arm64（RK3318）与 amd64（147 / 115）两个目标。

### 容量与非功能目标（2026-10-04）

按「100 人同时查看展示页」设计。评估结论：Rust axum + 进程内读缓存 + 简单索引查询在该硬件上余量 20 倍以上，架构成立。硬指标：

| 项 | 目标 |
|---|---|
| 并发展示读者 | ≥ 100 人同时在线；榜单发布后 30 秒内 100 人集中打开不降级 |
| 公开接口延迟 | 缓存命中 P95 < 50ms；未命中 P95 < 300ms |
| 刷新节奏 | 展示端每分钟静默刷新，客户端加 ±10s 随机抖动，避免整点同步请求形成尖峰 |
| 导出 | 单次 CSV/Excel（全团 ≤ 100 行）服务端 < 1s；服务端并发导出上限 10，超出排队而非拒答；长图导出在浏览器端完成，服务器零负担 |
| 机器人 | 命令路由纯规则 + 缓存数据，单条处理 < 100ms；按会话限流（默认 10 条/分钟），渠道 SDK 自身限流为准 |
| 连接池 | MariaDB 读池 ≤ 10、写池 ≤ 4；并发用户数不等于并发数据库连接 |
| 静态资源 | SPA hash 文件名 + gzip + 长缓存，首屏传输 < 500KB |
| 公网可达 | RK3318 为内网设备，部署阶段 F 必须实测端口映射/内网穿透与 TLS 路径的稳定性 |

机器人分层边界（2026-10-10，见 docs/09）：未绑定会话静默、已绑定主播 5 条用户命令、管理员全部；上表「100 人」指展示页读者。若要开放粉丝 QQ 查榜，属范围变更，须先修订 docs/06、docs/08 并补充只读命令白名单与会话限流设计。

### 对外展示信息架构（目标）

- `/st/m`：男团公开站点；`/st/f`：女团公开站点。链接本身决定团别，不提供页内团别切换。
- 两个站点均按后台开关展示每日、每月、每年音浪与直播时长、涨跌对照、个人页和 PK 分组；关闭的数据由后端不下发。
- 「我的」通过抖音号验证身份。客户端只保存不含原始抖音号的身份凭证；公开 API 不返回抖音号、全量候选名单或可枚举的关联信息。
- `/s/:planId` 保留为单个已发布 PK 方案的分享链接；`/st` 保留为兼容旧固定公告短链，在迁移期指向默认公开内容。
- 团链接关闭时返回统一的「暂未公布」状态，不泄露该团是否存在数据。

## 3. 目标系统架构

```text
手机 / 桌面浏览器
        │ 同源 HTTPS
        ▼
宿主机 Caddy（TLS、反向代理、访问日志；早期文档写的 Nginx 已换成 Caddy）
        │
        ▼
Rust pk-server（唯一常驻应用服务）
  ├─ auth       管理员会话、机器人凭据和限流边界
  ├─ admin      数据概况、主播台账、设置
  ├─ import     文件/文本解析、预览、校验、提交与批次审计
  ├─ collect    受控采集任务和采集状态（后续阶段）
  ├─ grouping   HTTP 编排；算法调用 pk-core
  ├─ public     男团/女团榜单、个人视图、已发布方案的字段裁剪
  ├─ bot        QQ/微信适配器与确定性命令路由，不调用模型
  ├─ repository MariaDB/MySQL 的持久化边界
  └─ static     统一 Web SPA 静态资源
        ├─ MariaDB(douyin)：主播、账号、日/月指标、采集与导入批次
        └─ MySQL 业务库：方案快照、别名、名单草稿及少量本地配置（2026-10-10 单库化并入）
```

`admin`、`import`、`collect`、`bot` 是目标模块边界；当前 Rust 仓库中尚未全部实现。禁止为每个功能再次拆成独立常驻应用服务。确需外部执行任务时，先作为 `pk-server` 的受控任务/适配器设计，并证明单进程不可行后再评审。

## 4. 数据归属与安全边界

### MariaDB：业务事实源

核心实体：

```text
person          主播档案、团别、状态、师傅/队长关联
account         抖音账号；抖音号为敏感字段，后台写、受控验证查询
daily_metric    按主播和业务日期记录音浪、累计值、直播状态/时长及可靠性
monthly_metric  月度聚合指标
monthly_duration 月度时长导入（平台月报：一人一月一行的整月开播有效时长）
wave_snapshot   账号级音浪观测，用于补充副号数据
duration_snapshot 账号级直播时长观测
import_batch    导入来源、业务日期、团别、行数和结果审计
```

**时长口径（2026-10-10 用户口径：「每日不能导入时长，只有月时长」）**：抖音公会后台只导得出
**整月**开播有效时长（`9月份时长.csv` 的「开播有效时长」= 75小时29分钟41秒），每日文件里没有时长。
所以按日导入**不写** `daily_metric.minutes`，时长统一由「时长（按月）」导入落 `monthly_duration`；
展示端月榜 / 年榜 / 个人月卡的时长**优先用整月值**，某月没有整月记录（历史月份）才回落到
`daily_metric` 求和，日榜与每日明细不受影响。整月值「相同不覆盖、不同才覆盖」，与音浪同一套幂等口径。

音浪口径必须保持显式：`total` 为累计口径；`lastN` 为最近 N 个有效业务日口径；首个基线日不得误算成普通日增量。
**基线日 = 最早那个 `wave_reliable=0` 的累计快照日**（不能用 `MIN(biz_date)`：清空音浪数据后重新开始导入时，
第一天是正常的当日音浪，用 MIN 会把它当基线从趋势图/导出里剔掉）。**导入行的取舍（2026-10-10）**：
文件同时给「当日音浪」和「累计音浪」→ 以当日音浪为准（累计只留作次日差分快照）；只给累计才做差分；
**同一天重复导入时，值完全相同的行不覆盖**（报告里报「未覆盖 N 行」），值变了才覆盖。一人多号按已验证规则合并：主号采用 `daily_metric`，副号仅累加有快照的当日音浪，不从缺失快照推算差分。任何源字段口径变化都先补数据证据和回归测试，再改查询。

**单库决策（2026-10-09）**：MySQL（本机 `douyin_dev`）是**唯一**业务事实源，不再从远程源库（sqlpub douyinxs）同步——`sync.rs` 模块、`/api/admin/roster/sync`、`/api/admin/metrics/sync`、QQ 机器人「同步主播」命令均已删除。日常数据变更只发生在这一个库（导入、台账编辑、师徒登记都在管理端完成）；上线部署时把该库**整体 dump 上传**到生产机（147 用 `scripts/deploy/upload-db-vps147.sh`，dump → scp → 恢复进生产 MariaDB），生产不配置 `DB_A_*` 远程源。`DB_SRC_*` / `DB_A_*` 环境变量不再有同步用途。

### SQLite → 并入 MySQL（2026-10-10 单库化）

运行时状态表（`aliases` / `plans` / `roster_state` / `config` / `bot_sessions` /
`my_accounts` / `anchor_claims`）已从本地 SQLite **整体并入 MySQL 业务库**
（migrations/003_runtime.sql），与业务事实源同库——部署时 `upload-db` 一次带全，
生产不再单独维护运行时数据。旧 SQLite 文件只作为一次性搬家来源：
`pk-server migrate` 把其中数据幂等搬进 MySQL（`config.sqlite_carried=1` 后跳过），
文件保留不删。列名差异：`config.key→cfg_key`、`roster_state.text→body`
（方言/保留字）；`payload` 用 MEDIUMTEXT、截图用 MEDIUMBLOB。

补充（2026-10-09）：`push_bindings` / `my_targets` / `wx_sessions` 三张表由
`migrations/004_push.sql` 新建，承载「我的」页个人微信推送（绑定关系、追分目标、
私聊会话上下文）。**新增迁移文件必须手动登记进 `migrate.rs` 的 `MIGRATIONS` 数组**
（它是硬编码列表，不扫目录）。

### 账号权限

| 身份 | 最小权限 | 责任 |
|---|---|---|
| `pk_reader` | `SELECT` | 分组匹配、榜单、个人公开数据查询 |
| `douyin_writer` | 指定业务表 `SELECT/INSERT/UPDATE/DELETE` | 主播档案、导入、采集结果写入；**永远不持有 DDL 权限** |
| `douyin_migrator` | 受控 DDL + 业务表写 | 仅显式迁移窗口使用（见下） |

**Migration 执行方式（2026-10-04 决策，经 TypeSafe 判断确认）**：采用独立的 `douyin_migrator`
账号 + `pk-server` 内置显式 `migrate` 子命令（或等价 env 开关，默认关闭）。`pk-server`
日常启动**不执行任何 DDL**；DDL 只在管理员显式触发迁移时经 `douyin_migrator` 连接执行。
不采用「writer 持 DDL + 启动自动迁移」（业务写账号持 DDL 违反最小权限，启动自动 DDL
在断电重启频繁的盒子上风险偏高）。

Rust 端读写连接池分离。读查询使用固定 SQL/参数化查询和表字段白名单；导入先预览、校验、幂等提交，并记录批次。公网 API 采用 DTO 白名单，不能直接序列化数据库实体。

## 6. 数据主流程

```text
主播档案/团别确认
   → 每日数据导入或受控采集
   → 预览与业务规则校验
   → MariaDB 事务写入 + import_batch 审计
   → 清理相关缓存
   → 后台数据榜 / PK 分组读取
   → 管理员审核并保存方案到 MySQL 业务库（单库化）
   → 配置团别和模块显隐并发布
   → 公开 API 按团别、开关和隐私策略裁剪响应
```

采集失败不能覆盖已有可信值；同一团别/日期重复导入必须明确选择拒绝、替换或幂等合并策略。月/年和涨跌指标应由后端定义统计窗口、时区和缺失值语义，不让前端各自推导。

## 8. 统一实施顺序与验收门槛

| 阶段 | 工作范围 | 必须验收后才进入下一阶段 |
|---|---|---|
| A. 基线统一 | 以本文统一产品词汇、实体、路由和状态；整理 OpenAPI；确认现有数据迁移清单 | 文档之间无相互冲突；接口标注真实状态；现有线上 `/s`、`/st` 行为不变 |
| B. 数据与 API 闭环 | Rust 迁移 runner、写池、主播/团别管理、导入预览/提交/审计 | 本地 MariaDB 与旧源抽样一致；重复导入安全；读写权限实测隔离；备份可恢复 |
| C. 管理端统一 | `apps/douyin-web` 实现数据、主播、导入、PK、设置；复用 `pk-core` 服务 API | 六类工作流同一 SPA 完成；关键表单、空态、移动端通过验收；旧 PK 页面功能无回归 |
| D. 公开端扩展 | `/st/m`、`/st/f`、日期口径、个人验证、时长、涨跌与后端显隐 | 两团数据隔离；抖音号不可枚举/外泄；关闭模块时响应中无该类数据 |
| E. 机器人与采集 | 管理员绑定、QQ/微信适配器、文件导入/导出；评估 DouyinLang 采集 | 未授权消息不能触发读写（普通用户仅只读 / 开关命令，分层见 docs/09）；回调验签、重放防护、限流、文件限制和审计通过 |
| F. 单体部署切换 | Caddy → 单一 Rust `pk-server`；MariaDB 单库持久化（运行时表已并入）；下线 Go 服务 | `/`、`/api`、`/s`、`/st/m`、`/st/f` 健康；回滚演练通过；监控、备份和权限核验完成 |

每阶段先补契约和测试，再实现 UI/API；数据库迁移先备份、校验行数与关键汇总，禁止通过删除卷或重建库来“解决”迁移失败。

## 9. 统一术语与决策规则

- 「徒弟提成」（2026-10-11 拍板，1.0.1；**已下线 2026-10-11，d30a13a**）：**直系徒弟**（`person.master_id = 本人`，徒孙不计）的可信音浪合计 ÷ 折算比例 = 人民币金额，默认 10 音浪 = 1 元；比例与排除名单（鹏先生等不参与统计的师傅）存 `config.commission_settings`，后台可改、即时生效、**不追溯**；只有有直系徒弟的人可见提成卡；排除名单内师傅一律不下发。**下线说明**：曾上线（1.0.1），Stitch 改版（2026-10-11，d30a13a）时随展示端重写下线，代码已移除（前后端/路由全量删除），产品确认不再恢复（2026-10-11 审计确认）；以上为历史口径，仅供追溯。是主播所属的 `male` 或 `female` 团；公开端两个独立链接，不是筛选控件。
- 「音浪口径」统一为 `total`、`lastN` 或明确的单日日期，不混用累计值和日增量。
- 「赛事类型」（2026-10-06 拍板，2026-10-09 定名）：PK 分组分五类——**初级争霸赛小组赛**（月初）、**中级争霸赛小组赛**（月中）、**月终争霸赛**（月末）、**初级争霸赛晋级赛** / **中级争霸赛晋级赛**（晚上）。核心差异是参赛名单；开赛时间每场自定义（第一组开赛时间 + 组间隔，方案自带）。各类共用同一套分组策略与内置约束。类型值用中文字符串直接落库，Rust `store::EVENT_TYPES` 是唯一白名单，白名单外的值落空串（= 未分类，老方案兼容）；改名前的老值（初级/中级争霸赛/月底争霸赛/初级晋级赛/中级晋级赛/晋级赛）由 `store::LEGACY_EVENT_RENAMES` 在启动迁移里原地改名，读路径再归一兜一层。
- 「复活赛」（2026-10-09 拍板）：**只打一场 20 分钟**，落在「上半程最后一组」之后，即第 `ceil(组数/2)` 组比完接着打——8 个组 / 7 个组落第 4 组后，6 个组落第 3 组后。复活赛不需要程序分组，运营手动排；排期上按 20 分钟占位（初级/中级争霸赛小组赛固定，不可改）。月终争霸赛与两级晋级赛没有复活赛，沿用第 3 组后的可调加长休息。
- 「上架互斥」（2026-10-06 拍板）：展示端同一时刻只显示一场比赛的分组；新方案上架时，其它已上架方案由后端自动下架。
- 「当前实现」只由代码、契约测试和部署验证证明；PRD 中的描述不能作为实现证据。
- 「机器人」按角色分层（docs/09）：未绑定会话静默、已绑定主播 5 条用户命令、管理员全部；不支持粉丝群查榜，不调用生成式模型执行命令或写库。
- 架构变更先改本文和 ADR，再改 API 契约与实现；淘汰兼容路由前，须有迁移观测和回滚方案。
