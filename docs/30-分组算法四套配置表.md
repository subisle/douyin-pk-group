# 30 · 分组算法四套配置表

> 2026-11-08 用户口径：**分组是一套算法 + 四套配置**。
> 归类：`初级争霸赛小组赛 + 中级争霸赛小组赛` = A 套；`两级晋级赛` = B 套；
> `月终争霸赛前两天` = C 套；`月终争霸赛最后一天` = D 套（按前两天成绩重排）。
>
> 本文只定义配置与规则，**不改代码、不部署**。当前系统现状与本文的差异见第 6 节。

## 1. 结论速览

| 套 | 覆盖赛事 | 一句话区别 |
|---|---|---|
| A | 初级争霸赛小组赛 / 中级争霸赛小组赛 | 库里近 3 天音浪，蛇形均衡，12:15 开赛，带一场 20 分钟复活赛 |
| B | 初级争霸赛晋级赛 / 中级争霸赛晋级赛 | 名单自带分数，每组 ≥6 人反推组数，**08:15 开赛**，**无复活赛、无 20 分休息**，全程每组 +15 分 |
| C | 月终争霸赛 第 1、2 天 | 库里音浪（近 7 天），每天单独分一次组，08:15 开赛，**不插 20 分休息**，全程每组 +15 分 |
| D | 月终争霸赛 第 3 天（最后一天） | **按前两天累计成绩重排名单/分数**，其余参数同 C 套（同样不插休息） |

**一套引擎**：四套共用 `pk-core/src/group.rs::auto_group`，差异只体现在参数，
不各写一份算法。切换赛事 / 天数时自动套用对应 profile；载入历史方案时，方案里的旧值覆盖 profile 默认值。

## 2. 共用：算法引擎与硬条件

```
auto_group：
  抽出固定位的人 → 其余人按 strategy 分组 → 固定位插回指定组
  → 修互斥 → 修最小间隔 → 均衡微调（梯队式跳过）→ 强度位次（梯队式跳过）
```

**内置条件永远优先**，共 13 条，四套默认全部生效（2026-11-08 实测本地 8787 与
`rust/crates/pk-core/src/constraints.rs::ConstraintSet::default()` 一致）：

| 类别 | 条数 | 内容 |
|---|---|---|
| 固定位 pinned | 7 | 啸泽→末组、啸阳→G1、啸帆→G2、浩森→G1、浩泽→末组、浩龙→G3、玖玉→G3 |
| 互斥 excludeTogether | 2 组（展开 4 对） | 玖玉/玖妹/玖玥两两不同组；狼影≠浩冬 |
| 最小间隔 minGap | 3 | 啸昭–啸寻≥4 组、浩森–浩泽≥3、狼佑–玖安≥3 |
| 最低组号 minGroup | 1 | 浩阳≥第 6 组 |

名单里不存在的人自动跳过，不算违规。`constraints.full` 是**整包替换**，
任何一次覆盖都要把 13 条抄全，否则会丢条件。

注 1：前端 `strengthMode` 默认值是 `top`，但 2026-11-07 用户明确要求「去掉头牌，按必要条件分组」，
本表按 `off` 记；若最终以产品默认 `top` 为准，需改此行。
注 2：用户 2026-11-08 口径「**不显示『头牌』这个名字即可**」——理解为分组逻辑照旧
（`top`，全场前 8 名一人一组），但**导出图 / 页面不出现"头牌"字样或徽标**，
赛制文案里「每组一个最强：全场前 8 名一人一组当头牌」建议改写为不含该词的表述。
注 3：服务端把浩龙、玖玉都钉在 G3；B 套若两人同时进入前 8，与「前 8 名一人一组」直接冲突，见 §6。
注 4：2026-11-08 用户最终口径「**晋级赛和月终都没有休息的 20 分钟**」——
**B（初级 / 中级晋级赛）、C、D 套一律不插加长休息**（`longBreak=0`），时间轴连续每组 +15 分钟；
只有 A 小组赛的 20 分钟复活赛保留。中途「中级没有休息 20 分钟」只是过渡口径，以本条为准：
**所有晋级赛（含初级）和月终全部取消该休息**。
2026-11-08 的 41 人分组图已按本条重出，去掉第 3 组后的休息块。
注 5：2026-11-08 用户口径「**小组赛才有 20 分钟的复活赛**」——系统里有两种 20 分钟，别混：
  1. **小组赛**（初级 **和中级** 争霸赛小组赛）：上半程最后一组（`ceil(组数/2)`）之后的
     20 分钟是**复活赛**，是一场真比赛，运营手动排、程序不分组，固定不可改；**晋级赛没有复活赛**。
  2. **晋级赛 / 月终争霸赛**：产品里原本有「第 3 组后加长休息 20 分」这个可配置项（不是比赛），
     但用户明确**不用**，B / C / D 套一律 `longBreak=0`，时间轴连续 +15 分。
注 6：2026-11-08 用户强调「**811 图片里有音浪**」——B 套的分数来源是
**811 结算图中各人晋级那一场的音浪**（每格名次旁的数字），**不是库里的日音浪 / 月累计音浪**。
11-08 当天音浪尚未导入，别改用库里数据；一度误取 `last1`（11-07 日音浪）的版本已作废。

## 8. 功能增量：拖拽即存 / 前端同步 / 展示端倒计时与锁定

> 2026-11-08 用户追加：「后端支持手动拖动名片进行分组，拖动完立即保存；
> 然后前端同步显示；然后展示端显示分组倒计时，倒计时结束就不能加入和去除了」。
> 本节仍只定义方案，未改代码。

### 8.1 现状：三个必须先绕开的坑

1. **`store::save_plan` 只有 INSERT，没有 UPDATE**：每点一次「保存方案」就新建一条方案
   （历史里 #14~#23 一堆同标题方案就是这么来的）。拖拽即存若继续走 `POST /api/plans`，
   拖一次生成一条，几分钟就能把方案表刷爆。**必须先加「原地更新当前方案」的接口。**
2. **展板 `BoardPage` 的拖拽不落库**：拖拽代码从 GroupPage 原样搬来，注释明写
   「展板的数据不落库（没有保存方案）」，结果只在内存，刷新即丢，还挂着离开页面确认。
3. **SSE 已有，但通道没打通**：后端 `events.rs` 在方案保存/上架/删除时广播 `SCOPE_PLANS`；
   管理端 `GroupPage` 订阅了 `['plans']`，但只用来刷方案列表、**不刷当前看板**；
   展板 `BoardPage` 完全没订阅；展示端 `/api/public/events` 目前**只转发 `SCOPE_IMPORT`**，
   分组变更推不到主播手机。所以「前端同步显示」不需要新建 WebSocket，改造现有 SSE 即可。

### 8.2 目标链路

```
拖拽落下（管理端 / 展板）
  → applyGroups() 先本地更新（不阻塞手感）
  → 防抖 300ms → PATCH /api/plans/{id}/groups { buckets, revision }
  → 后端：校验 revision + 未过锁定期 → UPDATE payload → events::emit(plans)
  → 各前端 SSE 收到 → 重拉 /api/plans/{id} → 覆盖本地 buckets
      （自己那次提交按 revision 跳过，避免回写抖动）
```

「立即保存」= 无感自动保存，不弹确认、不点按钮；但用**防抖 + 乐观锁**，
否则一次拖动发十几个请求，多端同时拖会互相覆盖。

### 8.3 接口设计（新增）

| 项 | 内容 |
|---|---|
| `PATCH /api/plans/{id}/groups` | body `{ buckets: [{name, players}], revision }`；只替换 `payload.buckets`，title / metric / schedule / display 不动 |
| 后端写入 | 读旧 payload → 换 buckets → `UPDATE plans SET payload=? WHERE id=?`；`payload.revision` 每次 +1 |
| 冲突 | 请求 revision 与库里不符 → `409 { reason:"stale", revision:最新值 }`，前端重拉后再试 |
| 锁定 | `now >= lockAt` → `423 { reason:"locked" }` |
| 响应 | `{ ok, id, revision, savedAt }` |
| 广播 | `events::emit(SCOPE_PLANS, "方案 {id} 分组已更新")` |
| 展示端 SSE | `public_sse` 增加转发 `SCOPE_PLANS`，**只带 scope / at / id**，不带后台 detail 与业务数字（保持现有脱敏口径） |

重拉仍用现有 `GET /api/plans/{id}`，不新增读接口。

### 8.4 倒计时与锁定

- 方案 payload 新增 `lockAt`（ISO 时刻，分组锁定时间）。展示端「分组」页顶部显示
  `距离分组锁定 mm:ss`，每秒刷新；到点显示「分组已锁定」，并切成只读态。
- **锁定必须后端强制**：写接口（`PATCH /api/plans/{id}/groups`、加人/移人走同一入口，
  以及保存/删除方案）在 `now >= lockAt` 时一律拒绝；前端只做按钮置灰 + 禁用拖拽，
  不能只靠前端拦。
- 「加入 / 去除」对应管理端现有的 `addPerson()`（加入该组）与 `removeCard()`（移出到未分组），
  外加跨组拖拽；到点后这三类写操作全部拒绝。展示端本身没有加人/移人按钮，只负责显示倒计时。

## 10. 赛事日历与冻结时刻（2026-11-08 定案）

### 10.1 手动设置赛事日期

用户口径：赛事日期**手动设置**，不写死按日历自动推算。默认模板：

| 日期 | 赛事 | 套 | 开赛 |
|---|---|---|---|
| 每月 8 日 | 初级争霸赛小组赛 + 晋级赛 | A + B | 12:15 / **08:15** |
| 每月 18 日 | 中级争霸赛小组赛 + 晋级赛 | A + B | 12:15 / **08:15** |
| 月底最后 3 天 | 月终争霸赛（每天单独分一次组） | C / C / D | 每天 08:15 |

即 8 日、18 日各要**两份方案**（A 套 12:15 + B 套 08:15），各有一个 `lockAt`；
月底三天各一份方案，第 3 天用 D 套按前两天成绩重排。

> ⚠ **时间顺序待用户确认**：晋级赛 08:15 早于小组赛 12:15，若排在同一天不合逻辑，
> 很可能是**次日 08:15**（8 日中午打小组赛、9 日早上打晋级赛）。
> 冻结仍按「各自赛事日前一天 17:00」计算，不影响本节结论；日期落到代码前需定一句。

### 10.2 冻结时刻（2026-11-08 用户拍板）

**用户口径：8 号开始比赛 → 7 号下午 5 点（17:00）冻结。上一轮建议的「开赛前 90 / 120 分钟」作废。**

推广成规则：**每个赛事日的前一天 17:00 冻结**——运营下班前定稿，主播有一整晚确认，
第二天不用在开赛前赶工。

| 赛事 | 比赛日 · 开赛 | **冻结 = 倒计时归零** | 距开赛 |
|---|---|---|---|
| 初级争霸赛小组赛 | 8 日 12:15 | **7 日 17:00** | 19 小时 15 分 |
| 初级争霸赛晋级赛 | 8 日 **08:15** | **7 日 17:00** | 15 小时 15 分 |
| 中级争霸赛小组赛 | 18 日 12:15 | **17 日 17:00** | 19 小时 15 分 |
| 中级争霸赛晋级赛 | 18 日 **08:15** | **17 日 17:00** | 15 小时 15 分 |
| 月终第 1 天 | 月底倒数第 3 天 08:15 | 前一天 17:00 | 15 小时 15 分 |
| 月终第 2 天 | 月底倒数第 2 天 08:15 | 前一天 17:00 | 15 小时 15 分 |
| 月终第 3 天（D 套） | 月底最后一天 08:15 | 前一天 17:00 | 15 小时 15 分 |

**✅ 晋级赛名单来源已明确（2026-11-08 用户：「晋级赛名单我会发给你」）**：
B 套名单**不**从「当天中午小组赛晋级者 + 复活者」自动生成，而是**由用户 / 运营手动提供**
（与 §3 的 `scoreSource = roster-score`、`名字 分数` 格式一致；发截图则由我 OCR 成名单）。
因此 7 日 17:00 冻结时晋级赛名单已在手，**A 套与 B 套同一时刻一起冻结**：
不需要分级冻结，也不存在「锁名单还是锁分组」的歧义，
`freezeScope` 直接定为 `groups`（连分组结果一起锁，不能再加入 / 移出 / 拖动）。

实现影响：

- B 套名单录入走现有「名单与配置」文本框，**不做**「从小组成绩自动算晋级者」的功能；
- 一份名单 = 一份 B 套方案：名单发来 → 按 B 套分 8 组 → 7 日 17:00 前上架并锁定；
- 若名单在冻结之后才到，只能走「管理员强制解锁」（§10.3 仍待确认）。

**为什么前一天 17:00 站得住**

- 运营在下班前把分组定稿，不用第二天开赛前赶；
- 主播有一整晚在展示端确认自己第几组、几点开赛，异议当天下午就处理完；
- 音浪口径本来就是「最近 3 天」，前一天下午冻结时用的只能是再往前三天的数据
  （2026-11-07 实测：11-06 未入库，实际取 11-03~11-05），不会因为等当天数据而卡住；
- 月底 D 套按前两天成绩重排：倒数第 2 天 08:15 开赛、约 10:30 打完，当天 17:00 冻结时成绩已齐。

### 10.3 倒计时显示口径

- 展示端倒计时从**方案上架 / 公布**时开始显示，终点是 `lockAt`，不是从当天 00:00 起算
  （否则手机上一打开就是一个几小时的巨大数字，没有意义）。
- 文案：`距离分组冻结 18:23:11` → 归零后 `分组已冻结 · 不能再加入或移出`。
  按用户口径冻结落在**前一天 17:00**，倒计时会跨夜、跨度十几小时，别按「开赛前 90 分钟」设计样式。
- 冻结即 §8.4 的后端 423 校验；前端只做置灰，不参与判定。
- 可选「运营强制解锁」：留一个管理员口令级的开关，供开赛前突发换人时临时重开窗口，
  操作写审计日志。**是否要这个口子仍待用户确认**。

### 10.4 配置结构（落地时用）

```ts
type EventCalendarEntry = {
  monthDay: number | 'month-end-3' | 'month-end-2' | 'month-end-1';  // 手动设置
  eventType: string;
  profile: 'A' | 'B' | 'C' | 'D';
  start: string;            // '12:15'（小组赛）| '08:15'（晋级赛 / 月终）
  /** 冻结规则：默认「赛事日前一天 17:00」，也可直接给绝对时刻 */
  freezeRule: { type: 'previous-day'; at: '17:00' } | { type: 'absolute'; at: string };
  /** 冻结对象：默认 groups（名单由用户提供，连分组结果一起锁）；roster 保留为备用 */
  freezeScope: 'roster' | 'groups';
  /** 第 3 组后加长休息分钟数：B/C/D 一律 0（晋级赛与月终不休息）；仅 A 小组赛用复活赛 20 分 */
  longBreak?: number;
  publishedAt?: string;     // 上架时刻 → 倒计时起点
  lockAt?: string;          // 手动覆盖值，优先于计算值
};
// lockAt = lockAt ?? (赛事日 - 1 天) 17:00（本地时区）
```

默认：所有套别都是 `previous-day / 17:00`；8 日 → 7 日 17:00，18 日 → 17 日 17:00，
月底三天各自前一天 17:00。`freezeScope` 已定默认 `groups`（名单由用户提供，见 §10.2）；
`longBreak` 默认 **0**（晋级赛与月终都不插 20 分休息，注 4）；只有 A 小组赛的复活赛 20 分是固定比赛。
D 套的公布时刻受「前两天成绩何时齐」约束，需人工确认后再上架。
