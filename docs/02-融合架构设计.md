# 02 · 融合架构设计：douyin-data-manager(3328) × 抖音pk分组

> 目标机：RK3328（arm64 盒子，Docker，1–2GB 内存）
> 融合对象：`subisle/douyin-data-manager` 分支 `3328`（Go 后端重写）→ 并入本仓库
> 日期：2026-10-01 · 状态：设计稿，待拍板后按 S0–S5 执行

---

## 0. 三十秒结论

1. **3328 不是要"接进来"的外部系统，而是本项目的数据上游。** 它的 Go 后端建的表
   （`person / account / daily_metric / monthly_metric / wave_snapshot / duration_snapshot /
   tier_rule / import_batch`）与 pk-server 正在读的 douyinxs（dialect A）**几乎逐字段一致**——
   3328 本来就是 douyinxs 的自托管重写。融合的本质是：**数据主权从 sqlpub 云库收回盒子**。
2. **融合后的形态：一个盒子、一个主库、两个服务、一个入口。**
   - Go 服务（douyin-server）：采集 / CSV 导入 / 微信 iLink + QQ 机器人 / 管理后台，**写库**。
   - Rust 服务（pk-server）：分组算法 / 展示页 `/st` / 导出长图，**只读**。
   - MySQL（容器，主数据）：两边共用的唯一事实源。
3. **拿不准的决策不拍脑袋，交给类型系统兜底**（下文第 7 章逐条落地）：
   方言、口径、采集来源、机器人通道、渲染后端，全部收成 enum / trait，
   非法状态在编译期就表达不出来，后续改主意只加 variant，不破坏契约。

## 1. 两边资产盘点

### 1.1 douyin-data-manager @3328（并入方）

| 资产 | 技术 | 融合后的角色 |
|---|---|---|
| `server/`（Go 1.26，cmd/server + internal/*） | chi/gin 风格 HTTP + sqlx + migration | **主数据服务**：主播/账号管理、快照与四类指标、导入批次、机器人、管理 API |
| `web/`（管理前端，构建为静态 dist） | 前端 + Vite 类构建 | 管理后台 UI（挂在 `/dy` 路径下） |
| `electron/`（桌面主进程、微信/QQ bot、RAG） | JS，1.5 万行 | **不随融合部署**；其中 bot 逻辑 3328 已迁入 Go 的迁移范围，桌面壳保留为开发工具 |
| `deploy/3328/`（Dockerfile + compose） | arm64 scratch 镜像 ~25MB | 部署模板，改造后沿用 |
| 硬规则（CLAUDE.md） | 微信 iLink 唯一用户通道、bot 无模型调用 | 继续作为约束写入融合后的文档 |

### 1.2 抖音pk分组（本仓库，接收方）

| 资产 | 技术 | 融合后的角色 |
|---|---|---|
| `rust/crates/pk-core` | 纯函数分组算法（有单测） | 不动，继续作为算法权威 |
| `rust/crates/pk-server` | axum + sqlx + SQLite(方案/别名) | 展示/分组服务，**新增 dialect Local 指向盒子主库** |
| `apps/web` | React + Vite | 展示页 `/st` + 管理三页，不动 |
| `packages/shared` | TS 展示工具 | 不动 |

### 1.3 关键契合点（为什么这次融合成本低）

- **schema 同源**：3328 的 migration 建出的表 = dialect A 的表。pk-server 读本地库
  只需把 `DB_A_*` 指向 `127.0.0.1:3306`，理论上**零代码改动**即可跑通；
  正式做法是加一个显式 `Local` 方言（见 §7.1），把"指向哪个库"变成编译期可查的事实。
- **都已是单二进制 + 静态前端**：Go scratch 镜像、Rust 静态编译、React dist，
  盒子上一个 compose 全拉起来。
- **职责天然切分**：写库的（采集/管理/机器人）和读库的（分组/展示）不交叉，
  唯一共享物是 MySQL —— 集成面最小。

## 2. 目标与非目标

**目标**

1. 单仓库管理两套服务，一次 CI 构建 arm64 镜像，一条 compose 在 RK3328 上拉起全栈。
2. 主数据落地盒子本地 MySQL；sqlpub 的 douyinxs 降级为"历史参考源"（dialect A 保留可切）。
3. pk 展示页 `/st`、分组看板读本地库，数据新鲜度由 3328 的采集/导入链路保证。
4. 微信 iLink / QQ 机器人 7×24 常驻盒子，指令查数据走本地库。
5. 所有"现在拿不准"的架构决策以类型收窄，决策变更 = 加 enum variant / 换 trait 实现，不改调用方。

**非目标**

- 不做多租户、不做 SaaS、不做 WebSocket 实时大盘（3328 设计同样后置）。
- 不重写 DouyinLang 采集协议（继续作为外部数据源通过导入 API 喂数）。
- 不把 Electron 桌面搬上盒子（桌面只做开发/兜底工具）。
- 本次不合并两个前端为一个大前端（见 §7.5 的类型化挂载，先分离后择机合并）。

## 3. 总架构（盒子视角）

```
                        RK3328 盒子 (arm64, Docker)
┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│  采集源                    Go: douyin-server (写库)      Rust: pk-server (只读)
│  ┌──────────────┐   ┌──────────────────────────┐   ┌─────────────────────┐
│  │ DouyinLang   │──▶│ 导入 API（批次状态机）    │   │ /api/group/*        │
│  │ CSV 上传     │   │ 快照差分 → daily/monthly │   │ /api/public/*  /st  │
│  │ 微信 iLink ──┼──▶│ 管理后台 API             │   │ /api/auth|plans|... │
│  │ QQ 机器人    │   │ bot 长连接（iLink + QQ） │   │ 分组算法 pk-core    │
│  └──────────────┘   └───────────┬──────────────┘   └──────────┬──────────┘
│                                 │ 写                            │ 只读（SQL 账号只授 SELECT）
│                                 ▼                               ▼
│                    ┌─────────────────────────────────────────────┐
│                    │        MySQL 8（主库，容器，512M）           │
│                    │  person / account / daily_metric / ...      │
│                    └─────────────────────────────────────────────┘
│
│  caddy（单入口 80）
│    /dy/*        → douyin-server  （管理后台 web + API）
│    /st, /s/*    → pk-server      （展示页）
│    /api/pk/*    → pk-server      （如需前后端分离调用）
└─────────────────────────────────────────────────────────────────────┘
          │
          └── 备份：mysqldump 定时 → 盒子外（sqlpub / 115）每日一份
```

数据流一句话：**采集与导入只有 Go 一个写入方；Rust 与机器人都是读者；分组与展示永远不写业务表。**

## 5. 数据层设计

### 5.1 主库归属与账号权限

| 项 | 决策 |
|---|---|
| 主库 | 盒子容器 MySQL 8，`douyin` 库，migration 由 Go 侧管理（`DY_AUTO_MIGRATE`） |
| Go 账号 | `douyin_writer`：SELECT/INSERT/UPDATE/DELETE + DDL（migration 用） |
| Rust 账号 | `pk_reader`：**仅 SELECT**。pk-server 现有只读守卫（mysql.rs）保留，双保险 |
| 兼容源 | sqlpub douyinxs 保留为 dialect A 配置，用于历史数据核对，不再写入 |
| SQLite | pk-server 本地的方案/别名库不变（它不是业务数据，是 pk 的应用状态） |

### 5.2 指标即表，不再现场算

3328 已把四类一等公民指标物化（`daily_metric` / `monthly_metric` / `yearly_metric` / 时长差分），
pk-server 现在的 WAVES_A/SERIES_A SQL 原样可用。基线日语义（首日是累计快照）
在 3328 里由 `prev_snapshot_date` 正式承载——比 pk-server 现在的 `MIN(biz_date)` 推断更可靠，
切到 Local 方言后按 `prev_snapshot_date IS NULL` 判基线，两条链路语义完全对齐。

## 6. 服务间契约：类型安全的三道锁

1. **结构体即契约**：Go 侧 API 响应结构、Rust 侧 serde 结构，禁止在 handler 里手拼
   `map[string]any` / `json!` 散装字段（pk-server 现有 public.rs 的 json! 要在 S2 重构为
   `#[derive(Serialize)]` 的 typed struct——这是本次融合里 Rust 侧最大的一笔还债）。
2. **生成 TS 类型**：`packages/contract` 从 Go/Rust struct 生成 `.d.ts`，两个前端只 import
   生成物；后端改字段、前端不改编译期直接红。
3. **CI 漂移检查**：PR 跑「重新生成 → git diff --exit-code」，契约漂移的 PR 无法合并。

## 7. 拿不准的决策 → 类型化清单（typsafe 落地）

> 原则：**不确定 = 建一个封闭集合。** 每个当前没有唯一答案的架构问题，都收敛成
> enum / trait，先给一个默认实现跑起来；改主意时加 variant 或换实现，调用方零改动。

### 7.1 数据源方言 → `Dialect` enum（Rust）

```rust
pub enum Dialect {
    /// sqlpub douyinxs（历史参考源，远程）
    A,
    /// userxs（旧 32 人库，已停更）
    B,
    /// 盒子本地主库（3328 Go 管理，融合后的权威源）
    Local,
}
```

- 现状 `source(id)` 的字符串分发改为 enum match，**新增方言必须新增 match 分支，漏了编译不过**。
- Local 首版直接复用 A 的 SQL（schema 同源）；差异出现时（如基线判定改用
  `prev_snapshot_date`）只改 `Local` 分支。

### 7.2 指标口径 → `MetricScope` enum（Rust + Go 各一份，契约包对齐）

```rust
pub enum MetricScope { Daily { date: NaiveDate }, Monthly { period: Period }, Yearly { year: u16 } }
```

杜绝 `metric: &str` 到处传。pk 展示页的 `total/lastN` 保留为展示层口径，
落到查询层时映射到 MetricScope。

### 7.3 采集来源 → `ImportSource` enum（Go）

```go
type ImportSource string
const (
    SourceCSV       ImportSource = "csv"        // 微信/网页传 CSV
    SourceDouyinLang ImportSource = "douyinlang" // 外部采集端推 API
    SourceManual    ImportSource = "manual"     // 管理后台手填
)
```

`import_batch.source` 已有此字段（migration 005），Go 侧收成常量集，
批次状态机（pending → imported → recomputed → failed）用同法收窄，非法迁移编译不过。

### 7.4 机器人通道 → `BotChannel` trait（Go）

```go
type BotChannel interface {
    ID() ChannelID                 // ilink | qq
    SendMedia(ctx, Artifact) error
    Poll(ctx) ([]Inbound, error)
}
```

微信 iLink 与 QQ 各一个实现；3328 设计里"服务器 worker 是否生产化"悬而未决，
trait 化之后桌面端与盒子端可以共存同一套技能，先跑谁不影响业务代码。

### 7.5 前端拓扑 → `RouteMount` 显式配置（caddy Caddyfile 是唯一事实）

```caddyfile
/st, /s/*      → pk-server:8787     # 公告与指定方案
/dy/*          → douyin-server:8080 # 管理后台
/api/pk/*      → pk-server:8787     # pk 前端 API（同源免跨域）
```

"以后要不要合成一个大前端"不预设答案：两个前端各自的 base path 已隔离，
合并不需要动后端路由表——到时只改 caddy 一处。

### 7.6 导出图片渲染 → `Renderer` trait（Go，sidecar）

3328 设计文档的红线是"像素与 615 一致"。渲染后端（headless chromium vs resvg sidecar）
在 1–2GB 盒子上没有定论 → trait 化：

```go
type Renderer interface { RenderPNG(ctx, Template) ([]byte, error) }
```

默认实现 `chromium-sidecar`（保真最高），内存吃紧时切 `resvg-sidecar`，
业务代码零改动。两个 sidecar 都打成独立 arm64 镜像。

## 8. RK3328 部署

### 8.1 全栈 compose（deploy/rk3328/）

| 容器 | 镜像 | 内存上限 | 说明 |
|---|---|---|---|
| mysql | mysql:8.0 | 512M | 主库，数据卷 + 每日 mysqldump 备份 sidecar |
| douyin-server | 本仓构建（Go scratch，~25MB） | 256M | 采集/导入/机器人/管理 API，挂 `/dy` |
| pk-server | 本仓构建（Rust 静态，~15MB） | 128M | 分组/展示，只读账号连 mysql |
| caddy | caddy:2-alpine | 64M | 单入口 80，按 §7.5 路由 |

总计常驻 ~1GB 以内，RK3328（1–2GB）可跑；bot 长连接与定时器都在 douyin-server 里。

### 8.2 构建与发布

- GitHub Actions 单条流水线：`pnpm build 两前端` → `go build arm64` → `cargo build --release --target aarch64`
  （pk-server 用 Dockerfile 多阶段交叉编译，现有 Dockerfile 已验证）→ 两个镜像推 ghcr → 盒子 `docker compose pull && up -d`。
- 盒子在内网不暴露公网；远程查看展示页走 115 反代或内网穿透（沿用现有方案）。
  115 上的 pk-server 继续读 sqlpub（公网访客不进家庭内网），**盒子上跑的是全栈私有版**——
  两套部署共存，数据以盒子为准回灌。

## 10. 风险与开放决策（需用户拍板）

| # | 问题 | 现状倾向 | 类型化兜底 |
|---|---|---|---|
| 1 | RK3328 实机内存/磁盘规格未确认（1GB 还是 2GB？eMMC 容量？） | 按 2GB 设计，MySQL 512M 起 | compose mem_limit 参数化，不够就砍 |
| 2 | 盒子在家庭内网，公网看 `/st` 的路径（115 反代 or 穿透 or 只在内网） | 115 反代读盒子？还是 115 继续读 sqlpub？ | §8.2 已按"两套部署共存"设计，不影响融合 |
| 3 | chromium sidecar 在 1GB 盒子可能跑不动 → 出图保真 vs 内存 | 先 chromium，不行切 resvg | Renderer trait（§7.6） |
| 4 | 3328 的管理前端与 pk 前端最终合不合并 | 先分离 | RouteMount（§7.5） |
| 5 | sqlpub douyinxs 里 9 月的历史数据要不要灌进盒子主库 | 建议灌（否则每日排名只有导入后的数据） | 导入工具走 ImportSource=csv/manual，一次性脚本 |
| 6 | bot 生产化标准（3328 文档标记"实验"） | 按微信 iLink 硬规则直接上盒子跑 | BotChannel trait + 技能确定性，无模型调用 |

## 11. 与现有部署的关系（不变项）

- 115（pk 展示公网入口）、64（生产机）、本地开发流程全部不动；本设计新增的是
  **盒子上的私有全栈**与主数据迁移路线。115 切不切盒子数据源，等 §10.2 拍板后动。
- pk 分组算法、展示页三页签、`/st` 公告短链等已上线行为不受影响。
