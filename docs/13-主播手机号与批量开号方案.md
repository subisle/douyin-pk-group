> 版本 v1 · 2026-10-11 · 设计 + 已落地代码
> 目标库：rk3318 本地 MariaDB（库名 `douyin`，docker 容器内实查）
> 相关文档：docs/00 §4（实体）、docs/07（后端）、docs/08 §4.5（展示端「我的」页）、
> docs/09（机器人绑定）、docs/12（身份统一锚点 person_id，本方案的前置）
> 迁移落地：`rust/crates/pk-server/src/migrations/016_streamer_phone.sql`
> 代码落地：`store.rs`（批量开号核心）/ `admin.rs`（两个接口）/ `dialect.rs`（SQL 模板）/
> `main.rs`（路由）/ `migrate.rs`（登记）/ `apps/douyin-web/src/StreamerPage.tsx`（台账 UI）

**数据库选型：MySQL/MariaDB。** 本方案不评估其它数据库（docs/12 §1 已定，理由：全仓 MySQL 方言 + 生成列）。

---

## 1. 一句话问题

**104 个在职主播里只有 1 个人有登录账号**（鹏先生 / `13354463148`），因为：

1. `person` 表**根本没有存手机号的地方** —— 运营手里有主播手机号，库里没地方放
   （`SHOW COLUMNS FROM person LIKE '%phone%'` 返回空）；
2. 没有批量开号入口 —— 运营只能 `POST /api/admin/my-accounts` 一条条建，104 人逐个点不现实；
3. 开号后还要主播自己扫码绑微信 bot，104 人逐个扫不现实（§4 给解法）。

三件事互相放大：手机号没地方存 → 批量开号没有数据源 → 微信绑定只能靠主播自助 →
102 个人永远停在「没账号」状态，展示端的「我的」页对 102/104 的人是死的。

---

## 2. 决策一：手机号存哪

### 2.1 结论

**在 `person` 表加 `phone` 列**（016 迁移），**不建 `person_contacts` 多联系方式表**。

```sql
ALTER TABLE person
  ADD COLUMN phone VARCHAR(24) NOT NULL DEFAULT '' COMMENT '主播手机号（运营登记；空串 = 未登记）',
  ADD COLUMN phone_uniq VARCHAR(24) GENERATED ALWAYS AS (NULLIF(phone, '')) STORED,
  ADD UNIQUE KEY uk_person_phone_uniq (phone_uniq);
CREATE INDEX idx_person_phone ON person (phone);
```

### 2.2 三个备选的对比

| 方案 | 一人多号 | 唯一性 | 改名后跟不跟 | 查询成本 | 结论 |
|---|---|---|---|---|---|
| **A. `person.phone` 单列**（推荐） | ❌ 不支持 | ✅ 生成列软唯一（空串不参与） | ✅ 天然跟着人走（就在人这一行） | 零 JOIN，台账列表直接带出来 | ✅ **选它** |
| B. `person_contacts` 子表（person_id + phone + kind + is_primary） | ✅ 支持 | ⚠️ 要额外写唯一索引 + 主号判定 | ✅ 跟着 person_id | 每条台账查询多一个 LEFT JOIN；「主号」判定要 SUBQUERY | ❌ 现在用不上 |
| C. 只存 `my_accounts.phone`（不碰 person） | ❌ | ✅ 012 已有 uk_my_phone_uniq | ❌ 没开号的人就没有手机号，无法「先登记后开号」 | 已有 | ❌ 解决不了 P7 |

**格式口径（两套手机号同一个校验）**：`person.phone` 与 `my_accounts.phone` 共用
`validate_my_phone`（store.rs:514）—— 去空格 / 横线后须为 5~20 位纯数字，空串 = 未登记。
两边必须同一套口径，否则会出现「台账里能存、开号时被拒」的割裂（store.rs:510-513 的注释
就是钉这条的）。

### 2.3 为什么选 A —— 逐条回答设计问题

**Q：一人可能多个联系方式吗？**
当前事实是「一人一号」。运营手上的手机号是**联系这个主播的唯一方式**，也是登录账号、
忘记密码、微信绑定的唯一凭据（三件事都读它，见 §5）。真出现「一个主播两个号」时，
升级路径是明确的（§2.4），**不需要现在就为它付 JOIN 的代价**。过早抽象在这里是负债：
台账页每加载一次要多跑 104 次子查询或一次 LEFT JOIN，换一个今天用不上的能力。

**Q：手机号要不要唯一？**
**要，但是"软唯一"** —— 用与 012 迁移**完全同款**的生成列手法：
`phone_uniq = NULLIF(phone, '')`，对它建 `UNIQUE KEY`。

- 空串 → `NULL`，`UNIQUE` 允许多个 `NULL` → **104 个还没登记手机号的人不会互相冲突**，
  迁移不会因此失败（这是 012 踩过的坑，也是 015 沿用的约定）；
- 只有「两个在职主播登记了同一个号」才报错 → 这正是要拦的情况：
  批量开号时一个号只能落到一个登录账号上（my_accounts 侧 012 已经唯一），
  台账侧不唯一就会出现「开号随机落到其中一人头上」，而运营完全看不出来为什么。

**Q：改名后手机号跟不跟？**
**跟。** 手机号就在 `person` 这一行上，主播改名（`PUT /api/admin/streamers/{id}` 改 `name`）
不影响 `phone` 一个字节。反过来也正是 015 迁移的意义：登录账号按 `person_id` 锚定，
改名后 `my_accounts.name` 由管理员改绑，手机号始终跟着人。
> 对比方案 C（只存 my_accounts）：改名且未改绑时，**手机号跟的是"账号名"而不是"人"**，
> 这正是 docs/12 P1 要根治的失联问题。

### 2.4 什么时候升级到 `person_contacts`

出现下面任一条再上子表，升级成本可控（016 的列保留作"主号缓存"）：

1. 运营明确要求「一个主播留两个号（本人 + 经纪人）」；
2. 需要**手机号变更历史**（谁、什么时候、从什么号改成什么号）—— 现在是直接覆盖，
   旧号立刻可被他人登记（业务可接受，见 §7.3）；
3. 需要区分「手机号 / 微信号 / 抖音号」多类联系方式。

## 3. 决策二：批量开号流程

### 3.1 结论：管理端勾选批量开号为主，CSV 导入为辅（二期）

| 方案 | 落地成本 | 运营体验 | 结论 |
|---|---|---|---|
| **A. 台账页勾选 → 批量开号**（已落地） | 低（复用已有的多选 + 弹窗） | 勾 104 个 → 填统一口令 → 确认 → 结果表抄密码 | ✅ **选它** |
| B. CSV 导入（姓名/抖音号 + 手机号） | 中（要解析、要按姓名模糊匹配、要处理重名） | 运营手上有 Excel 时更快 | 🟡 二期（§3.5） |
| C. 纯 SQL `INSERT ... SELECT FROM person` | 极低 | ❌ 写不出 argon2id 哈希（`pass` 是哈希列，SQL 只能写明文） | ❌ 不可行（docs/12 B-4 已注明） |

### 3.2 已落地的接口

```
POST /api/admin/my-accounts/batch
{
  "items": [ { "personId": 1027, "phone": "13354463148" },   // phone 选填
             { "personId": 1028 } ],                          // 留空 = 沿用台账 person.phone
  "defaultPass": "6688",      // 选填：既没入参手机号、台账也没登记的人用它当初始密码
  "forceReset": false,        // 默认 false：已存在的账号**不动密码**
  "dryRun": true              // 选填：只回预览，不写库
}
→ dryRun=true：只回一条汇总，不逐条判定、不写库（admin.rs:2908-2914）
  { "ok": true, "dryRun": true, "total": 2,
    "note": "预览：将对 2 个主播开号（初始密码 = 手机号后四位；无手机号时用 defaultPass）" }
→ 真跑（dryRun 缺省 / false）：逐条判定后返回（admin.rs:2945-2952）
  { ok, created, updated, skipped, failed,
    items: [ { personId, name, phone, status: created|updated|skipped|failed, note, initialPass? } ] }
  // initialPass：created 一定下发；updated 只在 forceReset 时下发（BatchAccountRow，store.rs:834-836）
```

### 3.3 初始密码规则：**手机号后四位**

| 情况 | 初始密码 |
|---|---|
| 有手机号（入参或台账已登记） | **手机号后四位**（`phone_suffix_pass`） |
| 没有手机号 | `defaultPass`（运营填的统一口令） |
| 两者都没有 | `skipped`，不开号 |

**为什么是后四位**：与已经上线的「忘记密码」重置口径**逐字一致**
（`store.rs` 的 `my_account_reset_password_to_phone_suffix` 就是取后四位）。
运营按重置流程改过之后，批量开号再跑一遍**不该又把密码变成另一个值** —— 两条路同款，
用单测钉住（`phone_suffix_pass_takes_last_four`）。

**为什么 `forceReset` 默认 false**：重跑一遍批量是运营的常态操作（补开漏掉的人）。
默认不重置，104 个已经改过密码的人不会被刷回初始密码 —— 那等于一次批量操作把全站
登录全部打断。只有运营明确勾「同时重置已有账号的密码」才重置。

### 3.4 幂等与逐条独立

- **逐条独立判定**：一条失败不影响其它条。104 人一次提交，不能因为第 3 个人手机号重号
  就让剩下 101 个都开不成（结果表逐条给 `status` + `note`）。
- **已存在账号** → 走更新（补 `person_id` / 手机号），不新建、不覆盖 `is_admin`
  （管理员观看账号不会被批量开号降级）。
- **存在性判定按 `person_id` 优先、`name` 兜底**（015 锚点口径）：主播改名后 `name` 对不上，
  按 `person_id` 仍能命中，不会开出第二个号。
- **开号即绑定**：`bound=1`、`name` = 台账姓名、`person_id` 锚定，与自助注册
  （`my_account_register`）同口径 —— 主播拿到号就能登，不用再绑一次。
- `source` 一律标 `batch`，与管理端手建（`admin`）、自助注册（`register`）区分，便于事后审计
  "这 104 个号是谁、什么时候开的"。

### 3.5 二期：CSV 导入（未实现，接口已留好位置）

入参扩展成 `items: [{ personId?, name?, douyinNo?, phone }]`：
`personId` 缺失时按 `name` 精确匹配台账（`STREAMER_BY_NAME_SQL`），
**同名主播直接报「有歧义，请指定 personId」** —— 绝不静默取 id 最小的那行
（docs/12 P4 的同名串人问题）。手机号列缺失的行照常开号（用 `defaultPass`）。

## 4. 决策三：开号与绑微信怎么衔接

### 4.1 结论：**扫码必须一人一码，但可以"不扫码先开号"**

先说清楚一件事：**微信 bot 凭证是账号级的，不是服务级。**
`wx_push_accounts`（013 迁移）存的是扫码拿到的 `bot_token`，
一个扫码账号对应一个主播，`wxpush.rs` 为每个账号各跑一条 `getupdates` 长轮询。
**协议上不存在"批量绑"** —— 不存在代他人扫码的机制。

### 4.2 三条路径，按运营成本排序

| 路径 | 谁操作 | 104 人成本 | 是否已支持 |
|---|---|---|---|
| **① 管理员机器人 + 绑定码**（推荐先做） | 运营在群里发一条「绑定 手机号」 | 主播**不用扫码**，加一次管理员机器人好友即可 | ✅ **代码已全在线上** |
| ② 用户自助扫码 | 主播自己在「我的」页扫码 | 104 人逐个扫，每人 1 分钟 ≈ 2 小时 | ✅ 已支持（013 + wxpush.rs） |
| ③ 运营代扫 | 运营拿自己微信扫 104 次 | ❌ 不可行：一个微信只能挂一个账号，会互相抢占 | ❌ 不支持（也不该支持） |

### 4.3 路径 ① 的完整链路（为什么它是正解）

```
管理员在「机器人」页扫码登录一个 bot（bot/mod.rs:weixin_qrcode）
   ↓ 凭证落到 wx_push_accounts（service 级：服务自己这个 bot）
主播微信加这个 bot 为好友，发一条消息（第一次发消息 = 留下 context_token）
   ↓ wxpush.rs 的 handle_msg 记下会话
主播发「绑定 13354463148」
   ↓ bot 命令路由 → store::push_bind_by_phone(phone, conversation_id, to_user_id)
   ↓ my_accounts 按 phone 找到账号姓名 → push_bindings 写入会话
完成：该主播以后就能收到追分提醒 / 每日报告
```

**关键点：主播要做的只是「加好友 + 发一条手机号」**，不用扫任何码。
104 人的真实成本是运营在群里发一条通知 + 主播各发一条消息，不是 104 次扫码。

### 4.4 批量开号 → 微信绑定的衔接点

批量开号**必须先把手机号写进 `my_accounts.phone`**，路径 ① 才走得通
（`push_bind_by_phone` 是 `SELECT name FROM my_accounts WHERE phone = ?`）。
本方案的 `my_accounts_batch_open` 已经做到这点：开号时手机号同步写进 `my_accounts.phone`
（不只是 `person.phone`），所以**开完号立刻就能走绑定**。

运营 SOP（一次搞定 104 人）：

1. 台账页登记手机号（编辑弹窗的「手机号」项，或 CSV 二期）；
2. 全选 → 「批量开号」→ 结果表里的初始密码复制出来，发给各主播；
3. 群里发一条：「加机器人好友，发『绑定 你的手机号』」；
4. 主播登进去看数据（姓名或手机号 + 初始密码）。

### 4.5 二要素绑定（手机号 + 验证码）的取舍

2026-10-10 审计 P1-1 后，机器人侧改成了二要素（`push_bind_by_phone_code`：
手机号 + 6 位一次性绑定码，30 分钟有效），单要素的 `push_bind_by_phone` 已停用
（现在只被集成测试调用）。

**取舍**：安全性 ↑，但主播要从「我的」页先取一次码。建议：
- **内网/熟人场景**用单要素（一个手机号就能绑，省一步）；
- **对外场景**保持二要素。
这个开关不在本次改动范围（涉及 `bot/weixin.rs`，另一个 agent 在做 bot 断连修复，**本次不动**）。

## 5. 迁移 SQL（`016_streamer_phone.sql`）

> 完整文件：`rust/crates/pk-server/src/migrations/016_streamer_phone.sql`
> 已登记到 `migrate.rs` 的 `MIGRATIONS` 数组（**不登记生产不会执行**，docs/12 踩过的坑）。

### 5.1 风格对齐 015：information_schema 探测 + PREPARE/EXECUTE

MySQL/MariaDB 没有 `ADD COLUMN IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`，
统一用「查 information_schema → 拼 DDL 字符串 → PREPARE/EXECUTE」三件套，
**重跑或人工提前加过列都不会报错卡住部署**。

```sql
-- ① person.phone
SET @s = IF(
  (SELECT COUNT(*) FROM information_schema.columns
    WHERE table_schema = DATABASE() AND table_name = 'person' AND column_name = 'phone') = 0,
  'ALTER TABLE person ADD COLUMN phone VARCHAR(24) NOT NULL DEFAULT ''''
     COMMENT ''主播手机号（运营登记；空串 = 未登记）''',
  'SELECT 1'
);
PREPARE stmt_016 FROM @s;
EXECUTE stmt_016;
DEALLOCATE PREPARE stmt_016;

-- ② 软唯一：与 012 的 my_accounts.phone_uniq 完全同款
SET @dup_phone_groups = (
  SELECT COUNT(*) FROM (
    SELECT phone FROM person WHERE phone <> '' GROUP BY phone HAVING COUNT(*) > 1
  ) t
);
SET @has_phone_uniq = (SELECT COUNT(*) FROM information_schema.columns
  WHERE table_schema = DATABASE() AND table_name = 'person' AND column_name = 'phone_uniq');
SET @s = IF(
  @dup_phone_groups = 0 AND @has_phone_uniq = 0,
  'ALTER TABLE person
     ADD COLUMN phone_uniq VARCHAR(24) GENERATED ALWAYS AS (NULLIF(phone, '''')) STORED,
     ADD UNIQUE KEY uk_person_phone_uniq (phone_uniq)',
  'SELECT 1'
);
PREPARE stmt_016 FROM @s; EXECUTE stmt_016; DEALLOCATE PREPARE stmt_016;

-- ③ 按手机号反查主播（唯一索引在生成列上，等值查询用不到它）
CREATE INDEX idx_person_phone ON person (phone);   -- 同样包在 IF 探测里
```

### 5.2 只做结构，不做数据

沿用 009 / 015 的先例：**迁移不写任何业务数据**。存量 1 条账号的兼容由代码负责（§7.2），
运营登记手机号走接口（`PUT /api/admin/streamers/{id}/phone` 或台账编辑弹窗）。

`migrate.rs` 的单测 `embedded_migrations_split_cleanly` 对语句有**白名单**
（每条必须以 `CREATE` / `ALTER` / `SET` / `PREPARE` / `EXECUTE` / `DEALLOCATE` 开头），
裸 `UPDATE` / `INSERT` 会让单测红 —— 这也是"数据动作不放迁移"的硬约束（docs/12 §4.6）。

### 5.3 为什么不在 016 里做回填

生产上 `person.phone` 现在**全是空串**，没有存量数据可回填。手机号只能由运营录入
（库里从来没有过），所以 016 之后台账页的「手机号」列会全部显示"未登记"，
这是**预期状态**，不是迁移失败。

### 6.1 「迁移没跑」的三层兜底（016 不是强依赖）

生产上服务重启与 `pk-server migrate` 是两步（docs/12 §6.2 的 G0~G2 灰度），
**服务可能先于迁移起来**。所以每个读 `person.phone` 的地方都有 LEGACY 兜底：

| 位置 | 016 没跑时 | 单测守着 |
|---|---|---|
| `admin::streamer_rows`（台账列表 + 导入匹配） | 退回 `STREAMERS_SQL_LEGACY`（少 `phone` / `has_account`） | `streamers_legacy_sql_is_a_subset_of_016` |
| `admin::streamer_row_by_id`（详情页 + 设师傅） | 退回 `STREAMER_BY_ID_SQL_LEGACY` | 同上函数体 |
| `store::my_accounts_batch_open`（批量开号） | 退回 `PERSON_ROSTER_FOR_ACCOUNTS_SQL_LEGACY`，手机号一律当"未登记"（靠 `defaultPass` 开号） | `batch_open_sql_is_readonly_and_scoped` |
| `store::person_set_phone`（写手机号） | 返回「请先跑 pk-server migrate（016_streamer_phone）」 | 行为在 Err 分支 |

**唯一会明确报错的是"写手机号"** —— 那是运营需要看见并去处理的，静默吞掉更糟。
读路径一律降级，保证台账页、详情页、批量开号在任何迁移状态下都能打开。

### 6.2 「已开号但没登记手机号」的边界

批量开号第一批里如果有人没填手机号（用 `defaultPass` 开号），他**仍然有账号**。
所以「这个主播有没有账号」的判定**不能只查 `phone <> ''` 的行** ——
否则第二遍批量开号会走到 `INSERT`，被 `PRIMARY KEY(name)` 撞回 `failed`，
运营看到"已存在"却开不了号。代码里 `account_by_name` 显式捞**全部** `my_accounts` 行
（见 `store.rs` 里那条注释），这条坑单独写在注释里防回退。

## 7. 风险与处理

### 7.1 手机号唯一冲突

| 场景 | 016 迁移时 | 运行时（登记 / 批量开号） |
|---|---|---|
| 存量已有重复手机号 | **跳过建索引**（`SELECT 1`），迁移照常成功 → 重复号需要人工改掉后再补建（见下） | `person_set_phone` 报「手机号 X 已被其它在职主播登记」，不写入 |
| 新增时撞台账 | — | 同上，逐条 `failed`，**不影响同批其它人** |
| 新增时撞登录账号 | — | 报「手机号 X 已绑在「某某」的账号上」，指明去哪改 |
| 并发穿过预检 | — | 唯一索引兜底抛 `Duplicate entry`，代码翻成中文文案（单条路径的 P6 不一致已一并修） |

**补建索引**（重复号清理后）：

```sql
-- 先找出重复的号
SELECT phone, COUNT(*) AS n, GROUP_CONCAT(name) AS names
  FROM person WHERE phone <> '' AND deleted_at IS NULL
  GROUP BY phone HAVING COUNT(*) > 1;

-- 人工改掉重复后补建（与 016 的 IF 判定同款，不存在就建）
SET @s = IF(
  (SELECT COUNT(*) FROM information_schema.statistics
    WHERE table_schema = DATABASE() AND table_name = 'person'
      AND index_name = 'uk_person_phone_uniq') = 0,
  'ALTER TABLE person
     ADD COLUMN phone_uniq VARCHAR(24) GENERATED ALWAYS AS (NULLIF(phone, '''')) STORED,
     ADD UNIQUE KEY uk_person_phone_uniq (phone_uniq)',
  'SELECT 1');
PREPARE s FROM @s; EXECUTE s; DEALLOCATE PREPARE s;
```

**验收查询**：

```sql
SHOW INDEX FROM person WHERE Key_name IN ('uk_person_phone_uniq','idx_person_phone');
SELECT COUNT(*) AS dup FROM (
  SELECT phone FROM person WHERE phone <> '' AND deleted_at IS NULL
   GROUP BY phone HAVING COUNT(*) > 1) t;   -- 必须为 0
SELECT COUNT(*) AS persons FROM person WHERE deleted_at IS NULL;   -- 104，一个都不能少
```

### 7.2 存量 1 条数据怎么兼容（鹏先生 / 13354463148 / person_id=1027 / is_admin=1）

`my_accounts` 现在唯一那行**完全不受影响**：

- 016 只动 `person` 表，`my_accounts` 一行不碰；
- 台账页上「鹏先生」的手机号列会显示"未登记"（`person.phone` 还没录），
  但他**已经开号**（`hasAccount=true` → 显示"已开号"角标）；
- 运营把 `13354463148` 补进台账时会被 `person_set_phone` 拦下
  （"已绑在另一个展示端账号上"）—— **这是对的**：这个号已经在 `my_accounts.phone` 里，
  台账侧再记一份会让人以为可以拿去给第二个人开号。
  处理方式二选一：① 台账不填（推荐，保持"档案无号"的真实性）；
  ② 先 `DELETE` 该账号的手机号再补 —— 不推荐，会打断他的手机号登录。

- `is_admin=1` 的管理员属性：批量开号的更新路径**不带 `is_admin` 字段**
  （`UPDATE ... SET phone, person_id, bound`），不会被误改。

### 7.3 其它已知边界

| 项 | 现状 | 评估 |
|---|---|---|
| 手机号变更历史 | 直接覆盖，旧号立刻可被他人登记 | 🟢 业务可接受（docs/12 P6 同款结论）；要留痕时按 §2.4 上子表 |
| 手机号后四位当密码的安全性 | 4 位数字，可被撞库 | 🟠 缓解：① 展示端登录已有每 IP 每分钟 5 次限流（`public_teams.rs` 的 `VERIFY_LIMITER`）；② 首登后应引导改密（未实现，见 §8） |
| 初始密码只在结果表出现一次 | 库里只存 argon2id 哈希，明文不落库 | ✅ 正确行为；运营要当场抄走，重跑只会重置不会回显旧值 |
| `person.phone` 与 `my_accounts.phone` 可能不一致 | 两份独立数据（档案号 vs 登录号） | 🟡 有意为之：一个人可以"档案上留经纪人的号、登录用自己的号"；批量开号以**入参 > 台账**为准 |
| 批量开号的事务粒度 | 逐条自动提交，无大事务 | ✅ 104 行在 RK3318 上是毫秒级；任一行失败不回滚其它行（正合需要） |

### 7.4 回滚

016 只做 `ADD COLUMN`（带 `DEFAULT ''`）/ 生成列 / 索引，**不删列、不改类型、不删行** →
结构上不可能丢数据。真要回滚：

```sql
ALTER TABLE person DROP INDEX idx_person_phone,
                   DROP INDEX uk_person_phone_uniq,
                   DROP COLUMN phone_uniq,
                   DROP COLUMN phone;
DELETE FROM schema_migrations WHERE version = '016_streamer_phone';
```

代码侧即使**不回滚也能跑**：`streamer_rows` / `streamer_row_by_id` 检测到
`Unknown column` 会自动退回 LEGACY SQL（`STREAMERS_SQL_LEGACY` / `STREAMER_BY_ID_SQL_LEGACY`），
只有 `person_set_phone` 会返回「请先跑 migrate」的提示。
