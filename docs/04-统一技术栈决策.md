# 04 · 统一技术栈决策（Rust 后端）

> 决策日期：2026-10-02（v2，取代 v1 的「Go + Rust 双服务」方案）；2026-10-04 明确运行环境范围
> 运行环境：生产以 RK3318（aarch64 / Docker，/opt/pk-server）为准；115（x86_64 / CentOS 7 / Docker）仅作开发与验收，不是生产路径；不部署到其他服务器

## 结论

后端统一为 **Rust 单技术栈**：一个 `pk-server`（axum）同时承担分组、展示、数据管理、
采集导入、机器人五类职责；业务数据与运行时状态统一落在 MySQL/MariaDB 业务库
（2026-10-10 单库化，见 docs/00 §4），旧 SQLite 只作一次性搬家来源留底。

| 层 | 技术 | 原因 |
|---|---|---|
| 主数据 | MariaDB 11.4 | RK3318 已有运维基础；数据主权回盒子；避免外部 sqlpub 连接抖动 |
| 后端（全部） | Rust（`pk-core` + `pk-server`） | 算法权威实现已有回归基线；单一运行时、低内存、无 GC 停顿；机器人路径保持确定性 |
| 前端 | React + Vite | 现有 PK 管理/展示界面成熟；`apps/douyin-web` 复用同一构建模式 |
| 契约 | OpenAPI 3.1 + JSON Schema | 边界显式化，避免同名接口不同语义 |
| 入口 | 宿主机 Caddy | 147 / RK3318 公网入口均由 Caddy 反代（早期写的 Nginx 已换）；不额外常驻网关消耗内存 |
| 缓存 | 服务内缓存 + MariaDB | 当前数据量不需要 Redis；减少一个常驻进程 |

## 为什么把 Go 服务并进 Rust

v1（2026-10-01）曾决定「Go 写库 / Rust 只读、双服务共存」。落地过程中确认：

1. **Go 服务体量很小**：健康检查 + 机器人命令路由 + migration 工具，合计不足 700 行；
   与 `pk-server` 共用同一张 `douyin` 库和同一套账号体系，双服务只带来镜像、端口、
   Caddy 路由、健康检查的额外复杂度。
2. **Rust 重写成本可控**：确定性机器人路由（`help/query/rank/group`）是纯逻辑，
   没有 AI/长连接依赖，迁移后仍有单测保护。
3. **一套运行时 = 一套部署**：镜像从两个减到一个，CI、Compose、离线打包、升级回滚
   全部只对 `pk-server` 负责。
4. **无「强行合并」的代价**：机器人、采集、导入都可以作为 `pk-server` 内的独立模块
   （`bot` / `import` / `collect`），代码边界与原来 Go 的包边界一一对应。

## 职责边界

```text
Caddy
 ├─ /s/*     → pk-server:8787   对外公布页
 ├─ /admin/* → pk-server:8787   管理端 SPA（apps/douyin-web）
 └─ /*       → pk-server:8787   展示端 / 其余入口
MariaDB(douyin)
 ├─ douyin_writer → pk-server（写：导入 / 采集 / 管理）
 └─ pk_reader     → pk-server（只读：分组 / 展示 / 榜单）
运行时表（plans / aliases / roster / my_accounts / bot_sessions …）
 └─ 已并入 MySQL 业务库（2026-10-10 单库化；旧 SQLite 只作搬家来源留底）
```

只读与写路径在同一进程内分账号隔离：查询走 `pk_reader` 池，写入走
`douyin_writer` 池，SQL 仍集中在 `dialect.rs`，不接受外部传入的 SQL 字符串。

## 账号权限

| 账号 | 权限 | 用途 |
|---|---|---|
| `douyin_writer` | 业务表 `SELECT / INSERT / UPDATE / DELETE` | 导入、采集、管理写入；**不持有 DDL** |
| `douyin_migrator` | 受控 DDL + 业务表写 | 仅显式迁移窗口使用 |
| `pk_reader` | `SELECT` | 分组、展示、榜单查询 |

**Migration 执行方式（2026-10-04 修订，取代旧文「writer 启动时跑 DDL」）**：
DDL 由独立的 `douyin_migrator` 账号执行，通过 `pk-server` 的显式 `migrate` 子命令
（或等价 env 开关，默认关闭）触发，**不随服务启动自动执行**。`pk_reader` 永远只读。
理由：业务写账号持有 DDL 违反最小权限与「读写权限实测隔离」验收；启动自动 DDL 在
断电重启频繁的 RK3318 盒子上容易掩盖迁移错误（该决策经 TypeSafe 结构化判断确认）。

## 数据库访问层统一约定（2026-10-12）

> 背景与改证据（三套执行入口并存、219 处直连、月度落库权限错误等乱象）见
> docs/18-数据库访问层统一改造.md。本节写**长期有效**的标准，新增/改动数据访问代码以此为准。

### 标准方案

**sqlx 0.8 + PgPool + MySQL 风格 `?` 占位符 + `crate::pq::rewrite` 运行期重写为 `$N`**，
唯一事实源 = 本机 PostgreSQL 17 的 `douyin_dev`（`127.0.0.1:3318`，见 docs/16）。

```rust
// 读：走 pgrs 入口，守卫 + 重写都内建，调用方只写 SQL
let rows = pgrs::query(&st.pools, "LOCAL", "SELECT id, name FROM person WHERE team = ?").await?;
let rows = pgrs::query_with_binds(&st.pools, "LOCAL",
    "SELECT wave FROM daily_metric WHERE person_id = ? AND d = ?",
    |q| q.bind(pid).bind(&day)).await?;

// 写：writer 池（DB_WRITER_*，账号 pk_writer）+ 手动包 pq::rewrite
sqlx::query(&crate::pq::rewrite(
    "INSERT INTO monthly_metric (person_id, period, wave) VALUES (?,?,?)
     ON CONFLICT (person_id, period) DO UPDATE SET wave = EXCLUDED.wave",
))
.bind(pid).bind(&period).bind(wave)
.execute(&pool).await?;
```

### 三条铁律

1. **读走 `pgrs::query` / `pgrs::query_with_binds`** —— 只读守卫（仅放行 SELECT）与
   `?` → `$N` 重写都在入口内建，调用方不手动包 rewrite、不直连 `sqlx::query` 拿读池。
2. **写走 writer 池（`DB_WRITER_*`，账号 `pk_writer`）+ `writer::write_guard` + `pq::rewrite`**
   —— 账号本身无 DDL 权限是根本，写守卫拦 DDL 关键字是应用层兜底，`?` 必须包 rewrite。
3. **禁止拿只读池执行写** —— `pk_reader` 只有 SELECT 权限，用只读池 INSERT 必然
   `permission denied`；历史上月度落库（metrics.rs）就是这么静默失败、从未成功过的。

### 新调用点 checklist

- [ ] SQL 里的占位符**全是 `?`**（MySQL 风格），没有 `$N` 混用；
- [ ] 读查询 → `pgrs::query` / `pgrs::query_with_binds`（不要手动包 rewrite，入口已内建）；
- [ ] 写语句 → writer 池执行，SQL 用 `&crate::pq::rewrite("…")` 包好；
- [ ] PG 方言核对：`now()`（不是 `NOW(3)`）、`UPDATE…FROM` / `DELETE…USING`（不是 JOIN 写法）、
      `SUM(条件::int)`（布尔不能直接 SUM）、`ON CONFLICT`（不是 `ON DUPLICATE KEY`）；
- [ ] 无参字面量也要包 rewrite（`sqlx::query(&crate::pq::rewrite("SELECT …"))`），
      统一样式，避免将来加参数时漏包。

### `?` 与 `$N` 不混用

`pq::rewrite` 从 0 开始给 `?` 顺序编号成 `$1..$N`；SQL 里若同时手写了 `$N`，
编号会错位（值绑到错误的参数上）。**同一条 SQL 要么全是 `?` 要么全是 `$N`**：
新写的 SQL 一律用 `?`；只有从 PG 原生示例抄来、占位符编号有特殊依赖的（极少）才保留 `$N`。
判断口诀：看到 `?` 就交给 rewrite，看到 `$N` 就一个都别混。
