## 0. 一句话结论

把 pk-server 里三套并存的 SQL 执行入口收敛成**一条标准链路**：
sqlx 0.8 + PgPool + MySQL 风格 `?` 占位符 + `crate::pq::rewrite` 运行期重写为 `$N`；
读路径走 `pgrs::query` / `pgrs::query_with_binds`（只读守卫 + 入口内建重写），
写路径走 writer 池（`DB_WRITER_*`，账号 `pk_writer`）+ `pq::rewrite`。
唯一事实源 = 本机 PostgreSQL 17 的 `douyin_dev`（`127.0.0.1:3318`），见 docs/16 §0。

## 1. 改造前的乱象（收敛前实查清单）

### 1.1 执行入口三套并存

| 入口 | 处数 | 说明 |
|---|---:|---|
| `pgrs::query` | 49 | 只读守卫 + 连池，但没有内建重写 |
| `pgrs::query_with_binds` | 25 | 同上，带 bind 闭包 |
| `sqlx::query` 直连 | 219 | 绕过守卫直接拿池执行 |

### 1.2 直连 219 处的细分（重写责任全压在调用方）

- **193 处**手动包 `pq::rewrite` —— 同样的样板代码抄了两百遍；
- **27 处**直传不包（其中 2 处是动态拼 SQL 的，调用方自己手动做了重写）；
- **6 处无参字面量裸传** —— SQL 里没有 `?` 所以侥幸没炸，但性质和漏包一样。

历史上 60+ 处漏包重写的方言残留（`?` 直传 PG、`NOW(3)`、`UPDATE…JOIN`、`DELETE…JOIN`、
`SUM(布尔)`）就是这么来的，其中展示端登录台账反查的
`syntax error at or near "ORDER"` 就是一个裸 `?` 卡在 `ORDER BY` 前面（见 §3.7）。

## 2. 统一标准方案

```text
                  ┌─ 读：pgrs::query / query_with_binds
                  │    只读守卫（仅放行 SELECT）→ pq::rewrite（内建）→ pk_reader 池
调用方写 SQL(?) ──┤
                  └─ 写：writer 池（DB_WRITER_*，账号 pk_writer）
                       pq::rewrite（调用方手动包）→ write_guard 接入后兜底 DDL
migrate：独立通道，douyin_migrator/pk_writer 账号执行 DDL（不随启动自动跑）
```

- **方言约定**：SQL 一律写 MySQL 风格 `?` 占位符，由 `crate::pq::rewrite` 在运行期
  机械重写成 PG 的 `$1..$N`（跳过单引号字符串字面量里的 `?`）。调用方从此不用关心方言。
- **`?` 与 `$N` 不混用**：同一条 SQL 里要么全是 `?` 要么全是 `$N`——重写器从 0 开始数，
  混用会导致 `$N` 编号错位（详见 pq.rs 头注释与 docs/04 的规则条）。
- **读 / 写分池分账号**：读走 `pk_reader`（仅 SELECT），写走 `pk_writer`
  （业务表 DML，无 DDL），账号权限是根本、守卫是应用层兜底。

三条铁律与新调用点 checklist 见 docs/04「数据库访问层统一约定（2026-10-12）」，此处不重复。

## 3. 改动明细（2026-10-12，访问层收敛这一次）

| # | 改动 | 位置 | 说明 |
|---|---|---|---|
| 3.1 | `pgrs::query` / `pgrs::query_with_binds` 两个入口**内建 `pq::rewrite`** | pgrs.rs | 调用方从此不用关心方言；守卫仍在重写前执行。传 `$N` 原生写法的 SQL 无 `?` 可重写、原样通过 |
