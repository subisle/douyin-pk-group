## 发现 2：闸门拦截时仍返回 Ok → 被拦截的一轮被当成成功，去重标记与 job 终态一起被推进
- 位置：push.rs:441（send_binding 拦截）、push.rs:471（send_binding_images 拦截）、push.rs:766/797/809/817（push_set_last_report_date）、push.rs:930/943/951（push_set_lineage_date）、push.rs:311（push_job_finish ok=true）
- 严重度：P0
- 冲突：闸门为「不打断调度器」在拦截时 `return Ok(())`，于是 `run()` 把这一轮当成功：日报告/师门日报的同业务日去重标记（`last_report_date` / `last_lineage_date`）立刻写成当天，追分目标的 `last_notice_date` 也写成当天，任务 finish 成终态 `done`。后果不是「少发」而是**去重标记被空跑提前消耗**：PUSH_OUT_ENABLED=0（或灰度白名单外）期间，主播本该在开闸后收到的那份日报/追分提醒被永久吞掉 —— 标记已是今天，即使立刻开闸、当天也再不会重推（`push_job_take` 只捞 pending/failed:N，done 是终态）。叠加发现 1 的生产漏配，上线当天全员推送静默归零，而日志里全是 INFO「每日报告已推送 / 延迟推送完成」，看不出没真发。同一机理还有第二个侧面：`run()` 内部所有发送失败都只记 warn + `push_touch`，从不向外抛 Err，所以 push.rs:316 的 `push_job_finish(&st, id, false, ...)` 分支**永远走不到**，任务一律落 done、不重试。

## 发现 7：push_jobs 崩溃恢复要等 5 分钟，且 pending 扫描无 SKIP LOCKED 兜底
- 位置：store/push_jobs.rs:57-108（push_job_take）、store/push_jobs.rs:59-61（running 回收条件）、docs/17-数据库对齐与64部署方案.md:427（已登记为已知项「多实例抢占无显式锁」）
- 严重度：P2
- 冲突：`push_job_take` 的扫描 SQL 里，pending 分支只判 `run_at <= now()`，pending→running 靠后续的 `UPDATE ... WHERE id = ? AND status = prev_status` 的 CAS 保证同一瞬间只有一个实例抢到，但没有 `SELECT ... FOR UPDATE SKIP LOCKED`。真正的风险在**进程崩溃后的恢复**：`running` 不在 pending 分支里，只有 5 分钟超时分支才回收（且要求 `done_at = ''`，而 `push_job_finish` 一定会写 `done_at = now_str()` → 已 finish 的行不会被误捞，但崩溃留下的 running 行 `done_at` 是空的 → 5 分钟后才回收）。崩溃后最多 5 分钟该 (team, biz_date) 的任务不会被重推；加上 `uk_push_job (team, biz_date)` 唯一键，这段时间内的补数导入只会刷新 run_at，不会叠加。功能上不丢（靠 `last_report_date` 兜底），但后台队列页会显示一行卡在 running 的任务，与「60 秒一轮」的运维预期不符。
- 证据：
```rust
// store/push_jobs.rs:58-65
"SELECT id, team, biz_date, status FROM push_jobs
 WHERE (status = 'pending' AND NULLIF(run_at,'')::timestamptz <= now())
    OR (status = 'running' AND done_at = '' AND NULLIF(run_at,'')::timestamptz <= now()
        AND created_at <> '' AND NULLIF(created_at,'')::timestamptz < now() - INTERVAL '5 minutes')
```

## ✅ 已核实

- **开关独立性（docs/10 §「每日报告与追分提醒两套独立开关」）** —— 成立，且已扩到三套。`push_bindings` 上 `notify_target` / `daily_report` / `lineage_report` 是三列，落库路径互不覆盖：`push_set_daily_report`（wxpush.rs:398，只写 daily_report）、`push_set_lineage_report`（wxpush.rs:435，只写 lineage_report）单独成列；`push_set_flags`（wxpush.rs:375）是整行覆盖两列的历史入口，注释明确警告不能用它代替；机器人「暂停/开启接收每日推送」只动 `daily_report`（bot/mod.rs:1259/1269）。三套各自的同业务日去重（`last_report_date` / `last_lineage_date` / 目标侧的 `last_notice_date`）也互相独立，不串。管理员消息下发（admin_send.rs）与自动推送完全分离，不写这三个去重列，docs/23 §5.1 的承诺在代码里成立。
- **上游整行覆盖的缺省语义** —— 刻意不一致但已被前端对齐，不冲突。`my_push_settings`（wx.rs:675）对 `notifyTarget`/`dailyReport` 缺省按 false 落库、`lineageReport` 缺省不动现值；前端 `saveFlags`（st_page.html:4825-4846）每次全量带三个开关的当前值（未渲染的开关回落到接口下发的现值），不会因为只传一个而把另两个覆盖成关。
- **追分目标分类计数（docs/10 § 追人 ≤5 / 目标分数 ≤5 各自独立）** —— 落实到位，无合并计数残留。`store::target_counts`（wxpush.rs:1017）按 kind 三路返回，`targets_add_serialized`（wxpush.rs:1172-1181）在事务内按 `kind` 单类 COUNT 校验 `MAX_TARGETS`，`plan_inserts`（wxpush.rs:1095）按「现有 + 本次」判单类上限。生产写入只有一个出口 `targets_add_serialized`（wx.rs:81 `add_targets`），单条 / 批量 / 三种 kind（person 用 Reject、value 用 Ignore、batch 用 Skip）全走它；`push::MAX_TARGETS` 复用为单类上限，与 docs/10 口径一致。**仅发现 6 的旧函数整段残留，当前无调用方。**
