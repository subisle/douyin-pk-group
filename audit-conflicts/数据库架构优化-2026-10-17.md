# 数据库架构优化（2026-10-17）

## 原则

**只做对应用透明、可一键回滚的改动**：补索引 + 改查询写法，
不新增表、不改列、不动任何读写语义。出问题 `DROP INDEX` 即可回滚。

## 一、查询改写：`TO_CHAR(...) LIKE` → 日期范围（实测 3.9×）

- 位置：`dialect.rs::period_rollup_sql`（月/年榜聚合的公共 SQL）
- 问题：日明细窗口写成 `TO_CHAR(d.biz_date,'YYYY-MM') LIKE '2026-10%'`。
  这是**函数表达式比较**，PG 用不上 `biz_date` 上的 B-tree 索引 →
  每张月榜/年榜都要全表扫 `daily_metric`
- 改法：`d.biz_date >= '2026-10-01'::date AND d.biz_date < '2026-11-01'::date`
  （新增 `like_to_date_range()` 把 LIKE 窗口翻成范围，含跨年边界与脏值兜底）

**实测**（本机 768 行，30 次平均）：

| 写法 | 耗时 |
|---|---|
| `TO_CHAR ... LIKE`（旧） | 0.780 ms |
| 日期范围（新） | **0.201 ms**（≈3.9×） |

首次 EXPLAIN ANALYZE 对比：5.92ms → 0.76ms。数据量增长后差距会更大
（当前 768 行下 PG 仍选 Seq Scan，索引已就位，行数上来会自动切索引扫描）。

**等价性已验证**（实库逐窗口比对，人与数值完全一致）：

| 窗口 | 旧 | 新 |
|---|---|---|
| 月 `2026-10%` | 104 人 / 5,657,216 | 104 人 / 5,657,216 ✅ |
| 年 `2026%` | 104 人 / 5,657,216 | 104 人 / 5,657,216 ✅ |

单测：`dialect::tests::like_to_date_range_covers_month_and_year`（月/年/跨年/脏值）、
`month_rollup_prefers_imported_wave_over_daily_sum`（反向断言不再出现函数比较）。

## 二、索引补齐（迁移 `032_query_indexes`）

| 索引 | 作用 |
|---|---|
| `idx_daily_person_date_reliable` | 日/月/年榜聚合都带 `wave_reliable=1`，把可靠行钉进索引 |
| `idx_daily_date_reliable` | 按业务日捞全团（日榜 / 缺数据 / 导入状态） |
| `idx_person_list_scope` | 榜单公共过滤三件套 `(gender, status, hide_in_daily_report)` WHERE 未删 |
| `idx_person_master_live` | 师门/族谱按师傅查门下 |
| `idx_account_person_primary` | 「我的抖音号」分号口径按 `(person_id, is_primary)` 取号 |
| `idx_plans_event_created` | 方案列表按赛事类型 + 时间倒序 |

另清理 `001_core.sql` 里**重复定义两次**的 `idx_name`
（`CREATE INDEX IF NOT EXISTS` 只认名字，第二次静默跳过，库里实际只有一个）。

迁移已实际执行成功（`DB_MIGRATOR_USER=zmy cargo run -p pk-server -- migrate`），
库里索引总数 96。

⚠️ 本机表属主是 `zmy`、迁移账号是 `pk_writer`，跑迁移要带 `DB_MIGRATOR_USER=zmy`
（与 AGENTS.md 速查表一致），否则 DDL 被拒且**不会自愈**。
