## 发现 1：月/年榜音浪只算主号（daily_metric），不含副号 wave_snapshot；实时音浪（WAVES_A）却算副号 —— 同一人两个音浪数

- 位置：`rust/crates/pk-server/src/dialect.rs:365-381`（period_rollup_sql 内层）vs `rust/crates/pk-server/src/dialect.rs:65-74`（WAVES_A）
- 严重度：P1
- 冲突：月榜 / 年榜 / 管理端月年聚合 / 公告席位选人全部走 `period_rollup_sql`，内层只 `FROM daily_metric d`；而 `WAVES_A`（分组页实时音浪、matching.rs）与分号口径把副号 `wave_snapshot` 并进来。
  上线后具体表现：一个挂 3 个号的主播，主号当月 daily_metric 合计 50 万、两个副号快照合计 30 万 —— 月榜显示 **50 万**，同一个人在分组页实时音浪显示 **80 万**；`/my` 月卡 50 万、`/my/accounts` 合计 80 万。主播会直接拿月榜和「我的抖音号」两处数字来问差在哪。
- 证据：
```rust
// dialect.rs:365-372 —— 月/年骨架内层：只有 daily_metric，没有 wave_snapshot
"SELECT {select} FROM ( \
   SELECT d.person_id AS pid, TO_CHAR(d.biz_date, 'YYYY-MM') AS m, \
     SUM(d.wave) AS w, SUM(d.minutes) AS dm, \
     SUM(CASE WHEN d.wave >= 2 THEN 1 ELSE 0 END) AS live, \
// dialect.rs:70-73 —— WAVES_A 把副号并进来（is_primary = 0）
SELECT a.person_id AS k, SUM(ws.wave_value) AS w
 FROM wave_snapshot ws JOIN account a ON a.anchor_id = ws.anchor_id AND a.is_primary = 0
```

## 发现 2：`/my` 的「累计」与 `/my/accounts` 的「合计」口径不同，代码注释却声称能对齐

- 位置：`rust/crates/pk-server/src/public_teams/minutes.rs:298-303` vs `minutes.rs:668-680`、`minutes.rs:603-626`
- 严重度：P1
- 冲突：`/my.total` 只 `SUM(daily_metric.wave)`（主号口径，不含副号）；`/my/accounts` 的 `summary.total` 是「主号 daily_metric + 副号 wave_snapshot」逐号相加。`minutes.rs:668` 注释写「因此 summary 与 /my 的 total 可以对得上，前端卡顶直接显示它」——只要有副号就永远对不上。上线后具体表现：某人 `/my` 累计 50 万，同一页面「我的抖音号」卡顶部合计 80 万。
- 证据：
```rust
// minutes.rs:298-303 —— /my 的 total：只按 person_id 直查 daily_metric
let mut total = one(
    &st,
    format!(
        "SELECT (SUM(wave))::BIGINT AS wave, (SUM(minutes))::BIGINT AS minutes \
     FROM daily_metric WHERE person_id = {person_id} AND wave_reliable = 1"
    ),
)
// minutes.rs:620-623 —— /my/accounts：副号 wave_snapshot 也进合计
FROM wave_snapshot ws JOIN account sa \
  ON sa.anchor_id = ws.anchor_id AND sa.is_primary = 0 \
WHERE sa.person_id = {person_id} \
```

## 发现 3：累计口径里「时长」用整月值、「音浪」不用 —— 同一页两个累计互相矛盾

- 位置：`rust/crates/pk-server/src/public_teams/minutes.rs:321`（total 时长）、`minutes.rs:170-172`（total 音浪回落纯日明细）
- 严重度：P1
- 冲突：`/my` 的 `total["minutes"]` 走 `my_minutes(Total)`，`MinutesScope::Total` 的 `period_where()` 返回空串 → **把所有 `monthly_duration` 的整月时长都加进来**；而 `total["wave"]` 走 `daily_metric` 全量求和，`my_wave_sql` 对 `Total` 显式回落到纯日明细、**完全不看 `monthly_wave`**。
  上线后具体表现：某月只导了平台月报（整月时长 4529 分、整月音浪 60 万，当月没有日明细）→ `/my` 显示「本月 60 万 / 时长 75时29分」，而「累计」显示「音浪 **0** / 时长 **75时29分**」。同一个累计块里时长有值、音浪为 0；而且「累计时长」会大于「本月时长」以外的月份之和，主播会问累计音浪为什么是 0。
- 证据：
```rust
// minutes.rs:321 —— 累计时长：整月值全算进去
total["minutes"] = json!(my_minutes(&st, person_id, &MinutesScope::Total).await?);
// minutes.rs:170-172 —— 累计音浪：显式回落纯日明细，不看 monthly_wave
if !with_monthly || matches!(scope, MinutesScope::Total) {
    return daily_only;
}
```

## 发现 4：「我的抖音号」分号明细的月 / 年 / 累计不走「整月优先」，与月卡、月榜两套月累计

- 位置：`rust/crates/pk-server/src/public_teams/minutes.rs:603-626`（`/my/accounts`）、`rust/crates/pk-server/src/push.rs:1266-1286`（推送分号明细）
- 严重度：P1
- 冲突：月卡（`my_wave_sql`）、月榜（`period_rollup_sql`）、族谱（`lineage_wave_window_sql`）都改成 `COALESCE(monthly_wave, 日明细求和)`，分号明细仍是纯 `daily_metric` + `wave_snapshot` 按日期窗口 `SUM(CASE WHEN t.d LIKE '{month}-%' ...)`。
  上线后具体表现：某人 9 月导了整月音浪 60 万、当月日明细只有 3 天共 5 万 → 月卡与月榜显示 **60 万**，「我的抖音号」卡的「月」列与合计显示 **5 万**；机器人文案 `· xxx（主号） 日 X / 月 X / 年 X` 也是 5 万（push.rs:1400-1406）。

## 发现 5：切主号后历史 daily_metric 从「分号口径」整段消失

- 位置：`rust/crates/pk-server/src/admin.rs:3697-3707`（后台「设为主号」）→ `rust/crates/pk-server/src/public_teams/minutes.rs:610-615`
- 严重度：P1
- 冲突：`daily_metric.anchor_id` 在导入时回填的是**当时的主号** anchor_id。后台把另一个号设为主号后，旧主号行 `is_primary` 变 0；分号 SQL 主号分支要求 `pa.is_primary = 1`，历史行 JOIN 不上，副号分支又要求 `sa.is_primary = 0` 且来源是 `wave_snapshot`（旧主号未必有快照行）→ 这批历史音浪在分号口径里既不归主号也不归副号。
  上线后具体表现：切主号当天起，「我的抖音号」每个号的历史月 / 年 / 累计全部掉一截，而 `/my` 月卡（按 person_id 直查 daily_metric）数字不变 —— 两处立刻对不上，且没有任何提示。
- 证据：
```rust
// admin.rs:3699-3705 —— 设为主号：只改 account.is_primary，不动 daily_metric.anchor_id
"UPDATE account SET is_primary = 0 WHERE person_id = ? AND is_primary = 1",
...
"UPDATE account SET is_primary = 1 WHERE id = ?",
// minutes.rs:612-615 —— 分号主号分支：按 anchor_id + is_primary=1 关联历史行
FROM daily_metric d JOIN account pa \
  ON pa.person_id = d.person_id AND pa.anchor_id = d.anchor_id \
   AND pa.is_primary = 1 \
```

## 发现 6：月 / 年榜「未播天数」永远走日明细，整月补采的人恒显示「未播 0 天」

- 位置：`rust/crates/pk-server/src/dialect.rs:352`（补齐行写死 0）、`dialect.rs:369-371`（live/off/days 只由日明细算出）
- 严重度：P1
- 冲突：`period_rollup_sql` 的音浪是「整月优先」，但同一行的 `off` 只来自 `SUM(CASE WHEN d.wave < 2 ...)`；而「只导了整月音浪、当月没有日明细」的月份由 `month_wave_only` 补一行占位，`live/off/days` 硬编码 0。
  上线后具体表现：运营用平台月报补采 2026-08（整月音浪 40 万，无日明细）→ 该人月榜显示「音浪 40 万、未播 0 天」，与同榜「音浪 38 万、未播 5 天」的人并排；未播天数在月榜上对不同数据源的人不可比（docs/10 §三 声称月榜「含未播天数」）。
- 证据：
```rust
// dialect.rs:350-357 —— 整月补采行：开播/未播/天数一律 0
UNION ALL \
SELECT mw0.person_id AS pid, mw0.period AS m, 0 AS w, 0 AS dm, \
       0 AS live, 0 AS off, 0 AS days \
  FROM monthly_wave mw0 \
```

## ✅ 已核实

- **① 整月时长写 `monthly_duration`、整月音浪写 `monthly_wave`** —— **真**。`commit_month_metrics`（admin.rs:3109-3182）按 `metrics.minutes / metrics.wave` 分别 upsert 两张表，`ON CONFLICT (person_id, period)`；两者唯一键与 001/026 一致，落库路径没有交叉写。边界例外：累计口径里时长用了整月值、音浪没用（发现 3）。
- **② 月 / 年榜优先用整月值、缺月回落日明细** —— **真，且是「取代」不是「相加」**。`period_rollup_sql` 用 `COALESCE(mw.wave, t.w)` / `COALESCE(md.minutes, t.dm)`（dialect.rs:337、328），两值并存时取整月值；`month_wave_only` 补齐行带 `NOT EXISTS`（dialect.rs:355-357）保证同一人同一月只走一路，**不存在音浪翻倍**。回落开关互相独立（dialect.rs:396-416，有单测钉住）。缺口：只覆盖 `daily_metric` 主号口径（发现 1）。
- **③ 「我的」页分号：主号 daily_metric、副号 wave_snapshot，is_primary 互斥不重复计** —— **真，四处口径一致**：`dialect.rs:71`（WAVES_A）、`minutes.rs:615/621`（`/my/accounts`）、`push.rs:1278/1286`（推送分号），主号分支一律 `is_primary = 1`、副号一律 `is_primary = 0`，且 `account.anchor_id` 有 `uk_anchor` 唯一索引，一个号不可能同时落两边。真值源是 `account.is_primary`，`ensure_primary`（admin.rs:2096-2132）在每次导入时兜底收敛；但**切换主号不会同步历史 `daily_metric.anchor_id`**（发现 5）。
- **④ 时长统一显示 x时x分（不带秒）** —— **单位一致，格式化一致**。`csvparse::parse_duration`（csvparse.rs:201-238）把 `2:30:45` / `37小时16分钟5秒` / `150分钟` 全部换算成**分钟**；`monthly_duration.minutes` 同为分钟（001_core.sql:184）；三处格式化逐字同构：`push.rs:88`、`st_page.html:1933`（`minFmt`）、`ImportPage.tsx:126`（`hourText`），并有 `fmt_minutes_matches_display_format` 单测钉住边界（108→1时48分、120→2时、1440→24时）。**没有把秒当分钟**。缺口：机器人侧拿不到时长（发现 8）。
- **⑤ 按日导入不写 `daily_metric.minutes`** —— **真**。`strip_minutes` 双保险：`body_rows`（admin.rs:1392-1396）与 `commit_import`（admin.rs:1701），机器人两条导入路径（bot/mod.rs:1006、1501）都走 `commit_import`，因此进 `import_pending` 的行 `minutes` 已是 None，`absorb_pending` 的叠加分支（admin.rs:2382）不会把时长写回日明细。唯一写 `daily_metric.minutes` 的路径仍是 `/import/month/*`。
- **⑥ 019 / 021 与导入幂等唯一键同口径** —— **真**（附加核实）。001 已用带表前缀的名字 `uk_monthly_metric_person_period` / `uk_person_period`（monthly_duration）/ `uk_monthly_wave_person_period`（026），019 是幂等 no-op，无跨表撞名；021 用新名 `uk_wave_snapshot_anchor_date` 补上 `wave_snapshot(anchor_id, biz_date)`，与导入侧 `ON CONFLICT (anchor_id, biz_date)`（.dbmerge/merge.py:170）同键。按日导入幂等键 `daily_metric(person_id, biz_date)`、月度导入 `(person_id, period)`、暂存 `(douyin_no, biz_date)` 各管各的表，未发现「不同键导致重复计或二次导入判重复丢数据」。019/021 均已登记在 `migrate.rs:76、88`。
